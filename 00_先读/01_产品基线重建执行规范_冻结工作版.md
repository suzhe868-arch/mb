## 3.1 当前已实现 / 已测试事实优先识别规则｜2026-10-04 新增强制规则

> 本规则补强原有“9/19 主底盘 + 前后历史反查 + 知情修改测试 + 用户裁决”方法，不替代原方法。

### 3.1.1 核心原则

进入任何 PDM、跨系统架构、API、数据同步、鉴权、缓存、回调、部署边界判断前，必须先识别：

> **当前真实系统已经实现了什么、实际怎么运行、哪些版本已经测试 / 验收。**

“当前已实现 / 已测试事实”首先用于回答“现在系统事实上是什么”，防止历史中间方案、推荐方案、旧摘要覆盖已经验证过的当前实现。

但：

> **已实现 ≠ 自动成为最终产品权威。**

若当前实现与用户明确裁决、正式业务规则或当前产品基线冲突，必须进入显式冲突复核，不得因为“代码已经这么做了”就自动修改产品规则。

### 3.1.2 固定证据分层

后续证据必须至少分成以下层级，不允许混为同一种“文档证据”：

1. **CURRENT_IMPLEMENTED_FACT**
   - 当前运行版本；
   - 已实现代码 / 配置；
   - CURRENT_HANDOFF；
   - 已执行测试、验收报告；
   - 实际接口 / 数据流 /运行行为。

2. **USER_DECISION / PRODUCT_AUTHORITY**
   - 用户后续明确裁决；
   - Decision Register；
   - 已批准 PDM 最终规则；
   - 正式产品业务基线。

3. **919_ANCHOR_AND_FORMAL_HISTORY**
   - 9/19 主底盘；
   - 9/22 冻结台账；
   - 更早已冻结正式规则。

4. **HISTORICAL_PROPOSAL / INTERMEDIATE_DESIGN**
   - “建议 / 推荐 / 候选 / 待实现 / 未施工”；
   - 中间版本设计；
   - 旧架构草案；
   - 未经测试的工程建议。

5. **RADAR / DERIVED_CARRIER**
   - 001～078；
   - IA / Low-Fi / Engineering Delta 中仅用于发现问题、承载规则而非创造业务权威的内容。

### 3.1.3 冲突处理

出现冲突时，必须先区分两件事：

- **当前事实是什么**：由 CURRENT_IMPLEMENTED_FACT 证明；
- **当前最终应该是什么**：由产品权威、历史谱系、用户裁决共同决定。

固定判定：

- 当前实现与历史推荐方案冲突：不得让历史推荐方案覆盖当前实现事实；
- 当前实现与正式产品权威一致：可作为强验证证据；
- 当前实现与正式产品权威冲突：标记 `CURRENT_IMPLEMENTATION_CONFLICT`，不得自动选择任一方；
- 历史正式规则与后续实现不同：必须继续执行“知情修改测试”，确认这是有意演进还是错误施工；
- 无法判断时标记 `EVIDENCE_INCOMPLETE`，交用户裁决。

### 3.1.4 跨系统 / API 架构强制三问

凡涉及 API、Webhook、回调、同步、Collector、外部系统、鉴权、Base URL、Path、Token、缓存等问题，继续推导前必须先回答：

1. **谁提供 API？**
2. **谁调用 API？**
3. **数据实际往哪个方向流？**

并同时确认：

- 当前实际运行版本；
- 是否已经施工；
- 是否已经测试 / 验收；
- 当前调用链与旧方案是否一致。

上述事实未确认前，禁止继续推导：

- Base URL / Path 应归谁配置；
- Token / Secret 应归谁持有；
- 是主动请求还是回传；
- 缓存归属；
- P03 / PC 后台应配置什么；
- 是否需要新增连接配置。

### 3.1.5 每个 PDM 的“当前实现事实卡”

每个涉及已有工程实现的 PDM，在 Batch 1 前或首次发现实现证据时，必须建立最小事实卡：

```text
CURRENT IMPLEMENTATION FACT
- 当前版本：
- 谁是数据源：
- 谁提供 API：
- 谁调用 API：
- 数据流方向：
- 已实现：
- 已测试 / 已验收：
- 已废弃旧实现：
- 与产品权威是否冲突：
```

该事实卡只作为当前现实基线，不直接替代产品裁决。

### 3.1.6 禁止事项

禁止：

- 把“历史上写过”直接等同于“现在系统就是这样”；
- 把“建议 / 推荐”当成已施工事实；
- 把旧中间版本覆盖已测试的当前实现；
- 因“代码已经实现”而自动推翻用户已确认规则；
- 未确认 API 提供方 / 调用方 / 数据方向就继续讨论 URL、Path、Token、缓存和权限；
- 用模型旧记忆替代当前实现证据。

### 3.1.7 与原六步法的结合

原“每个业务点固定六步法”继续有效，但执行顺序补强为：

```text
先识别 CURRENT_IMPLEMENTED_FACT（如存在）
→ 看 9/19 正向规则
→ 向前扫历史
→ 读取 001～078 雷达
→ 向后扫 9/22 / IA / Low-Fi / Engineering
→ 做知情修改测试
→ 对“当前实现 vs 产品权威”再做冲突校验
→ 形成候选规则
→ 四批用户审查
```

一句话：

> **先搞清楚系统现在实际上怎么跑，再判断它业务上应该怎么跑；已实现事实不能被旧方案污染，已实现事实也不能绕过产品裁决。**

## 3.2 信息保真 / 一次性收口硬门禁｜2026-10-04 强制升级

> 目标：解决“规则写过很多轮，但越合并越丢细节、后续 PDM 又忘记前序裁决”的系统性问题。  
> 本节优先级高于任何依赖模型记忆、单一版本、单一模块、摘要继续摘要或仅以 `UNMAPPED=0` 判定完整的旧做法。  
> **任何 PDM 从本节生效后开始，不满足本节全部适用门禁，不得进入 COMPLETE。**

### Gate 1｜Memory Zero-Trust｜记忆零信任

涉及以下任何判断时，禁止直接依据模型记忆、聊天上下文、其他窗口摘要或“刚才记得是这样”下结论：

- 当前规则是什么；
- 历史有没有某规则；
- 某规则是否已被用户确认；
- 某规则是否已废弃 / 替代；
- 前序 PDM 当前最终规则是什么；
- 当前仓库已经实现 / 测试什么；
- 当前状态、下一步或已完成范围是什么。

记忆只允许用于：

> **提示应该去仓库哪里检索。**

最终判断必须重新读取当前 GitHub 文件。

以下情况必须强制刷新，即使同一聊天前面刚读过：

- 仓库在当前会话中已发生修改；
- 中间发生过用户新裁决、reopen、supersession；
- 经过较长讨论后重新回到旧问题；
- 涉及跨 PDM / 跨域判断；
- 准备输出“当前最终规则”“没有”“已废弃”“已完成”等强结论。

若 GitHub 当前文件与聊天记忆冲突：

> **先报告冲突，禁止用记忆覆盖仓库。**

### Gate 2｜Current Authority Refresh｜当前权威刷新

每个 PDM、每个 Batch、以及任何高影响规则原子开始判断前，至少重新确认：

1. `CURRENT_PROJECT_STATE.md`
2. `NEXT_ACTION.md`
3. `PROJECT_STATE.json`
4. `07_重建工作区/DECISION_REGISTER.md`
5. 当前 PDM 工作版
6. 所有已完成且与该原子相关的 PDM 正式 Final
7. 当前用户在本轮已经确认但尚未进入 Final 的有效裁决

当前产品 Authority 的判断优先顺序：

> **当前用户明确裁决 / 已批准 PDM Final / Decision Register**
> → 历史正式规则
> → 当前实现事实用于验证现实
> → IA / Low-Fi / Delta 用于承载与冲突发现

9/19、9/22、R1～R12、IA、Low-Fi 均不得绕过当前已批准 PDM Final 成为“当前最终答案”。

### Gate 3｜PDM Scope ≠ Evidence Scope｜业务域不等于证据边界

PDM 只决定：

> **这条最终规则归哪个业务域负责收口。**

PDM 不限制证据读取范围。

任何原子只要触及其他域的核心对象 / 不变量，就必须读取对应正式规则。

禁止：

> “这是价格域，所以只读价格文件”  
> “这是图片域，所以不看 Vehicle lifecycle”  
> “这是电话域，所以不看权限域”

跨域读取不是例外，而是默认要求。

### Gate 4｜Completed-PDM Dependency Card｜已完成 PDM 强制依赖卡

任何新 PDM 在 Batch 1 前必须建立一张：

> **Completed-PDM Dependency Card**

至少列出：

- 当前 PDM 涉及的核心对象；
- 当前 PDM 会读取 / 修改的全局不变量；
- 哪些已完成 PDM 对它形成上游约束；
- 每个依赖 PDM 的具体约束条款；
- 当前 PDM 允许补充什么；
- 当前 PDM 绝对不能静默改写什么。

格式至少包含：

| 依赖 PDM | 约束对象 | 当前有效规则 | 本域可补充 | 本域不可改写 |
|---|---|---|---|---|

没有完成依赖卡：

> **不得进入 Batch 1。**

依赖卡不能凭记忆填写，必须来自重新读取的正式 Final / Decision Register。

### Gate 5｜Global Invariant Gate｜全局不变量门禁

维护并持续检查以下跨域全局不变量：

- identity / 唯一身份；
- role；
- permission；
- data scope；
- hard DENY；
- owner / responsibility；
- vehicle_id；
- source_type；
- listing_cycle；
- visibility / hidden；
- lifecycle / terminal state；
- immutable snapshot；
- audit / history；
- current fact vs historical fact；
- customer-safe view vs internal view。

任何规则原子只要触及其中一项：

> **必须读取该不变量当前权威来源，并在工作底稿写出是否一致。**

不得因为当前 PDM 标题没有写该词，就跳过全局不变量检查。

### Gate 6｜Terminology & Field Normalization｜术语 / 字段统一

每个 PDM 在正式拆 Atom 前必须形成最小术语表：

> 中文业务叫法 ↔ 技术字段 ↔ 历史别名 ↔ 易混淆概念

例如：

- 底价 ↔ `upstream_wholesale_price`
- 上游标价 ↔ `upstream_list_price`
- 基础批发价 ↔ `base_wholesale_price`

固定要求：

1. 同义词必须归一；
2. 近义但不同概念必须显式拆开；
3. 全文搜索必须同时覆盖中文名、英文字段、历史别名；
4. 未完成术语归一前，不得据“关键词没搜到”判断规则不存在。

---

### Gate 7｜No Summary-on-Summary｜禁止摘要继续摘要

禁止以“上一轮总结”作为下一轮唯一来源继续压缩。

不得采用：

> 原始规则 → 摘要 A → 摘要 B → PDM → Final

并在每一层继续丢条件。

固定要求：

- 摘要只可用于定位；
- 最终规则必须回到原始正式证据、用户裁决、已批准 Final；
- 若当前 Final 是由多个 Atom 合并，合并时必须逐项校验条件、例外、否定边界没有丢失；
- “沿用”“其他不变”“参见某文档”不得代替完整规则正文。

---

### Gate 8｜Bidirectional Traceability｜双向可追溯

每个 PDM 必须同时满足两种追溯：

#### A. Source → Final

每一个有效来源规则 / Decision 必须有去向：

- MAPPED
- SUPERSEDED
- DEPRECATED / DO_NOT_RESTORE
- DEFERRED_WITH_TARGET
- ENGINEERING_ONLY
- USER_REJECTED

不得存在无去向的有效规则。

#### B. Final → Source

最终规则中的每一个实质性条款，必须能反向回答：

- 来自哪个用户裁决 / 正式历史规则 / 已批准 PDM；
- 是否是本轮新裁决；
- 如果覆盖旧规则，覆盖哪一条；
- 如果属于补全，补的是什么缺口。

> **只做 Source → Final 的 `UNMAPPED=0` 不足以证明完整。**

必须双向都能追溯。

### Gate 9｜Negative Claim Proof｜否定性结论证明门禁

以下强结论必须经过增强检索，不得靠单次关键词搜索或记忆：

- “没有这个规则”
- “历史从未有过”
- “已经废弃”
- “不需要 permission”
- “不存在这个功能”
- “没有冲突”
- “没有其他遗漏”

至少必须检查：

1. 业务中文词；
2. 技术字段 / 英文别名；
3. 已完成 PDM Final；
4. Decision Register；
5. 9/19 / 前史；
6. 001～078；
7. IA / Low-Fi / Current 中可能的反向承载。

证据不足时必须写：

> `EVIDENCE_INCOMPLETE`

禁止把“没搜到”写成“不存在”。

### Gate 10｜Conflict Before Classification｜先冲突、后分类

Batch 1/2/3/4 分类必须是**完整证据扫描后的最后一步**。

固定顺序：

> 当前 Authority
> → Completed-PDM dependencies
> → Global invariants
> → 当前实现事实（如适用）
> → 9/19
> → 前史
> → 9/22
> → IA / Current
> → Low-Fi
> → 001～078
> → Delta
> → 冲突矩阵
> → 最后才分类 Batch

任何未解释反向证据：

### Gate 11｜Cross-PDM Handoff 双向闭环｜跨域移交不得只写“交后面”

> 2026-10-05 用户明确升级：旧流程只有“来源 PDM 把任务交给后续 PDM”，但缺少“目标 PDM 做完后反向回写来源 PDM”的强制动作，导致已经完成的事项长期仍显示为“留后续”。本 Gate 自本次起改为**双向闭环**。

统一登记文件：

> `07_重建工作区/CROSS_PDM_HANDOFF_REGISTER.md`

该文件是跨域任务状态总账。任何 PDM Final、Decision Register、Integrity Audit、Current State 中出现“留给后续 PDM / 继续由 PDM-XX 承接 / 后续处理”的事项，都必须在该 Register 有唯一 `handoff_id`。

#### 11.1 固定状态

每条 handoff 只能使用以下四种主状态：

- `HANDOFF_OPEN`：来源已正式移交，目标 PDM 尚未完成该事项；
- `HANDOFF_ACCEPTED`：目标 PDM 已明确接收，并已进入其工作版 / Atom / Decision，但目标域尚未 Final CLOSED；
- `HANDOFF_CLOSED`：目标 PDM 已形成最终 Authority，本条移交完成；
- `HANDOFF_SUPERSEDED`：后续明确裁决改变或替代原移交语义；必须记录新的 Authority / replacement handoff。

如目标 PDM 改变，不新增第五种状态：旧 handoff 标 `HANDOFF_SUPERSEDED`，并新建一条指向新目标的 `HANDOFF_OPEN`。

#### 11.2 每条 handoff 最低字段

至少记录：

- `handoff_id`；
- 来源 PDM；
- Source Atom / Decision / Final 条款；
- 完整移交语义；
- 目标 PDM；
- 目标必须承接的 Guard / 不变量；
- 当前主状态；
- 目标 Authority / Decision / Final 位置；
- 来源 PDM 是否已反向回写；
- 最后核验日期；
- 如有 supersession，记录 replacement。

只写：

> “价格 → PDM-10”  
> “图片后面处理”  
> “交 PDM-XX”

均视为**无效 handoff**。

#### 11.3 来源 PDM 的责任

来源 PDM 在产生跨域移交时必须：

1. 先写入 Cross-PDM Handoff Register；
2. 写清楚目标 PDM 必须承接什么，不能只写主题名；
3. 写清楚来源域已经冻结、目标域不得静默推翻的 Guard；
4. Final 中保留 handoff_id 或可唯一定位的 handoff 条目；
5. 目标尚未开始时状态为 `HANDOFF_OPEN`。

来源 PDM 可以在仍有合法 `HANDOFF_OPEN` 指向未来 PDM 时 COMPLETE / INTEGRITY_PASS，前提是这些 open handoff 已完整登记，不属于遗漏。

#### 11.4 目标 PDM 的责任

任何目标 PDM 在 Batch 1 / Integrity Audit 开始前必须：

1. 查询 Register 中所有 `target = 当前 PDM` 且状态为 `HANDOFF_OPEN / HANDOFF_ACCEPTED` 的条目；
2. 把每条放入 Completed-PDM Dependency Card / Deferred Handoff Ledger；
3. 逐条形成 Atom / Decision / Final 去向；
4. 接入工作版后改为 `HANDOFF_ACCEPTED`；
5. 在目标 PDM Final / Integrity Gate 前逐条改为 `HANDOFF_CLOSED` 或 `HANDOFF_SUPERSEDED`。

目标 PDM Final 前只要还有一条指向自己的 `HANDOFF_OPEN / HANDOFF_ACCEPTED` 没有明确去向：

> **不得 COMPLETE / INTEGRITY_PASS。**

#### 11.5 目标完成后的反向回写责任

这是本次升级新增的硬规则。

当目标 PDM 将一条 handoff 关闭或替代后，**不能只改目标 PDM**。同一次收口必须检查并更新：

1. Cross-PDM Handoff Register；
2. 来源 PDM Final 的“跨域承接状态 / handoff”章节；
3. 来源 PDM Integrity Audit 报告（如该 PDM 已做过 Integrity Audit）；
4. Decision Register；
5. CURRENT_PROJECT_STATE / NEXT_ACTION / PROJECT_STATE 中仍显示旧状态的地方；
6. 受影响 IA / Low-Fi carrier ledger（产品阶段只登记，不立即施工）。

来源回写完成后，Register 中：

> `source_backwrite = YES`

如果目标已完成但来源仍显示“以后再做”，则即使目标 Authority 正确，该条仍属于：

> **STALE_HANDOFF / SOURCE_BACKWRITE_PENDING**

不得伪装为已完全闭环。

#### 11.6 COMPLETE / INTEGRITY_PASS 的新判定

原 `DEFERRED_HANDOFF_UNRESOLVED = 0` 统一解释为：

- 不存在未登记的 deferred；
- 不存在指向**已经 COMPLETE 的目标 PDM**却仍保持 OPEN 的 handoff；
- 不存在目标已经 CLOSED / SUPERSEDED 但来源未反向回写的 stale handoff；
- 当前 PDM 作为目标时，没有未处理 incoming handoff；
- 指向尚未开始的未来 PDM 的合法 `HANDOFF_OPEN` 可以存在，但必须已完整登记。

另外新增：

> `HANDOFF_REGISTER_SYNC = PASS`

没有 PASS：

> **不得 COMPLETE / INTEGRITY_PASS。**

#### 11.7 历史补录

本规则生效时，必须对已经完成的 PDM 做历史回填，不允许“从今天以后才管”。

当前首先回填：

> **PDM-01 ～ PDM-04 已出现的 integrity 问题、已完成 handoff、仍开放 handoff、stale carrier 与 PDM-04 当前审计中发现的 handoff 候选。**

以后每完成一个 PDM，都必须同步更新 Register。

禁止再次出现：

> “来源 PDM 写了交给后面 → 后面其实已经做完 → 来源还一直显示未做 → 到下一次全局审计才重新发现”。

## 3.3 Legacy Final Integrity Audit Gate｜PDM-01～PDM-10 强制补做全域完整性复核

> 生效日期：2026-10-04
> 目的：把在 §3.2 新信息保真门禁生效前已经完成的 PDM-01～PDM-10，统一补过今天的完整性标准。
> 本阶段不是推倒重做，也不是仅检查现有 Final 是否写得更细；必须同时重新查整条遗漏、语义细节缺失与跨 PDM 冲突。

### 3.3.1 适用范围与顺序硬门禁

适用范围固定为：

> **PDM-01 ～ PDM-10 全部正式 Final。**

执行顺序固定：

```text
PDM-01～PDM-10 Legacy Final Integrity Audit
→ PDM-01～PDM-10 全局 Cross-PDM / Handoff / Global Invariant 总复核
→ 全部门禁 PASS
→ 才允许开始 PDM-11
→ PDM-11 及以后按 §3.2 新标准正常重建
```

在 PDM-01～PDM-10 本轮复核未全部通过前：

- 禁止开始 PDM-11 Batch 1；
- 禁止把 PDM-11 标为当前正式在审业务域；
- 禁止用“PDM-01～10 以前已经 COMPLETE”为理由跳过本轮；
- 禁止直接进入 IA / Low-Fi / Engineering；
- 禁止把本轮复核降级为只检查格式、摘要或 Final 文案。

原 PDM-01～PDM-10 的 `COMPLETE` 保留为“当时已经完成用户裁决”的历史状态，不自动作废；但在本轮审计通过前，不得声称这些旧 Final 已经满足当前 §3.2 的 Final Semantic Integrity / Implementation-Ready 标准。

### 3.3.2 三层审查必须同时执行

每个 PDM 都必须执行以下三层，缺一不可：

#### A. Missing Rule Audit｜整条遗漏复核

必须重新从源头反查，而不是只读当前 Final。至少覆盖：

- 9/19 主底盘 / R1～R12；
- 9/19 以前更早正式规则与 CN11；
- 9/19 以后用户明确裁决；
- Decision Register；
- Current / IA / Low-Fi；
- 001～078 历史反向差集；
- deferred handoff；
- Current Implementation Fact / Engineering Delta 中能够暴露业务遗漏的事实。

目标是发现：

> **有没有整条业务规则、例外、角色边界、生命周期分支或历史事实压根没有进入当前 PDM Final。**

任何“未发现遗漏”都属于 Negative Claim，必须按 Gate 9 做多路证明。

#### B. Semantic Detail Audit｜已有规则语义细节复核

对 Final 已经存在的每条核心规则，必须回原始证据检查是否因摘要压缩丢掉：

- 对象 / 唯一标识；
- actor / role；
- permission；
- data scope；
- hard DENY；
- owner / responsibility；
- 前置条件；
- object state；
- listing_cycle / lifecycle；
- 空值 / 无结果；
- 失败 / timeout / retry；
- 并发 / 幂等；
- 等级 / 权限 / owner 变化；
- 日期 / TTL / 业务日；
- 配置与生效边界；
- immutable snapshot；
- audit / history；
- C / E / P 端必要业务表现；
- DO_NOT_RESTORE；
- 跨 PDM 依赖与例外。

目标是发现：

> **规则主结论还在，但条件、例外、权限、安全边界、时间边界或历史语义被压没。**

#### C. Cross-PDM Integrity Audit｜跨 PDM 完整性复核

必须检查 PDM-01～PDM-10 相互之间：

- 同一全局不变量是否出现不同定义；
- 后 PDM 是否静默覆盖前 PDM；
- 前 PDM 的 handoff 是否被目标 PDM 真正接住；
- supersession 是否只存在于聊天而未写进旧 Final；
- stale rule / stale carrier 是否仍可能误导后续施工；
- 同一对象在不同 PDM 的 lifecycle / permission / owner / source_type / listing_cycle 是否一致。

### 3.3.3 不是全量重做：按问题 reopen

本阶段不重新机械执行 PDM-01～PDM-10 的四批全流程。

每个旧 PDM 审计结果只允许归类为：

| 状态 | 含义 | 处理 |
|---|---|---|
| `INTEGRITY_PASS` | 未发现整条遗漏、语义缺失或跨 PDM 冲突 | Final 不改，记录 PASS |
| `MISSING_RULE` | 发现整条有效规则未进入 Final | reopen 对应 Atom / 新建补漏 Atom，提交用户审查 |
| `SEMANTIC_DETAIL_GAP` | 主规则存在但条件/例外/权限等不完整 | 只 reopen 对应规则段，不推倒整个 PDM |
| `CROSS_PDM_CONFLICT` | 与其他已批准 PDM 冲突 | 显式列出冲突并交用户裁决 |
| `STALE_RULE` | Final 内仍留被后规则覆盖的旧语义 | 写明 supersession / 修正旧 Final |
| `HANDOFF_GAP` | 有“后续处理”但目标 PDM 未承接完整 Guard | 补完整 handoff，并登记目标接收状态 |
| `EVIDENCE_INCOMPLETE` | 证据不足，不能安全判断 | 暂停该点，不得假设 PASS |

只有真正发现问题的 Atom / 段落才 reopen；已经完整且无冲突的规则不重复让用户重新裁一遍。

但凡需要改变现行产品业务语义、补入此前没有被用户批准的新规则、或处理真实 A/B 选择，仍必须按“用户全量审查门禁”显式提交用户确认。

### 3.3.4 每个 PDM 的强制审计流程

每个 PDM 固定执行：


IA / Low-Fi 只能作为承载与冲突发现证据，不能反向覆盖已批准 PDM Final。

### 3.4.3 为什么不在 PDM-10 后先改一轮

PDM-11～PDM-25 仍会继续定义 Demand、Recommendation、Consultation、CRM、公海 / Collaboration、Lock / Waitlist、Transaction、客户端、员工端、PC 后台、通知 / 审计等大量跨页面规则。

> **在 PDM-25 前提前集中整改 IA / Low-Fi 会造成二次甚至多次返工。**

统一延后到 PDM-25 与全局总复核完成后，让 IA / Low-Fi 一次性接收完整产品 Authority。

### 3.4.4 硬门禁

在 PDM-25 完成并通过 PDM-01～25 全局最终总复核前：

- 不启动全量 IA Alignment；
- 不启动全量 Low-Fi Alignment；
- 不因 stale carrier 与产品 Final 冲突而修改产品 Authority；
- 发现 carrier 问题必须挂账，不得丢失；
- 不以“暂时不改 IA / Low-Fi”为理由跳过 carrier 冲突扫描。

> **现在负责把产品规则做对、把 carrier 错误记全；PDM-25 后统一把 IA / Low-Fi 做对。**

### 3.4.5 PDM-25 后 Final / Integrity 历史阶段尾巴统一收口｜2026-10-05 用户冻结

PDM-01～PDM-25 重建过程中，各 PDM Final、Integrity Audit、阶段报告会自然保留当时真实的“下一审计域 / PDM-XX BLOCKED / 当前进入某阶段”等历史进度文字。这些内容属于审计轨迹，不得在 PDM-11～25 施工过程中反复批量清理，以免一边推进、一边持续重写历史记录。

固定规则：

1. **PDM-25 完成并通过 PDM-01～25 全局最终总复核前，不启动全量历史阶段尾巴清理。**
2. `README.md`、`CURRENT_PROJECT_STATE.md` 顶部当前快照、`NEXT_ACTION.md`、`PROJECT_STATE.json` 等**当前控制入口必须始终保持真实当前状态**；发现 stale current pointer 仍应立即修正，不受本条延后规则限制。
3. PDM Final / Integrity Audit / 阶段审计报告中，当时真实发生过的阶段状态、BLOCKED、下一步、目标域等历史事实**不得物理删除**。
4. PDM-25 + 01～25 全局最终总复核 PASS 后，统一扫描 PDM-01～25：Final 文件、Integrity Audit 报告、最终总览 / Coverage / 阶段审计报告中可能被误读为“当前状态”的尾部文字，以及其他会被新窗口当作 Current 的阶段性提示。
5. 统一收口方式是**清理歧义 + 标注边界**，不是删除历史：当前仍有效的状态标为 Current；仅在当时有效的“下一步 / BLOCKED / 当前进入”明确标为 `HISTORICAL_AUDIT_TRAIL` 或放入带日期的历史审计段；已被后续阶段完成的旧指针不再作为文件当前结论展示；业务规则正文、用户裁决、Source→Final / Final→Source 追溯不得因此改写。
6. 本轮统一清理必须产出机械检查报告，至少证明：stale current pointer = 0；历史审计事实保留；Final 业务语义变化 = 0；PDM-01～25 当前状态入口一致。
7. **该统一清理完成后，才进入 IA 全局集中对齐。**

推荐固定顺序：

```text
PDM-25 COMPLETE
→ PDM-01～25 Global Final Audit PASS
→ Final / Integrity 历史阶段尾巴统一清理与 Current / History 标注
→ IA Alignment
→ Low-Fi Alignment
→ Engineering
```

一句话：

> **PDM-11～25 期间不反复擦历史尾巴；PDM-25 全局收口后一次性把“当前状态”和“历史审计轨迹”彻底分开，同时保留历史证据。**

## 5. 第 1 阶段以后｜每个业务点固定六步法

对任意业务点，不再以“版本”为判断单位，而以**业务规则原子**为单位。

### Step 1｜看 9/19 正向规则

先明确 9/19 当时：

- 对象是什么；
- 谁能做；
- 什么时候做；
- 正常结果是什么；
- 有哪些异常 / 并发 / 超时 / 历史边界。

### Step 2｜向前扫描 9/19 以前历史

确认：

- 是否存在更完整定义；
- 9/19 是否漏掉细节；
- 是否长期多版本一致；
- 是否明确废弃 / 被替代；
- 是否只是旧实现细节，而不是业务原则。

### Step 3｜读取 001～078 雷达

检查该业务点是否已经出现：

- 历史遗漏；
- 规则冲突；
- Current / IA / Low-Fi 承载不足；
- 旧判断可能有误。

**只取证据线索，不直接继承结论。**

### Step 4｜向后扫描 9/19 → 9/22

必须同时读取：

- 9/22 冻结台账；
- IA V5 / Current；
- 实际 Low-Fi；
- 工程总闭环待执行 Delta。

确认：

- 后来新增了什么；
- 后来修改了什么；
- 哪些只是结构/页面自己推导出来的；
- 哪些问题后来已发现但没施工。

### Step 5｜执行“知情修改测试”

凡后续规则与 9/19 / 更早规则不同，必须判断：

#### PASS｜知情修改

必须有证据证明当时讨论明确知道旧规则 A，并主动决定改成 B，例如：

- 明确引用旧规则；
- 明确说明“原来是 A，现在改成 B”；
- 有 Decision / 用户裁决说明替代关系；
- 旧规则的关键影响已在讨论中被考虑。

→ 标记：`POST_919_INFORMED_CHANGE_CANDIDATE`

仍需在本轮最终基线收口时确认吸收，但可视为强候选。

#### FAIL｜疑似非知情修改

出现以下任一情况：

- 后续直接得出 B，却没有体现知道 A；
- 后续讨论基于已经压缩的 IA / Low-Fi；
- 只是页面 / 状态 /工程结构自行推导；
- 后续 FROZEN 只证明“当时冻结”，不能证明看过旧规则；
- 新规则与历史长期稳定规则冲突，却没有解释为什么改变。

→ 标记：`POST_919_UNINFORMED_CONFLICT`

**不能因为 9/22 更晚或 FROZEN 就判旧规则失效，必须重新交用户裁决。**

### Step 5A｜Batch 2 / Batch 3 入批前反向冲突门禁｜2026-10-04 新增强制规则

> 本门禁用于防止“后来的总结文件写了废弃 / FROZEN / CURRENT，就把较早正式规则直接判死”的 latest-wins 回归。

任何规则原子准备进入：

- Batch 2｜明确废弃 / 明确替代 / DO_NOT_RESTORE；
- Batch 3｜明确知情修改 / 后续明确新增；

之前，必须完成一次**反向冲突检查**，不得只依据单一后期文件分类。

固定检查至少包括：

1. **前史正式规则**：9/19 以前是否存在相反的正式规则、长期稳定规则或更完整定义；
2. **9/19 主锚点**：9/19 对该点实际怎么定义，是否已经发生摘要压缩；
3. **后续修改证据**：所谓“废弃 / 修改”是否有明确用户裁决、Decision 或可证明的知情修改过程，而不只是某份后期总结自行写成结论；
4. **Current / IA / Low-Fi 反向承载**：后续实际承载是否又出现与“已废弃 / 已修改”相反的 permission、Action、State、页面或交互；
5. **001～078 雷达**：是否已将该点标为冲突、反向复活、历史规则丢失、未收口、Current regression 或 permission pollution；
6. **已完成 PDM / Decision Register**：是否与前序用户已批准规则产生跨 PDM 冲突。

固定判定：

- 上述各层一致，且替代关系证据充分 → 才允许进入 Batch 2 / Batch 3；
- 只要任一层存在真实相反证据、替代关系无法证明、Current 又反向承载，或 001～078 已标记未收口 → **禁止把该项作为 Batch 2 / Batch 3 的确定项**；
- 此类规则必须标记为 `CROSS_EVIDENCE_CONFLICT` / `POST_919_UNINFORMED_CONFLICT` / `HISTORICAL_UNRESOLVED` 中适用状态，并强制进入 **Batch 4** 由用户显式裁决；
- “文件日期更晚”“写了 CURRENT / FROZEN / 废弃”“已进入 IA / Low-Fi”均不能单独证明旧规则已经合法失效；
- 若错误分类已经被用户在早一批次确认，后续发现真实冲突时必须**回开该规则原子**，记录 supersession / reopen 关系并重新裁决，不得因为“已经确认过”而继续保留错误结论。

强制输出要求：

> 对任何准备进入 Batch 2 / Batch 3 的规则，工作底稿必须能够回答“前史有没有相反正式规则、后续有没有反向承载、001～078 有没有报过冲突、已确认 PDM 有没有相反约束”。

无法回答完整时，不得入 Batch 2 / Batch 3。

本门禁的直接教训来源于 PDM-10 内部价查看权限：R4 存在“permission + data scope”正式规则，R11 后来取消独立 permission，但 IA V5 又部分恢复 CONDITIONAL permission，001～078 已明确记录反向复活；该项不应被直接归为 Batch 2/3 确定项。

- 只改业务文件、不更新项目状态；
- 状态文件声称已完成，但业务文件尚未落地；
- 多个互相独立的大范围修改堆积后一次性无说明 commit；
- 用聊天记忆替代 Git 当前文件状态。

## 14. 新窗口固定接力口径

后续任何新窗口应按以下原则接力：

> **以 GitHub 当前仓库文件为准，不使用旧聊天记忆替代证据。先读取项目状态入口与执行规范，报告当前阶段、已完成项、未完成项、下一步，再继续施工。**

如果 GitHub 状态与聊天陈述冲突，先报告冲突，不自动选择较新的聊天陈述覆盖仓库。

## 15. 用户全量审查四批门禁｜2026-09-23 新增强制规则

> 本节优先级高于前文任何“稳定项可直接保留 / 通常无需用户裁决”的旧表述。若有冲突，以本节为准。

### 15.1 核心原则

**任何业务规则原子，无论模型判断为稳定一致、明确废弃、明确替代、知情修改、历史遗漏、冲突、缺口或新选择，都不得未经用户本人审查直接进入最终产品业务基线。**

模型职责仅限于：

- 读取证据；
- 还原规则；
- 分类；
- 标记风险；
- 给出建议。

模型**没有自动批准业务规则的权限**。

所有规则原子在用户审查前统一处于：

`USER_REVIEW_PENDING`

只有用户明确审查后，才允许变更为：

- `USER_APPROVED`
- `USER_MODIFIED`
- `USER_REJECTED`
- `USER_DEFERRED`

### 15.2 每个 PDM 固定四批用户审查

#### 第一批｜稳定一致项

范围：

- `STABLE_CONSISTENT`
- 前后证据高度一致、模型建议直接保留的规则。

要求：

- 必须把本批全部规则原子展示给用户；
- 不能只写“稳定一致，全部保留”；
- 每条至少包含 Atom ID + 完整候选规则表述 + 简要证据结论；
- 用户可“本批全部通过”，也可逐条修改 / 否决 / 暂缓。

#### 第二批｜明确废弃 / 明确替代 / DO_NOT_RESTORE 项

范围：

- 有明确证据证明旧规则已经废弃、被替代或禁止恢复的规则。

要求：

- 展示旧规则；
- 展示废弃 / 替代依据；
- 展示当前拟保留规则或 `DO_NOT_RESTORE` 结论；
- 用户确认后才允许正式标记废弃 / 替代。

#### 第三批｜明确知情修改 / 后续明确新增项

范围：

- `POST_919_INFORMED_CHANGE_CANDIDATE`
- 有充分证据证明后续讨论明确知道旧规则并主动改动；
- 后续明确新增且来源完整的规则。

要求：

- 展示旧规则 → 新规则 → 修改原因 / 证据；
- 即使“知情修改测试”PASS，也必须由用户本人再次过目确认；
- 不得因 `FROZEN`、版本更新或 IA 已施工而自动采用。

#### 第四批｜冲突 / 历史遗漏 / 证据缺口 / 新选择项

范围包括但不限于：

- `PRE_919_OMISSION_CANDIDATE`
- `POST_919_UNINFORMED_CONFLICT`
- `IA_LOWFI_ONLY`
- `HISTORICAL_UNRESOLVED`
- `EVIDENCE_INCOMPLETE`
- 需要 A/B/C 业务方案选择的项。

要求：

- 必须展开来源差异；
- 不能替用户补业务选择；
- 必要时拆成更小的子问题逐项讨论；
- 用户明确裁决后才可进入最终规则。

### 15.3 批次硬停止

每一批都必须：

> 生成本批审查清单 → 展示给用户 → **停止等待用户审查**

未经用户明确确认：

- 不得自动进入下一批；
- 不得把本批候选写成最终规则；
- 不得将 PDM 标记 COMPLETE；
- 不得开始下一个 PDM。

### 15.4 PDM 最终总览门禁

四批全部审查完成后：

1. 生成该 PDM 的**完整、自包含最终规则草案**；
2. 不使用“沿用旧版 / 其他不变”等摘要代替规则；
3. 再交用户做一次 PDM 级最终总览审查；
4. 只有用户明确确认后，才能：
   - 写入正式中文产品基线；
   - 更新 Decision Register；
   - 将该 PDM 标记 `COMPLETE`；
   - commit；
   - 进入下一个 PDM。

### 15.5 禁止摘要继续作为证据

后续任何裁决必须重新回到原始证据链。

禁止：

> 原始证据 → 摘要1 → 摘要2 → 合并摘要 → 用户裁决

固定允许：

> 原始证据 → 规则原子索引 → 原文级比较 → 四批用户审查 → PDM最终总览 → 最终规则

地图、工作版、审查清单都只是索引 / 工作产物，**不能替代原始证据成为下一轮业务事实来源**。

### 15.6 一句话门禁

> **模型负责查清楚，用户负责逐批确认；没有任何“看起来没问题”的规则可以绕过用户审查进入最终产品基线。**

### 15.7 已确认规则的持续继承与冲突门禁

用户在前序批次、前序规则原子或前序 PDM 中已经明确确认的业务规则，必须作为后续筛选、比较、重建和裁决的**当前有效约束**持续继承。

后续执行必须遵守：

1. 后续任何规则原子与已确认规则存在交叉时，必须主动对照已确认规则，不得重新从零判断；
2. 后续证据若与已确认规则一致，应明确标记为继承/一致，不重复制造新裁决；
3. 后续证据若与已确认规则冲突，必须显式标记冲突，并重新交用户裁决；
4. 未经用户再次明确确认，不得以“版本更晚 / FROZEN / IA 已施工 / Low-Fi 已承载 / 工程已实现”等理由静默覆盖已确认规则；
5. 同一 PDM 内，前一批已确认规则立即成为后一批审查的约束；
6. 一个 PDM 通过最终总览后，其最终规则成为后续 PDM 的上游产品约束；
7. 如后续确需修改既有已确认规则，必须登记“原规则 → 冲突证据/修改原因 → 用户新裁决 → 替代关系”，并更新 Decision Register；
8. 已确认规则的正式跨窗口继承以 GitHub 当前文件和 Decision Register 为准，不依赖聊天记忆。

一句话门禁：

> **前面用户已经确认的规则，后面必须继续继承；发现冲突只能显式重审，不能失忆、重置或静默覆盖。**
