## 5. 第 1 阶段以后｜每个业务点固定六步法

对任意业务点，不再以“版本”为判断单位，而以**业务规则原子**为单位。

### Step 1｜看 9/19 正向规则

先明确 9/19 当时：

- 对象是什么；
- 谁能做；
- 什么时候做；
- 正常结果是什么；
- 有哪些异常 / 并发 / 超时 / 历史边界。

### Step 2｜向前扫描 9/19 以前历史

确认：

- 是否存在更完整定义；
- 9/19 是否漏掉细节；
- 是否长期多版本一致；
- 是否明确废弃 / 被替代；
- 是否只是旧实现细节，而不是业务原则。

### Step 3｜读取 001～078 雷达

检查该业务点是否已经出现：

- 历史遗漏；
- 规则冲突；
- Current / IA / Low-Fi 承载不足；
- 旧判断可能有误。

**只取证据线索，不直接继承结论。**

### Step 4｜向后扫描 9/19 → 9/22

必须同时读取：

- 9/22 冻结台账；
- IA V5 / Current；
- 实际 Low-Fi；
- 工程总闭环待执行 Delta。

确认：

- 后来新增了什么；
- 后来修改了什么；
- 哪些只是结构/页面自己推导出来的；
- 哪些问题后来已发现但没施工。

### Step 5｜执行“知情修改测试”

凡后续规则与 9/19 / 更早规则不同，必须判断：

#### PASS｜知情修改

必须有证据证明当时讨论明确知道旧规则 A，并主动决定改成 B，例如：

- 明确引用旧规则；
- 明确说明“原来是 A，现在改成 B”；
- 有 Decision / 用户裁决说明替代关系；
- 旧规则的关键影响已在讨论中被考虑。

→ 标记：`POST_919_INFORMED_CHANGE_CANDIDATE`

仍需在本轮最终基线收口时确认吸收，但可视为强候选。

#### FAIL｜疑似非知情修改

出现以下任一情况：

- 后续直接得出 B，却没有体现知道 A；
- 后续讨论基于已经压缩的 IA / Low-Fi；
- 只是页面 / 状态 /工程结构自行推导；
- 后续 FROZEN 只证明“当时冻结”，不能证明看过旧规则；
- 新规则与历史长期稳定规则冲突，却没有解释为什么改变。

→ 标记：`POST_919_UNINFORMED_CONFLICT`

**不能因为 9/22 更晚或 FROZEN 就判旧规则失效，必须重新交用户裁决。**

### Step 6｜形成当前候选结论

每个规则原子只允许进入以下状态之一：

| 状态 | 含义 | 是否需用户重新裁决 |
|---|---|---|
| `STABLE_CONSISTENT` | 前后长期一致，无真实冲突 | **必须用户审查** |
| `PRE_919_OMISSION_CANDIDATE` | 更早完整，9/19 无明确废弃却遗漏 | 是 |
| `POST_919_INFORMED_CHANGE_CANDIDATE` | 后续明确知情修改 | 重要项确认 |
| `POST_919_UNINFORMED_CONFLICT` | 后续与旧规则冲突，未证明知情 | 必须 |
| `IA_LOWFI_ONLY` | 仅 IA/Low-Fi/工程自行表达，没有业务裁决证据 | 必须，或排除 |
| `HISTORICAL_UNRESOLVED` | 历史内部本身没有最终收口 | 必须 |
| `EVIDENCE_INCOMPLETE` | 材料缺失 / 无法证明 | 暂不裁 |

## 6. 讨论阶段的输出纪律

为了避免再次长篇混乱：

### 稳定一致项

不得自动通过。必须把本批全部规则原子以**接近最终基线的完整规则表述**展示给用户审查。

模型只能标记：

> “前后规则一致；建议保留；状态 = USER_REVIEW_PENDING。”

用户明确通过后，才允许进入 `USER_APPROVED`。

### 漏项 / 变化 / 冲突项

必须展开：

1. 早期规则是什么；
2. 9/19 是什么；
3. 9/22 / IA / Low-Fi 后来是什么；
4. 为什么发生差异；
5. 是否通过“知情修改测试”；
6. 选择不同方案分别影响什么；
7. 用户需要裁决什么。

一次只集中处理真实差异，不把全部历史正文重复展示给用户。

## 7. 模块最终收口纪律｜禁止再次摘要丢细节

一个业务域裁完后，生成的“当前最终规则”必须完整、自包含，至少覆盖：

- 目标 / 业务定义；
- 核心对象与唯一标识；
- 前置条件；
- 角色；
- 谁能操作；
- 谁不能操作；
- 数据范围；
- 正常流程；
- 状态与生命周期；
- 异常；
- 并发 / 幂等；
- 超时 / TTL / 业务日；
- 配置与配置生效边界；
- 历史 / 审计；
- 跨对象影响；
- 客户端 / 员工端 / PC 的必要业务表现；
- 明确废弃 / DO_NOT_RESTORE；
- 与其他模块的依赖。

最终文件禁止只写：

- “沿用 9/19”；
- “其他不变”；
- “按 R4”；
- “参见 VR-X-xxx”；
- “历史规则继续有效”。

这些只能出现在来源说明，不能代替最终规则正文。

## 12. GitHub 长期工作底座规则

GitHub 仓库固定作为后续跨窗口、跨模型、跨执行环境的**长期项目工作底座**。聊天窗口不再承担唯一状态保存职责。

仓库根目录必须长期维护：

- `README.md`：仓库用途、证据边界、入口说明；
- `CURRENT_PROJECT_STATE.md`：当前阶段、已完成、进行中、阻塞项、当前权威版本；
- `NEXT_ACTION.md`：下一步唯一优先动作与当前禁止事项；
- `PROJECT_STATE.json`：供 ChatGPT / Codex / 自动化脚本读取的机器状态；
- `07_重建工作区/DECISION_REGISTER.md`：所有真正业务裁决的持续登记；
- `SOURCE_MANIFEST_SHA256.csv`：本包证据文件完整性索引。

任何新聊天窗口接手时，固定先读取：

1. `README.md`
2. `CURRENT_PROJECT_STATE.md`
3. `NEXT_ACTION.md`
4. `PROJECT_STATE.json`
5. `00_先读/01_产品基线重建执行规范_冻结工作版.md`
6. `07_重建工作区/DECISION_REGISTER.md`

然后再进入具体业务证据，不依赖旧聊天记忆直接续作。

## 13. 每轮工作闭环与 Commit 规则

每完成一个可独立验收的工作单元，固定执行：

> **更新业务文件 → 更新 Decision Register → 更新 CURRENT_PROJECT_STATE → 更新 NEXT_ACTION → 更新 PROJECT_STATE.json → 自验 → Git commit**

工作单元优先按“产品域 / 一组强依赖规则 / 一次完整裁决”划分，不按聊天轮次机械 commit。

禁止：

- 只改业务文件、不更新项目状态；
- 状态文件声称已完成，但业务文件尚未落地；
- 多个互相独立的大范围修改堆积后一次性无说明 commit；
- 用聊天记忆替代 Git 当前文件状态。

## 15. 用户全量审查四批门禁｜2026-09-23 新增强制规则

> 本节优先级高于前文任何“稳定项可直接保留 / 通常无需用户裁决”的旧表述。若有冲突，以本节为准。

### 15.1 核心原则

**任何业务规则原子，无论模型判断为稳定一致、明确废弃、明确替代、知情修改、历史遗漏、冲突、缺口或新选择，都不得未经用户本人审查直接进入最终产品业务基线。**

模型职责仅限于：

- 读取证据；
- 还原规则；
- 分类；
- 标记风险；
- 给出建议。

模型**没有自动批准业务规则的权限**。

所有规则原子在用户审查前统一处于：

`USER_REVIEW_PENDING`

只有用户明确审查后，才允许变更为：

- `USER_APPROVED`
- `USER_MODIFIED`
- `USER_REJECTED`
- `USER_DEFERRED`

### 15.2 每个 PDM 固定四批用户审查

#### 第一批｜稳定一致项

范围：

- `STABLE_CONSISTENT`
- 前后证据高度一致、模型建议直接保留的规则。

要求：

- 必须把本批全部规则原子展示给用户；
- 不能只写“稳定一致，全部保留”；
- 每条至少包含 Atom ID + 完整候选规则表述 + 简要证据结论；
- 用户可“本批全部通过”，也可逐条修改 / 否决 / 暂缓。

#### 第二批｜明确废弃 / 明确替代 / DO_NOT_RESTORE 项

范围：

- 有明确证据证明旧规则已经废弃、被替代或禁止恢复的规则。

要求：

- 展示旧规则；
- 展示废弃 / 替代依据；
- 展示当前拟保留规则或 `DO_NOT_RESTORE` 结论；
- 用户确认后才允许正式标记废弃 / 替代。

#### 第三批｜明确知情修改 / 后续明确新增项

范围：

- `POST_919_INFORMED_CHANGE_CANDIDATE`
- 有充分证据证明后续讨论明确知道旧规则并主动改动；
- 后续明确新增且来源完整的规则。

要求：

- 展示旧规则 → 新规则 → 修改原因 / 证据；
- 即使“知情修改测试”PASS，也必须由用户本人再次过目确认；
- 不得因 `FROZEN`、版本更新或 IA 已施工而自动采用。

#### 第四批｜冲突 / 历史遗漏 / 证据缺口 / 新选择项

范围包括但不限于：

- `PRE_919_OMISSION_CANDIDATE`
- `POST_919_UNINFORMED_CONFLICT`
- `IA_LOWFI_ONLY`
- `HISTORICAL_UNRESOLVED`
- `EVIDENCE_INCOMPLETE`
- 需要 A/B/C 业务方案选择的项。

要求：

- 必须展开来源差异；
- 不能替用户补业务选择；
- 必要时拆成更小的子问题逐项讨论；
- 用户明确裁决后才可进入最终规则。

### 15.3 批次硬停止

每一批都必须：

> 生成本批审查清单 → 展示给用户 → **停止等待用户审查**

未经用户明确确认：

- 不得自动进入下一批；
- 不得把本批候选写成最终规则；
- 不得将 PDM 标记 COMPLETE；
- 不得开始下一个 PDM。

### 15.4 PDM 最终总览门禁

四批全部审查完成后：

1. 生成该 PDM 的**完整、自包含最终规则草案**；
2. 不使用“沿用旧版 / 其他不变”等摘要代替规则；
3. 再交用户做一次 PDM 级最终总览审查；
4. 只有用户明确确认后，才能：
   - 写入正式中文产品基线；
   - 更新 Decision Register；
   - 将该 PDM 标记 `COMPLETE`；
   - commit；
   - 进入下一个 PDM。

### 15.5 禁止摘要继续作为证据

后续任何裁决必须重新回到原始证据链。

禁止：

> 原始证据 → 摘要1 → 摘要2 → 合并摘要 → 用户裁决

固定允许：

> 原始证据 → 规则原子索引 → 原文级比较 → 四批用户审查 → PDM最终总览 → 最终规则

地图、工作版、审查清单都只是索引 / 工作产物，**不能替代原始证据成为下一轮业务事实来源**。

### 15.6 一句话门禁

> **模型负责查清楚，用户负责逐批确认；没有任何“看起来没问题”的规则可以绕过用户审查进入最终产品基线。**
