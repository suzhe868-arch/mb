# 3. Batch 1｜稳定一致项｜重新展开版

> 本批只审没有被后续规则推翻的图片基础生命周期。与后续转换模型、分享图、4:3 等新增/改写内容分开处理。

### P08-A01｜首次图片集合冻结

批发车第一次入库时读取当次 `images[]`，保存图片身份、首次 `upstream_url` 和原始顺序，形成冻结快照。

后续普通 JYT 同步：
- 不因为上游后来新增图片而补入；
- 不因为上游删图而从本地集合删除；
- 不因为上游换排序而改本地原始排序；
- 单张冻结 URL 后续失效，只处理该图片自身失败 / 恢复；
- **不得因为单张 URL 失效重新同步整车图片集合。**

状态：`USER_REVIEW_PENDING`

### P08-A02｜采集批发车首图 CDN 自然缓存 / fallback / 占位图

批发车首次入库时只冻结图片来源、URL 与原始顺序，不要求主动调用 CDN 厂商预热，也不要求采集阶段先把首图永久落入名邦对象存储。

列表 / 首页首次真正请求车辆首图时：

1. 客户端只请求名邦受控 CDN 地址；
2. CDN 命中缓存则直接返回；
3. CDN 未命中时，CDN 在**同一次请求**中实时回源 JYT，拿到图片后直接返回给当前客户，并同时形成 CDN 缓存；
4. 原排序第一张回源失败时，按原始顺序继续寻找下一张可用图作为当前列表封面；
5. fallback 只改变当前展示封面，不改变数据库原始排序；
6. 原第一张以后恢复可用时，仍可按原始排序恢复为首图；
7. 上游 0 图或全部图片不可用，不阻止车辆入库、匹配、销售 / 在售；
8. 没有可用真实图时使用统一默认占位图。

> CDN 厂商“URL 预热 API / 每日预热额度”不进入本产品规则；图片正常可见性不得依赖主动预热。

状态：`USER_CONFIRMED`

### P08-A03｜名邦受控图片地址与可配置域名

批发 / 报告静态图片的业务数据只保存图片 path，不把前端公开域名或上游回源域名写死进数据库。

具体：
- 客户端、员工端不得直接使用上游图片域名；
- 对外图片地址由“名邦可控公开图片域名 + 配置前缀 + 图片 path”生成；
- CDN 未命中缓存时，再根据配置的上游图片源站域名 + 同一 path 回源；
- 当前标准上游图片源站配置使用 `img.jytche.com`；
- 名邦公开域名、路径前缀、JYT 图片源站域名均作为配置项，可后续替换；
- 完整 H5 / 报告页面不套用普通图片 path 规则。

状态：`USER_APPROVED`

### P08-A04｜其余批发图片按需本地化，viewer 与持久化复用同一次回源

封面以外的批发图默认只保留冻结来源信息，不在首次入库时全量下载。

图片进入真实查看 / 预加载窗口时：
- 才触发回源与服务端本地化；
- 第一次回源成功的**同一份图片数据**同时用于当前 viewer 展示和服务端持久化；
- 不要求客户先等待“服务器保存完成”，再重新发起第二次图片请求。

状态：`USER_REVIEW_PENDING`

### P08-A05｜详情页两阶段 CDN 预取

当前规则保留“两阶段预取”，但不依赖 CDN 厂商主动预热 API。

#### 第一阶段：进入详情，优先保障前 5 张

- 列表首图已经通过正常 CDN 请求获得；有缓存则直接返回，无缓存则 CDN 实时回源并在同一次请求中返回、缓存；
- 客户进入车辆详情后，除当前首图外，立即主动请求后续 **4 张**；
- 因此详情页优先准备的目标是：**前 5 张图片连续可看**；
- 这 4 张可以并行请求 CDN，不要求逐张等待前一张完成。

#### 第二阶段：浏览到第 3 张时，开始获取剩余图片

当客户实际浏览到 **第 3 张图片** 时，视为存在继续看图的明确意图：

- 将该车剩余尚未请求的图片全部加入 CDN 预取队列；
- “全部加入队列”不等于瞬间无限并发回源；
- 实际请求仍可分批并行，由 Engineering 根据终端网络、图片大小、CDN 状态等控制；
- CDN 已有缓存的图片直接命中；
- CDN 未缓存的图片由 CDN 实时回源 JYT，并在对应请求中返回给客户端，同时形成缓存。

这样可以避免客户只进详情看一眼时就为整车几十张图片产生无意义回源流量，同时又能保证真正继续浏览的客户后续看图尽量连续。

状态：`USER_CONFIRMED`

### P08-A06｜什么才算“已本地化”以及失败事务边界

图片只有同时满足：

1. 名邦对象存储保存成功；
2. DB 成功写入有效本地对象标识；

才视为真正“已本地化”。

异常处理：
- 对象存储成功、DB 最终失败 → 删除刚保存的新对象，避免孤儿文件；
- viewer 已经成功看到上游图片，但随后服务端持久化失败 → **本次客户体验不回滚**；
- 这种情况下数据库仍将该图片视为“未本地化”，以后按正常规则再次处理。

状态：`USER_REVIEW_PENDING`

### P08-A07｜本地优先与受控自愈

已经成功本地化的图片：

- 正常访问永久优先使用名邦本地资产；
- 不再每次读取都重新检查 JYT 原图；
- 冻结 `upstream_url` 继续作为来源 / 极端恢复依据；
- **只有确认名邦本地对象损坏、丢失或 404 时**，才允许用冻结 URL 做受控自愈；
- 自愈单张图片不触发整车图片重新同步。

状态：`USER_REVIEW_PENDING`

### P08-A08｜单图失败、重试轮次与原排序恢复

普通批发图按需本地化：

- 单图单轮最多自动尝试 3 次，并采用必要退避；
- 本轮 3 次仍失败则停止本轮；
- 以后该图再次进入真实查看场景，可以开启新一轮尝试；
- 当前失败图暂不占详情可见图片位置；
- DB 图片来源记录和原始排序永久保留；
- 以后恢复成功后，按原始排序位置重新进入可见图集。

> 一键转名邦的“转存失败重试”还有 9/22 新规则，Batch 3 单独处理，不能与这里混为一个泛化 retry 状态。

状态：`USER_REVIEW_PENDING`

### P08-A09｜CDN 并行加载 / 重复回源控制

旧历史“同一图片 single-flight + 单车最多 3 张本地化任务”来自服务端主动吞图模型，不能原样套到当前 CDN 直链 / 缓存模型。

结合当前 CDN 架构，候选改为：

- **取消产品级“单车最多 3 张并发”硬限制**；
- 客户端到 CDN 使用 HTTPS，并优先启用 HTTP/2 等可用协议能力，让多个图片请求复用连接并并行传输；
- A05 首阶段可并行请求后续约 4 张图片；到第 3/4 张后，可把剩余图片整体加入预取队列；
- 剩余图片实际下载仍采用受控并发，不建议几十张同时瞬时回源；具体并发数由 Engineering 可配置，初始可按约 4～6 路验证后调整；
- “同一资源避免重复回源”保留为工程优化目标，而非产品业务状态：可通过本地预取任务去重、CDN Cache Key、厂商合并回源 / 缓存能力等实现；
- 不同图片是不同资源，允许并行回源；不能因为旧 single-flight 规则把整辆车限制成一次只取一张；
- 若 CDN 已命中缓存，则请求直接由 CDN 节点返回，不产生对应 JYT 回源。

状态：`REVISED_PENDING_USER_REVIEW`

### P08-A10｜上下架 / listing_cycle 不重置图片资产

车辆 visible/hidden、真实下架、售出等销售状态变化：
- 不重置已经形成的图片资产状态；
- 已本地化图片继续保留；
- 未本地化图继续保留冻结 URL；
- 下架期间不主动继续批量本地化；
- 重新上架复用已有本地图，未完成图片仍继续原按需逻辑；
- 图片增删、本地化、自愈本身不创建新的 `listing_cycle`。

状态：`USER_REVIEW_PENDING`

### P08-A11｜人工名邦 / 4S 图片生命周期

人工名邦 / 4S：
- 允许 0 张真实图片正式发布；
- 0 图使用统一占位，不因此下架；
- 人工上传成功后即属于名邦服务端正式本地图，不存在“未本地化”状态；
- 正式发布后可继续补图、删图、拖动排序；
- 删除首图后，剩余排序第一张成为新首图；
- 删除到 0 图仍可继续在售。

批发采集图的原始排序：
- 普通人工不得直接拖动 / 改写。

状态：`USER_REVIEW_PENDING`

### P08-A12｜不设置产品级固定图片限额

产品业务层不硬编码：
- 最多几张；
- 固定单图大小；
- 固定业务格式清单。

仍保留必要技术安全校验，例如：
- 必须是真实可处理图片内容；
- 防危险内容；
- 防明显资源滥用；
- 平台 / 对象存储实际技术限制。

这些技术限制不能反向演变成未经产品确认的“业务最多 N 张图”。

状态：`USER_REVIEW_PENDING`

### P08-A13｜图片权限继承 Vehicle，不允许 URL 绕权

图片 Read 不是独立越权通道。

要求：
- 图片是否可读，继承当前 Vehicle Read / Visibility；
- hidden / Priority / Recommendation 等场景不能靠拿到历史图片 URL 绕过车辆权限；
- 当前无权读取 Vehicle 时，旧图片地址不能成为永久访问权；
- 客户端只获得名邦受控地址，不获得 JYT 原始 URL / 内部对象地址；
- 具体 URL 签名 / Token 机制属于 Engineering。

# 8. 2026-10-03 CDN URL 生成补充裁决

### P08-CDN-01｜图片路径与域名配置

用户确认：采集到的图片原始数据本身不包含固定域名，核心事实是图片路径。

因此普通图片类资源统一采用：

- 数据库只保存图片 path，例如：
  `/user/370436/report/image/1788072135101_1352.jpeg`
- 不在业务数据中写死名邦前端图片域名；
- 不在业务数据中写死 JYT 图片回源域名；
- 前端公开图片地址由“名邦可控公开图片域名 + 固定前缀 + 图片 path”运行时生成；
- CDN 回源地址由“配置的上游图片源站域名 + 图片 path”运行时生成。

示意：

```text
DB:
  /user/xxx/xxx.jpg

Frontend public URL:
  {PUBLIC_IMAGE_DOMAIN}/{PREFIX}/user/xxx/xxx.jpg

CDN origin:
  {JYT_IMAGE_ORIGIN}/user/xxx/xxx.jpg
```

当前示例可表现为：

```text
前端：
https://img.mingbang.com/ct/user/xxx/xxx.jpg

CDN 回源：
https://img.jytche.com/user/xxx/xxx.jpg
```

但 `img.mingbang.com`、`/ct/`、`img.jytche.com` 均属于可配置项，不冻结为数据库永久字段。

适用范围：
- 车辆相册图片；
- 出险记录图片；
- 4S 维保报告内静态图片；
- 其他报告静态图片；
- 后续同类采集图片附件。

例外：
- 完整报告 / H5 链接（如 `app.yutangkeji.com/#/detail/...`）不套用普通图片 path 规则，继续按完整报告 URL / report proxy 规则处理。

状态：`USER_APPROVED`

### P08-CDN-04｜4S 维保的 H5 与图片是两种独立呈现方式

用户纠正确认：

4S 维保记录可能以两种不同方式呈现：

1. **H5 报告方式**
   - 上游直接提供一个完整 H5 URL；
   - 例如 `https://app.yutangkeji.com/#/detail/...`；
   - 该完整 URL（含上游域名）作为原始报告链接写入数据库；
   - 客户端不能直接显示上游域名；
   - 对客户端输出时，将上游 H5 域名替换 / 映射为名邦可控的前置报告域名，后续 path / hash 等报告定位部分保持对应关系；
   - 名邦前置报告域名应配置化，不写死业务数据。

2. **图片方式**
   - 如果该维保记录返回的是图片，则它就是普通采集图片资源；
   - 与 H5 没有上下级或页面内资源关系；
   - 继续走既有 IMG / JYT 图片链路：数据库保存图片 path，客户端使用名邦图片公开域名，CDN 回源标准图片源站。

因此：
- **H5 是一种报告呈现方式；图片是另一种报告呈现方式；两者彼此独立。**
- 不再要求因为存在 H5 就去解析 / 改写其内部图片作为产品规则。
- H5 与普通图片分别走各自 URL 规则。

状态：`USER_APPROVED_CORRECTED`

# 12. PDM-08 新 Batch 1｜2026-10-03 CDN 重构后的稳定候选

### P08-RB-A01｜批发/上游图片只保存 path，前端域名与回源域名配置化

- 上游采集图片业务事实只保存图片 path 和必要来源身份/顺序；
- 客户端只获得名邦可控图片地址；
- 名邦公开图片域名、逻辑前缀、JYT 回源源站均可配置；
- CDN 根据 path 回源标准图片源站；
- 当前标准图片回源源站使用 `img.jytche.com`，但不写死进业务数据。

状态：`USER_REVIEW_PENDING`

### P08-RB-A02｜普通批发图片默认 CDN 缓存，不因浏览永久资产化

- 普通批发图未转名邦前，不因为列表/详情浏览而逐张永久写入名邦对象存储；
- CDN 缓存属于访问加速，不等于名邦取得长期图片资产；
- TTL、预取、并发、重试等性能参数归 Engineering。

状态：`USER_REVIEW_PENDING`

### P08-RB-A03｜首次图片集合与排序继续冻结

- 首次入库保存当次图片 path 集合与原始顺序；
- 后续普通同步不因上游增图/删图/排序变化重写整套集合；
- 第一张不可用时可按原顺序向后 fallback；
- fallback 不修改原始排序；
- 0图/全失败不阻塞车辆，使用占位图。

状态：`USER_REVIEW_PENDING`

### P08-RB-A04｜名邦 / 4S 自上传车辆图片直接进入对象存储

- 名邦车辆和 4S 车辆的人工上传图片直接进入名邦对象存储；
- 通过名邦 CDN 对外读取；
- 允许 0 图正式发布；
- 发布后可补图、删图、排序；
- 删除到 0 图不影响车辆继续在售。

当前逻辑命名：`vc`；实际前缀配置化。

状态：`USER_REVIEW_PENDING`

### P08-RB-A05｜出险 / 维保 / 档案图片与 H5 分型

- 出险记录当前按图片方式处理；
- 4S 维保记录可能是图片，也可能是完整 H5，两种呈现方式平行独立；
- 采集得到的报告图片继续走采集图片 CDN 链路；
- 名邦 / 4S 自上传报告/档案图片直接进入对象存储，可使用 `rc` 逻辑命名；
- 4S 维保 H5 保存完整原始 URL，客户端输出时映射成名邦可控 report 前置域名；
- H5 与图片不建立父子关系。

状态：`USER_REVIEW_PENDING`

### P08-RB-A06｜报告/档案存储链路不改变 PDM-07 可见性

- 使用 CDN / 对象存储只决定资源如何获取，不决定客户是否可见；
- 出险、维保、检测等报告图片不因为使用图片 CDN 就自动进入车辆相册；
- 敏感原件继续固定内部；
- 可对客报告/结果继续按 PDM-07 的“客户可见 / 仅内部”控制；
- 普通车辆轮播与档案/报告展示继续分离。

状态：`USER_REVIEW_PENDING`

### P08-RB-A07｜批发 → 名邦时图片正式资产化

- 一键转换只有批发→名邦，没有批发→4S；
- 车辆继续使用同一个 `vehicle_id`；
- 转换时将原 JYT/批发图片按 path 正式保存到名邦对象存储；
- 已成功资产化图片不重复处理；
- 转换后进入普通名邦图片生命周期；
- JYT 图片来源/path 历史继续保留用于 provenance。

状态：`USER_REVIEW_PENDING`

### P08-RB-A08｜车辆转换与图片资产化状态解耦

- source_type 转名邦成功后，不因个别/全部图片资产化失败回滚车辆转换；
- 图片子任务独立记录 `processing / success / partial_failed / failed`；
- 失败支持后续重试/恢复；
- 图片任务状态不得冒充车辆转换状态。

状态：`USER_REVIEW_PENDING`

- 转名邦资产化后，底层可切换到名邦对象存储；
