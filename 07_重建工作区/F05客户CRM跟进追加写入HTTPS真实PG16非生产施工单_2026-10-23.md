## 二、权限、真实数据源与可实施边界

- 服务入口须显式 CI-only 初始化；独立真实 PostgreSQL 16 非超级用户数据库，`CI=true`、`NODE_ENV=APP_ENV=test`、`GITHUB_REF` 与最终 SHA/Run ID 锁定、数据库为本机专用隔离库；无相应环境证明拒绝构造服务。
- 必须经现有 `IsolatedAuth.withSession` 进行合法 active 员工 PC 会话 + 当前 credential + force-password-change、员工/role 当前权限及个人 deny 优先检查；System Admin 控制面不能写名邦 CRM、4S hard DENY。只接受名邦销售/经理/店长；角色名称只按实际冻结表，未知角色拒绝。
- **必须有独立 CRM 写入 capability**，不能将静态 `crm.customer.view` 或历史 owner 当写权限。PDM-16 仅冻结“独立合法写能力”，未冻结具体生产 permission code：可在本次可销毁测试库以 `crm.followup.create` **合成 CI-only 技术别名**验证角色默认/员工个人 allow/deny/精确 Customer object Scope；绝不可写入生产种子、把测试权限冒充正式 source/Issuer 或为历史人员开放全局权限。若正式物理权限事实无法建立，应明确 `CI_ONLY_SYNTHETIC_PERMISSION / PRODUCTION_NOT_CONNECTED_SOURCE_GAP`。
- 在 session 后以一致稳定锁序获取 current Customer 行与当前 owner/permission scope/binding（含 granted_at/ended_at）及可选 Demand 行；合法 current owner 且有权限、或明确具备当前有效 Collaboration/manager scope 且有独立写权才可新增。owner 未分配/无合法受管责任人时不能发明一个 responsible；旧 owner 移交后失去无独立范围的写权。已停用 Customer 不允许继续执行新普通 CRM Follow-up，历史保留。
- Follow-up 责任人取合法、当前有效的 Customer 业务承接责任事实；不得伪装成 System Admin，也不得因为本次记录改变 Customer owner 或 Demand responsible。可选 `business_demand_id` 必须同属 Customer；不能跨客户引用/替换 owner/引入不存在 Demand。内容限长、非空、Unicode 输入规范；拒绝 HTML/SQL 注入不能以拼接 SQL 写入。必要的来源 context JSON 严格白名单，禁止原样记入 Cookie、手机号、权限 token 或客户敏感资料。
- `public.crm_followups` 只能 INSERT，不能 UPDATE/DELETE；更正/作废采用新增一条指向原合法 followup_id 的 append-only 纠正事实，并按安全协议记录 correction 类型，旧内容/作者/时间永久保留。若当前冻结结构不支持可验证的关联，请限制为新增普通 Follow-up、并明确更正尚 `NOT_CONNECTED`；不可偷偷加新列或公共迁移。
- 幂等采用服务端规范化 RequestKey+payload 摘要、真实业务键稳定 advisory 锁与既有 `public.audit_events` 可核事实，无新 public DDL。重复同键同 payload 返回同一已写记录，不重复写；同键不同 payload 或不同客户/操作者必须冲突；写入和审计同一 PG16 事务，失败回滚。历史 Follow-up 不计入 Consultation SLA，也不触发 Demand/Recommendation/Lock/Transaction 状态变更。
- 正式 HTTPS 仅 localhost TLS 明确注入 `/__ci__/f05/crm-followups/` 路由，拒绝生产、非本地、跨源、转发和重复敏感 Header、无效 Cookie/CSRF/Content-Type、非白名单 JSON、超长 body、奇异 path、查询串、恶意 id、错误泄漏；生产 `server.mjs` **绝不注册**本服务。
