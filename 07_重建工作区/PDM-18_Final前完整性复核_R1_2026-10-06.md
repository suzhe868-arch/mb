## 3. Final 前修复候选

### P18-LIA-01｜Waitlist 仍属于手机号人工服务门槛

历史 SSOT 明确：

> 登记候补属于手机号人工服务门槛。

建议补齐：

- 客户主动创建 Waitlist 前必须存在当前可用手机号；
- 无手机号时按 PDM-01 统一手机号授权流程处理；
- 授权成功自动继续原候补动作，不要求客户再次点击；
- 取消 / 拒绝授权不创建新的 Waitlist；
- P18-B4-02 的自动 Waitlist 来源于已经合法创建的 LockRequest，正常情况下复用该 Customer 已满足的人工服务身份/联系方式 Guard；创建时仍要重验 Customer/account/phone 当前可用性。

### P18-LIA-02｜客户 V1 不自助取消 Waitlist

历史 SSOT 明确：

> 客户 V1 不自助取消 Waitlist。

建议补齐：

- 客户端不提供“取消候补”业务 mutation；
- 客户只查看当前/历史候补及必要状态；
- Waitlist 可由合法 responsible / 授权管理人员人工结束，或按 Vehicle/cycle 终态自动结束；
- 人工结束继续遵守 B4-06 的 permission + scope + reason + audit；
- 该规则不影响客户以后重新表达新的购车意图，但不得直接复活已 ended Waitlist。

### P18-LIA-03｜LockRequest 正式结果集与审计 / 关联结果

当前规则已使用 PENDING、approve、reject、expired、LOCK_CONFLICT 等语义，但 Final 尚未形成统一结果合同。

建议冻结：

- `PENDING` 是唯一 live 申请态；
- 合法结束结果至少包括：
  - `APPROVED`：正式 Lock 原子创建成功，必须关联 `resulting_lock_id`；
  - `REJECTED`：合法员工明确拒绝；
  - `EXPIRED`：超过 6 小时服务端有效期；
  - `LOCK_CONFLICT`：其他请求先成功形成 active Lock；
  - `CLOSED_NOT_LOCKABLE`：提交重验时因 Vehicle/listing_cycle/当前可锁性等非竞争原因已经不可锁。
- 采用 B4-02 后，`LOCK_CONFLICT` 可同时关联 `resulting_waitlist_id` 或复用的 active Waitlist；这不改变 LockRequest 本体终态；
- 终态不重新变回 PENDING；需要新申请时创建新的合法 LockRequest；
- 创建 / approve / reject / timeout / conflict / closed-not-lockable 至少记录 request、Customer、Vehicle/cycle、actor/system、time、before/after、reason/result，以及 resulting_lock_id / resulting_waitlist_id（适用时）。

这里定义的是业务结果合同，不强制工程必须使用单一 master enum；具体 Schema / event carrier 交 PDM-25。

### P18-LIA-04｜正式 Lock 创建必须幂等 / retry-safe

历史 Current 明确保留“Lock 创建幂等”，当前 Batch 规则主要冻结了唯一性与并发，但还缺显式 retry 合同。

建议补齐：

- LockRequest approve 原子事务重试不得产生第二个 Lock；
- 员工直接正式 Lock 的同一合法业务提交重试不得产生第二个 Lock；
- 网络超时 / 客户端重复提交 / worker retry 不得把一次业务意图放大成多笔 active Lock；
- 已成功结果重试应返回/识别已有业务结果，而不是再创建；
- 幂等实现键、数据库唯一约束和并发测试由 PDM-25 / Engineering 承接，但业务 invariant 必须在 PDM-18 Final 明确。

### P18-LIA-05｜Waitlist 有处理顺序，但客户端不展示保证性“第几名”

B4-02 已明确：

> 自动转 Waitlist 的多个客户按原 LockRequest.created_at 保留候补顺序。

但历史客户端又明确“不显示第几名”，因为 Waitlist 不自动晋升 Lock。

建议统一为：

- Waitlist 可以存在确定性内部处理顺序；
- 顺序只用于员工后续联系 / 人工重新确认的稳定处理次序；
- **不表示客户拥有自动获得下一笔 Lock 的法律/业务承诺**；
- V1 客户端不展示“第1名 / 第2名”这类保证性排名；
- 可展示“候补中 / 等待顾问确认”等中性状态；
- 即使排在前面，正式 Lock 仍必须重新通过当时最新 Guard；
- 若以后要向客户展示排名，必须作为新的产品裁决，不由工程自行推导。
