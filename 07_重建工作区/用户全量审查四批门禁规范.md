# 名邦汽车 V1｜用户全量审查四批门禁规范

> 状态：`ACTIVE / HARD_GATE`  
> 日期：2026-09-23  
> 适用范围：PDM-01～PDM-25 全部产品域。

## 1. 唯一原则

任何规则原子都必须经过用户本人审查。

模型判断为“稳定一致”不等于用户已确认；`FROZEN` 不等于当前最终采用；“明确废弃”也必须由用户过目确认。

所有未审规则统一：

`USER_REVIEW_PENDING`

## 2. 每个 PDM 的四批审查

| 批次 | 内容 | 是否必须用户审查 |
|---|---|---|
| Batch 1 | 稳定一致、建议直接保留 | 是 |
| Batch 2 | 明确废弃、明确替代、DO_NOT_RESTORE | 是 |
| Batch 3 | 明确知情修改、后续明确新增 | 是 |
| Batch 4 | 冲突、历史遗漏、证据不足、新业务选择 | 是 |

## 2.1 Batch 2 / Batch 3 入批前反向冲突硬门禁

任何规则原子进入 Batch 2 或 Batch 3 前，必须完成以下四层反查：

1. 前史 / 9/19 是否存在相反正式规则；
2. 后续所谓“废弃 / 修改”是否有明确用户裁决或可证明的知情修改过程；
3. Current / IA / Low-Fi 是否存在与该结论相反的后续承载；
4. 001～078 是否已将该点标记为冲突、反向复活、历史规则丢失或未收口。

并必须再检查：

5. 是否与前序已批准 PDM / Decision Register 形成跨域冲突。

只要任一项存在未解释的真实反向证据：

> **不得进入 Batch 2 / Batch 3 作为确定项，强制转入 Batch 4。**

禁止仅凭：

- 文件日期更晚；
- 标记为 CURRENT / FROZEN；
- 后期总结写“废弃 / 已替代”；
- IA / Low-Fi 已经这样画；

就判定旧规则已经合法失效。

如果某规则已经在早一批次被用户确认，但后续全局复核发现其分类建立在遗漏证据之上：

> **必须回开该原子，保留原确认审计，再登记 reopen / supersession，并重新进入冲突裁决。**

该门禁与《产品基线重建执行规范》Step 5A 保持一致。

## 2.2 信息保真与一次性收口执行门禁

本节把《产品基线重建执行规范》3.2 的 14 项方法规则转成四批审查的强制执行检查。

### 2.2.1 进入 Batch 1 前必须有

- 当前权威刷新结果；
- Completed-PDM Dependency Card；
- Global Invariant Scan；
- Terminology / Field Normalization；
- 指向本域的 Deferred Handoff 清单；
- 当前实现事实卡（如本域已有实现）。

缺任一项：

> **不得开始 Batch 1。**

### 2.2.2 每条 Atom 入批前必须有

- 当前 Authority 对照；
- 前史 / 9·19 / 后续证据；
- 已完成 PDM 约束；
- Current / IA / Low-Fi 反向承载检查；
- 001～078 风险检查；
- 冲突结论；
- Source → Atom 去向；
- 是否影响全局不变量；
- 是否存在跨域 handoff。

Batch 分类只能在上述检查完成后进行。

### 2.2.3 每次用户修改 / 反转 / reopen 后必须立即做

> **Change Impact Analysis**

至少列出：

- 被覆盖的 Atom / Decision；
- 受影响已完成 PDM；
- 受影响当前 PDM；
- 受影响 DO_NOT_RESTORE；
- 受影响 IA / Low-Fi / Engineering carrier；
- 需要更新的状态文件。

不允许只改当前一条文字。

### 2.2.4 每批结束前必须反向审计

每批提交用户前，再问一次：

1. 有没有违反已完成 PDM？
2. 有没有违反全局不变量？
3. 有没有把条件 / permission / scope / hard DENY 压缩丢失？
4. 有没有 Deferred 但没有明确目标 PDM？
5. 有没有“没搜到 = 不存在”的否定性结论？
6. 有没有引用摘要而没有回原始证据？

任一为“有”：

> **本批不得提交用户作为完整候选。**

### 2.2.5 Final 前必须通过语义完整性矩阵

Final 不能只检查“每个 Decision 有没有去向”。

必须逐章节检查：

- 对象 / 标识；
- 角色；
- 前置条件；
- permission；
- data scope；
- hard DENY；
- 正常流程；
- lifecycle；
- listing cycle / 时间边界；
- 空值；
- 失败 / timeout；
- 并发 / 幂等；
- revoke / inactive；
- 配置生效；
- history / audit；
- immutable snapshot；
- 跨对象影响；
- 三端必要表现；
- DO_NOT_RESTORE；
- 跨 PDM 依赖。

不适用可以写 N/A，但不得静默遗漏。

### 2.2.6 COMPLETE 的新硬条件

以后任何 PDM 要标记 COMPLETE，必须同时满足：

```text
SOURCE_DECISION_COVERAGE = 100%
UNMAPPED = 0
FINAL_TO_SOURCE_TRACEABILITY = 100%
DEFERRED_HANDOFF_UNRESOLVED = 0
CROSS_PDM_CONFLICT = 0
GLOBAL_INVARIANT_CONFLICT = 0
SEMANTIC_INTEGRITY = PASS
NEGATIVE_CLAIMS_VERIFIED = PASS
USER_FINAL_APPROVED = YES
IMPLEMENTATION_READY = PASS
```

缺任一项，不得 COMPLETE。

> **“已审过四批”不再等于“已经完整”；“UNMAPPED=0”也不再等于“语义没有丢”。**

## 3. 每批输出格式

每个规则原子至少展示：

1. Atom ID；
2. **拟进入最终基线的完整规则文字**；
3. 证据结论（简短）；
4. 模型分类；
5. 模型建议；
6. 用户审查状态。

用户可回复：

- 本批全部通过；
- 第 X 条修改为……；
- 第 X 条不同意；
- 第 X 条暂缓。

## 4. 硬停止

每批展示完必须停止等待用户。

未经用户确认，不得：

- 自动进入下一批；
- 生成该域最终规则；
- 标记 COMPLETE；
- 进入下一个 PDM。

## 5. 四批之后还有一次最终总览

四批全部通过后，生成该 PDM 完整、自包含的最终规则草案，再由用户整体复核一次。

只有最终总览也通过，才能：

> Decision Register → 正式中文基线 → 状态 COMPLETE → commit → 下一 PDM

## 6. 证据规则

任何审查项都必须能回到原始仓库证据。

禁止用前一轮摘要替代原始证据继续推导。

固定链路：

> 原始证据 → 规则原子 → 四批用户审查 → PDM最终总览 → 最终基线

## 7. 已确认规则的后续继承门禁

用户在前序批次、前序规则原子或前序 PDM 中已经明确确认的规则，必须作为后续审查的当前有效约束持续继承。

固定要求：

- 后续筛选到交叉规则时，必须主动对照前面已确认规则；
- 一致时标记继承，不重新制造冲突；
- 冲突时必须显式展示冲突并重新交用户裁决；
- 未经用户再次确认，不得用更晚版本、FROZEN、IA、Low-Fi 或工程实现静默覆盖；
- 同一 PDM 前一批已确认规则，立即约束后一批；
- PDM 最终总览通过后，该 PDM 正式规则成为后续 PDM 的上游产品约束；
- 如需改动已确认规则，必须记录替代关系并更新 Decision Register；
- 跨窗口继承以 GitHub 当前文件与 Decision Register 为准，不以聊天记忆代替。

> **已确认规则必须持续继承；后续若冲突，只能显式重审，不能失忆、重置或静默覆盖。**
