## 1. 技术裁定：可信eligible与全池共同事务锁

- **只追加新的第5版迁移`000005`**；禁止改写旧`000001～000004`、任一旧manifest、冻结旧服务或旧CI证据。建议新增两张最小表：
  - `employee_receiving_eligibility(employee_id BIGINT PRIMARY KEY REFERENCES employees, eligible BOOLEAN NOT NULL, version BIGINT NOT NULL, decided_at TIMESTAMPTZ NOT NULL, decided_by_system_admin_id BIGINT NOT NULL REFERENCES system_admins)`；只允许当前有且可证、由可信独立System Admin在本CI内部设置的资格事实；缺行、失效、不明映射即**fail-closed**，无默认授资格，不因为`employees.receiving_status`而自动推断。
  - `receiving_pool_guards(guard_name TEXT PRIMARY KEY CHECK(guard_name='receiving_pool'), version BIGINT NOT NULL CHECK(version>=0))`，安装时精确1行。独立于000004的`governance_population_guards`（其CHECK只允许`system_admin`），**不得擅改管理员单例约束/复用它假装接客锁**。
- 两表只是经过A批准的**工程结构候选**。B从实际冻结结构推导迁移DDL及正确FK/约束/物理指纹，真实CI结构发现后明确计算新表列数/约束/索引；预期84表但不得预设未知列数为已验收。采用独立manifest/append-only版本和严格确切PG16 Guard：拒绝80/81/82版本及未批准额外schema；新旧不同版本各用**相互独立**一次性PG16测试库验收。
- System Admin设置**指定单个既存员工**eligibility(true/false)，只能在当前可信正常active且有效凭证的独立F03-1 System Admin会话中进行，需检查目标Employee active、合法主角色为`sales/manager/store_head`之一、非4S且身份一致；对false降资格，正常操作若使合格接客池从1→0，必须同事务拒绝，不能只查旧快照。不向System Admin授Employee业务权或变更Employee本人的主角色/门店；销售/经理/店长不能借该接口自行改eligible。
- Employee本人开/关当前接客状态：仅当正常F03-1 Employee会话与target`employee_id`匹配，当前active、当前主角色确实属于普通销售/经理/店长、具有独立`eligible=true`，方可从停用恢复为接受，或从接受变为暂停。本人不需要额外经理授权；**任何正常OFF会使最后一名active+eligible+accepting归零时严格拒绝**，即使管理员授予其他permission也不能绕过。角色“manager/store_head”如果当前已批准物理role目录无记录，则仅在CI合成fixture作逻辑正反例，不对真实role自动补种子。
- **真实性必须落在同一PG事务**：复用F03-1已验证正常会话与账号→会话锁，统一获取`receiving_pool_guards WHERE guard_name='receiving_pool' FOR UPDATE`，后锁当前eligible/employee/role实体，所有影响池人数的本批入口遵循相同全池序列化点；提交前查询变更后的可信合格池人数并同时验证operator/target仍合法，再更改`employee_receiving_eligibility`或`employees.receiving_status`，追加脱敏`audit_events`及guard.version递增，只有实际变更才追加成功审计；失败回滚全部（不留下半状态或半审计），重复同值NO_OP。整个本批不使用一个客户端传入的`eligible`、`poolCount`、`actor`或`lastPerson=false`标志作为权威。
- 若初始测试库完全没有合格接客者，**只允许经可信admin先使合法员工eligible，再由该员工本人ON从0→1恢复接客池**；不得因此允许正常OFF从1→0。恢复0→1属于安全修复，不等于真的已实现历史`owner_assignment_pending`清算。
- **异常池空与正常关闭严格分开**：合法员工突发inactive或资格事实不可用造成0人，不允许为了保留人数延长旧接客资格或让System Admin兜底成为owner。本批只验证安全读取/报告异常并保留`owner_assignment_pending`后续域适配要求；突发失效触发的真实客户分配/告警/自动补分由F04/F05及SG06相应正式授权批负责，不许借SG03内部模块直接修改Customer/业务责任。
- 经理/店长对下属开关接客状态仍依其**当前独立permission+data scope**，团队可信关系SG02未施工前不能从`store_id`代替team推权。本批**先完成本人操作与独立System Admin资格治理**；下属代理操作本批硬拒绝、列未完成项，不剥夺Final未来合法能力。
