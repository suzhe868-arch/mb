## 二、唯一允许的业务范围

只实现“其他联系电话事实”的真实非生产 CRUD（新增、替换、失效）和 HTTP 合同：

1. **新增**：为一个当前可管理的 Customer 增加一条新的其他联系电话事实。
2. **替换**：按 `phone_fact_id + customer_id` 定位仍有效的旧事实，将旧事实的 `ended_at` 置为当前事务时间，再插入新事实。
3. **失效**：仅将对应有效事实的 `ended_at` 置为当前事务时间。
4. **读取**：只返回当前有效其他联系电话的 `phone_fact_id`、时间和掩码号码；不得返回明文或 ciphertext。
5. 不提供主要手机号变更、客户合并、Owner 转移、微信身份绑定、客户账号停用/恢复或其他业务域写入。

不得物理 DELETE `customer_phone_facts`，不得原地覆盖历史号码的 `phone_ciphertext`，不得修改 `customer_id`、`valid_from`、客户 Owner 或其他业务事实。所有变更都必须保留可追溯的有效期历史。

## 三、权限与对象范围（不可扩大）

- 只使用现有 F03 身份/会话、`customer.phone.manage` capability、现有角色默认值和个人 override；个人 `deny` 优先于 role default/allow。
- 仅接受 active 名邦员工正式角色 `sales`、`manager`、`store_manager`；4S 员工与 System Admin 对该员工业务能力一律硬拒绝。
- 客户必须存在且当前 `account_status='active'`。
- 本纵切仅允许当前、未结束且已生效的显式 `scope_kind='object'`，且 `scope_reference_id=customer_id`；对应 `employee_capability_scope_bindings` 必须绑定到 `customer.phone.manage`。
- Store/team/owner/global scope、本地别名 `store_head`、其他权限 alias 均拒绝；不得自行推导或扩大。
- 现有 `F03_2_1B_ACCEPTED=NO` / `F03_2_ACCEPTED=NO` 不得由 B 修改为 YES。A 将在最终 SHA 上独立验收本纵切及其所依赖的范围 Guard；本任务不授予生产权限。

## 四、事务与并发要求

Guard、Customer 当前状态检查、电话事实写入与审计必须在**同一个 PG16 事务**内完成。禁止先调用独立的只读 Guard，返回允许后再另开事务写入。

- 先锁当前员工与目标 Customer，再以稳定顺序锁定权限/个人 override、data scope、capability-scope binding 和目标电话事实；锁顺序需与现有 F03 生命周期/撤权流程兼容。
- 在事务内重新确认会话主体 active、凭据 enabled、无强制改密、角色仍合格、Customer 仍 active、权限决定仍 allow、Scope/Binding 仍生效且 `granted_at <= transaction_timestamp()`。
- 并发撤权/结束 Scope：若撤权先取得相关锁并提交，本次写入必须拒绝；若写入先取得锁，则写入与审计先原子提交，随后撤权生效。必须以双 PG16 session 测试证明，不得只靠单线程 mock。
- 对同一 Customer 的 mutation 需要事务级序列化，避免重复 active phone fact；重复活动号码必须明确拒绝，不能依赖不存在的公共唯一索引。
- 必须支持 Idempotency-Key：同 key + 同请求返回同一结果；同 key + 不同请求返回 409；并发重放只能产生一组业务事实和审计。
- 任意审计插入失败、数据库错误或测试故障点均必须回滚电话事实变化，不能留下无审计变更。

## 五、号码保护与审计

- 使用 Node 标准库 AES-256-GCM；密钥只能由测试 harness 运行时注入/生成，长度必须为 32 bytes。禁止硬编码、提交、记录或复用生产密钥。
- 将版本标记、随机 12-byte nonce、16-byte authentication tag 与 ciphertext 以版本化二进制 envelope 存入既有 `phone_ciphertext bytea`；不增加公共列或索引。
- 输入必须严格校验并标准化；拒绝控制字符、过长输入、空值和非规范号码。不得把输入号码写入异常、日志、测试失败消息或审计 JSON。
- API 响应只返回掩码号码；审计 `before_json/after_json/role_context` 只记录 Customer ID、phone fact ID、掩码、有效状态、scope ID、操作、reason 和 Idempotency-Key 的 SHA-256；不写明文、ciphertext 或密钥。
- 使用既有 append-only `public.audit_events`；禁止 UPDATE/DELETE 审计。建议 action：`customer.phone.manage.add`、`customer.phone.manage.replace`、`customer.phone.manage.end`。
- 若需要幂等索引，优先用审计事件中的 `role_context.requestKeySha256` 并配合事务级 advisory lock；不得新增公共 Schema 或未经授权的私有 Schema，因为当前 runtime-scope Guard 对数据库结构有严格校验。

## 六、HTTP 与安全边界

只允许通过测试 harness 注入的 handler 暴露隔离路由，例如：

- `GET /__ci__/f03/customers/:customerId/other-phones`
- `POST /__ci__/f03/customers/:customerId/other-phones`（新增）
- `POST /__ci__/f03/customers/:customerId/other-phones/:phoneFactId/replace`
- `POST /__ci__/f03/customers/:customerId/other-phones/:phoneFactId/end`

路由可根据现有 HTTP 合同调整，但不得扩大能力。必须限制 `CI=true`、`GITHUB_ACTIONS=true`、`NODE_ENV=test`、`APP_ENV=test`、loopback bind 和显式 consent；非测试环境不得注册。拒绝伪造主体、未知字段、重复/歧义 Header、无效或重复 Cookie、非 loopback Host/Forwarded、超大请求体、错误 content-type、无效 ID、缺失/冲突幂等键。

**禁止修改** `engineering/src/server.mjs` 来注册生产路由；不做 PC/C/手机 UI，不接任何外部系统。

## 八、必测验收矩阵

1. 正常新增、读取掩码、替换（旧事实 ended + 新事实 inserted）、失效（逻辑结束）。
2. 数据库中不存在号码明文；响应、审计、日志、错误都不泄露明文/ciphertext/key。
3. 4S、System Admin、inactive employee、无会话、强制改密、凭据 disabled、未知角色全部拒绝。
4. role default allow、个人 allow、个人 deny、scope/binding 已结束、未到 granted_at、错误 Customer scope。
5. inactive Customer、无效 Customer ID、跨 Customer phoneFactId、已结束事实、重复 active 号码。
6. 同幂等键相同请求重放、同 key 不同 payload 冲突、双并发同 key 只产生一次变更。
7. 双 PG16 session 竞态：权限 deny、Scope 结束、Binding 结束与电话变更的锁顺序/原子结果。
8. 审计写入失败、插入新事实失败、旧事实结束失败均完整 rollback。
9. 当前只读 `checkCustomerPhoneScope` 原有行为回归；不得因新 mutation helper 使旧 Guard 放宽。
10. 真实 loopback HTTPS 合同测试、恶意 HTTP 输入/Host/Cookie/Forwarded/请求体负例。
