## 二、开工前避免重复建设：先核已验收实物，再定向施工

B 每接到 A 已放行的任务，先快速对照最新 `main`、本单规定的业务代码与接口、已合并 PR、A 正式验收、当前测试证据及来源签名，形成精简的四类差异清单：

| 分类 | 判定 | B 应做的事 |
|---|---|---|
| A. 已实现且 A 验收通过 | 具相符权威版本、实际代码及证据 | **直接复用，不重写、不再作为新开发任务** |
| B. 仅隔离 CI/Mock 通过 | 有可复用合同/测试，但未接正式业务来源或路由 | 复用现有实现和门禁，只补已授权的可信来源、适配或集成 |
| C. 已证实缺陷或来源不兼容 | 有可定位失败、签名不兼容或真实阻断 | **定向修复受影响的具体链路**，保留失败事实及旧历史 |
| D. 尚未实现或需额外授权 | 有缺口且代码/有效验收不存在，或需要生产/外部服务权限 | 仅在本单明确授权时施工；否则登记 `SOURCE_GAP`/`BLOCKED` 交 A |

- 禁止无证据断言“旧功能缺失”后直接复制旧模块、重建同一状态机或多套独立业务侧车。一个业务动作须明确现行可信实现或合法版本适配关系；不能伪造、改写冻结签名来源或迁移账本。
- 历史有效验收结论不撤销；同时**历史成功 SHA 不代表本次新代码在当前最终 SHA 通过**。
- 核对只做本单有关的目录、调用链和验收，不借机重新全面审计 F01～F05。

## 三、子任务增量自审与关联回归

B 日常开发只审：①本轮新增/修改的代码；②实际调用到的上下游接口、数据模型、签名和业务状态；③受变更影响的鉴权、数据范围、敏感投影、幂等、锁序、事务提交/回滚与失败补偿；④新测试及相关历史测试是否真实有效。

- **不得规定每完成一个子任务就从 F01～F08 全库重头代码审查。** 只有变更传播确实影响其他模块，才沿真实依赖扩大审查。

- CI（持续集成）以代码影响范围选取必测集合、可复用缓存/初始化与准确的触发路径；优化冗余工作流本身属于须经 A 授权的代码/工作流治理事项。**不删除或绕过 required checks，不跳过有效安全断言、不用假绿或历史绿灯冒充本 SHA 成功**。旧失败或 `queued`/`in_progress` 必须逐项说明适用性；不能凭方便就豁免。

## 七、每次提交前的 JavaScript 语法与基础质量强制门禁

**目的：在代码进入远程分支、触发官方 CI 之前，先消灭本地可发现的语法/格式错误。此项是强制执行流程，不表示本次治理变更已经安装 Git Hook 或新增 CI 工作流。**

1. **每一批代码修改完成后、每次 commit 前执行一次**；任何检查之后又改了代码，都必须重跑。先 stage 本次准备提交的文件，确认 staged diff 只包含本次预期修改，再执行基础检查。
2. JavaScript 的 `.js`、`.mjs`、`.cjs` 文件必须逐个通过当前 Node 版本的 `node --check`。不得只检查最后改的一个文件、只看编辑器无红线，或只依赖官方 CI 暴露语法错误。
3. 可在仓库根目录执行下列本地门禁（先确保 `origin/main` 已更新；如基准不同，设置 `BASE_REF` 为本任务实际授权基准）：

```bash
set -euo pipefail
BASE_REF="${BASE_REF:-origin/main}"

# 格式/空白错误：基线、已暂存、未暂存差异均检查
git diff --check "$BASE_REF"
git diff --cached --check
git diff --check

# 本分支相对基线、已暂存、未暂存的 JS 文件全部执行语法检查
{
  git diff --name-only --diff-filter=ACMR "$BASE_REF"...HEAD -- '*.js' '*.mjs' '*.cjs'
  git diff --cached --name-only --diff-filter=ACMR -- '*.js' '*.mjs' '*.cjs'
  git diff --name-only --diff-filter=ACMR -- '*.js' '*.mjs' '*.cjs'
} | sort -u | while IFS= read -r file; do
  [ -f "$file" ] || continue
  printf 'node --check %s\n' "$file"
  node --check "$file"
done
```

4. 其他文件按类型执行对应检查：TypeScript/TSX 使用仓库现有 typecheck/lint/build；Shell 脚本至少执行 `bash -n` 或对应解释器语法检查；GitHub Actions YAML 使用仓库可用的 `actionlint`/既有 workflow 校验；JSON 必须能被严格解析；SQL/迁移必须执行本施工单要求的真实 PG16 迁移及回滚验证，不能以文本语法检查代替数据库实测。
5. **任何语法、格式、类型、静态检查失败，都先在本地修复并重复检查，再 commit/push。** 若已经有一次错误提交触发 CI，不得把该 Run 当成最终通过证据；修复后只以新最终 SHA 的官方 CI 为准。禁止为了节省时间删除有效检查或把失败标为忽略。

## 八、每次提交及交 A 前的授权范围双门禁

1. **开工前建立授权矩阵**：从最新 `main` 读取 Issue、完整施工单、所有已合并且仍有效的 A 裁决/补充单；按“文件路径 / 授权来源 / 允许修改目的 / 禁止改变的语义 / 必测项”列出白名单和冻结清单。只读冻结目录不得通过文件名近似、旧分支已有改动、测试需要或 CI 方便等理由自动解冻。
2. **每次 commit 前核对真实差异**：执行 `git diff --name-status <授权基准>...HEAD`，同时检查暂存和未暂存差异；逐文件、逐关键 hunk 与授权矩阵核对。必须同时满足：
   - **路径授权**：文件属于当前有效施工单或 A 补充裁决明示的精确白名单；
   - **用途授权**：改动只实现该文件获准的具体目的，未借机改变冻结的业务规则、旧签名、旧 SQL、迁移、权限、状态机或兼容行为。
3. **白名单不是整文件自由修改权。** A 后续补充裁决仅覆盖其明确指出的冲突条款、文件和用途。例如 Issue #164 的 PR #166 补充裁决允许列出的 F06 既有文件为 `COMPOSITE_NONPROD_SIGNED_V1` 受控新入口/共用已验业务核心作最小适配；它不授权随意重写旧服务、不授权改变原资金/签名语义，未列文件及旧 SQL/公共 DDL/旧工作流仍冻结。新旧条款冲突时只按正式补充裁决的精确覆盖范围执行。
4. **一旦发现越界，立即停止该部分提交。** 在本地撤回或隔离未获授权的 hunk；若必须扩大范围，提交具体文件、函数、差异、原因、最小替代方案给 A 裁决。不能以“CI 绿”“测试通过”“先改了再说”豁免权限。当前分支已有的越界改动也必须先解决，不能把问题留给 A 在验收时发现。
5. **最终 `READY_FOR_A_REVIEW` 必须同时满足四项**：
   - 业务与本施工单强制测试通过，未运行项如实记录；
   - 本最终 SHA 对应的官方 CI 全部必需检查通过；
   - 修改路径和实际修改目的均符合授权矩阵，冻结文件/语义未被越界改变；
   - 中文交接中的文件清单、差异、测试命令、Run/Job、环境和通过/失败/未运行证据完整。
   
   任一项不满足，状态保持 `IN_PROGRESS` 或具体 `BLOCKED_*`，**不得**写 `READY_FOR_A_REVIEW`。A 对范围不合规的判定独立于测试结果。
6. **减少无效 CI，但不降低安全门槛**：本地基础门禁通过后再推送；一次集中修复本地可发现的问题。推送后 CI 若失败，先定位真实失败原因，修复并通过本地门禁，再推送新 SHA。不得在语法错误未修复时反复重启工作流，不得为了消除红灯删断言或重跑无关历史工作流。
