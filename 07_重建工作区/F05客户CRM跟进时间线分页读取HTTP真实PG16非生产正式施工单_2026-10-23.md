## 二、业务协议、读权限及竞态

1. 在本包原有**显式 CI-only** localhost TLS 私有 Handler 下增加 `GET /__ci__/f05/crm-followups/:customerId`；保持已有 `POST /:customerId` 和 `GET /:customerId/:followupId` 合同完整不变。允许列表 GET 的可选查询参数严格限定为 `limit` 和 `beforeFollowupId`，其它路径/方法/参数/重复 key/编码歧义、JSON Body、Cookie/Origin/Host/CSRF 和转发 Header 漏洞均按保守负例拒绝。非列表 GET、原 POST 仍严格拒绝查询串。
2. 缺省 `limit=20`，合法整数范围 1～50、不得前导零/浮点/符号/空值。游标 `beforeFollowupId` 只接受正 BIGINT 十进制字符串，最大 9223372036854775807；不接受 URL 二次解码、查询参数重复、伪造多字段 Cursor。新列表业务操作只读，不额外发业务事件、审计写、咨询首响、Demand/Transaction/Lock/Recommendation 动作。
3. 服务复用当前 `CrmFollowupService._withCustomer` 安全封装，在一个合法事务、客户行 `FOR UPDATE` 稳定锁和会话权限快照下完成列表查询；**Customer account_status 必须 active、owner_assignment_state 必须 assigned，旧 owner ID 非空不构成已分配证明**。员工 active、有当前对象级 Scope/有效 permission-binding、个人 deny 优先、当前 owner 或合法当前同店经理/店长、显式 CRM Collaboration；4S/System Admin/unknown role、force password change、旧 owner/离职/跨店/失效 Binding 均拒绝。反向竞态必须以实际 PG16 双连接确认，不能从已过期会话缓存沿用权限。
4. **读取采用 #239 既有更严格保守权限域**（CI-only 合成 `crm.followup.create` + Customer object Scope）。此实现不定义、不取代正式独立 CRM 查看权限 `crm.customer.view`，不因“列表是只读”放开任何写/读范围。任何未来扩大“可查看但不可写”须在合法正式 Reader Issuer 与 Authority 可签后另做独立授权。测试别名 `CI_ONLY_SYNTHETIC_PERMISSION` 永不是生产正向来源。
5. 查询强制 `WHERE customer_id=$1::bigint` 并按 `followup_id DESC` 稳定顺序；`beforeFollowupId` 为严格小于（exclusive），取 `limit + 1` 计算 `hasMore`，对外 `items.length<=limit`，只返回本 Customer 匹配的历史事实。下一游标为该页末条 `followup_id`；空页 `nextBeforeFollowupId=null`，不能传出任何其它 Customer 的记录/总记录计数。
6. 对每条投影只输出必要的 `followupId,customerId,actorEmployeeId,responsibleEmployeeId,occurredAt,content,businessDemandId` 与经**完全白名单**过滤的 `source.kind/reference`（仅允许沿用原 #239 `manual/call/visit` 与受限字符格式）。不能回传 raw `source_context_json`、角色权限、audit role_context、凭据、Cookie/CSRF、手机号/身份证、VIN、客户画像私有笔记或其它客户记录。历史上由更旧版本生成的非法 source 字段必须脱敏/忽略，不得原样对象展开。
7. 锁序、Idempotency Key / audit 写入路径均延续旧服务不变；列表只能 SELECT，不得暗中更新 `crm_followups`、`audit_events` 或 owner/Demand/Consultation。Customer 重新分配为合法新 owner 后，可在新 owner 的当前**独立权限和 Scope**均满足时查看公司旧 Follow-up；旧 owner 没有当前范围时不可继续看。若 Customer 未分配或 inactive，保持旧按 ID 读法的保守 fail-closed，不以“历史需要保留”绕过现时授权。
8. 关键序列化：并行旧新请求、历史读页间插入、新 owner 移交与访问并发、权限撤销与正在查询、客户停用与正在查询，必须用真实数据库两连接证明“提交以后没有越权新页”，已发出去的旧已授权响应不能追溯消除但不应保留服务器永续授权。分页新插入位于最前页，不破坏后续 `beforeFollowupId` 稳定去重与单客边界。
9. 真实 HTTP 边界必须仅显式 localhost TLS 且 CI 环境可构造，错误统一脱敏不暴露 SQL、账号、表名、JWT/token；原生产 `server.mjs` 绝不实例化本 Handler。
