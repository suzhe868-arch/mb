> 版本：2026-10-08｜状态：用户确认执行、作为工程管理协作指引落库
> 适用仓库：`suzhe868-arch/mb`
> 目的：对已通过的 Engineering Startup Gate 施工单细化协作、交接与验收；**不新增或修改产品业务规则、正式页面结构、业务状态机及数据库合同**。

## 1. 权威、边界与共同入口

1. 权威先后：`PDM-01～25 Final → Current IA → Current Low-Fi → 工程启动门禁正式施工单/验收标准 → 本协作规范与 B/C 路线图 → 历史工程资产`。本文件无权改写上层。
2. 新窗口依次读 `README.md`、`CURRENT_PROJECT_STATE.md`、`NEXT_ACTION.md`、`PROJECT_STATE.json`、`IMPORT_STATUS.md`、`07_重建工作区/DECISION_REGISTER.md`、工程启动门禁三份正式文件，以及本规范和本窗口路线图；实施前读取对应 PDM Final/Current IA/Current Low-Fi 的实际载体，不得以历史摘要替代。
3. 工程启动门禁结论：`PASS / USER_APPROVED / APPLIED`；其 160/160 资产与 218/218 旧接口是**归属分类**，不是实现、逐字段验证或运行验收。旧 9/22 Delta、`09_历史工程资产基线/` 为 `INPUT_ONLY`。
4. 产品基线保持 `NOT_READY`，F01/H01 尚无验收完成事实。不得将“规则完备”“门禁通过”“设计完成”“测试计划已有”写成“系统已可上线”。

## 2. 三窗口唯一职责

| 窗口 | 工作分支与职责 | 可以自主处理 | 不得自主处理 |
|---|---|---|---|
| **A 主控** | `main` 的全局状态、工作单调度、跨轨依赖、风险与冲突、独立验收、组织合并 | 静态审查、细化已批准施工单、核查 B/C 分支、出验收意见及技术协调方案 | 未经用户确认擅改产品 Authority；未经批准合并、部署、迁移生产数据 |
| **B 工程执行** | `feat/f01-foundation`；F01 起步，后续 F02～F08 按门禁调度；实际工程代码、数据层、接口、测试和自验 | **已授权施工批次内**的技术拆解、实现、测试、分支提交与技术决策记录 | 越级启用未获放行的 F 单；修改现行产品规则/设计结论；直接写 main；未经批准接触生产数据库 |
| **C 设计执行** | `design/h01-design-system`；H01 起步，H02 按批次放行；设计规范、核心模板、高保真交互与自查 | **已授权设计批次内**的规范、组件、状态图、代表性模板与设计分支提交 | 把视觉方案视为新产品规则；修改数据库/业务后端；提前批量开发正式页面；直接写 main |

- H03 是**已确认页面批次的正式前端实现**，由 A 根据已验收 H02 批次与可联调 F04/F05～F07 接口安排具体执行者，不默认全部归 C。
- H04 是三端联调、交互回归和用户验收；A 协同 B/C 安排，不视为设计图审即上线批准。
- A 不代替 B/C 暗中施工；B/C 无需由用户转发工作记录，A 可直接以相应 GitHub 分支 ref 审查已推送证据，但**聊天窗口之间不具备自动消息同步**。

## 3. 开工授权与阶段放行

1. **规划≠施工授权**：本次用户“确认执行”授权这三份管理文档和接力入口落库，**不自动批准全部 F01～F08 或 H01～H04 的代码/设计施工**。B/C 依据自己窗口已取得的明确授权执行。
2. 当前 Gate 已放行 F01/H01 作为可启动任务；B/C 获用户对相应施工范围确认后，可自主细分执行、在本分支提交，**同一已批准批次内的普通工程技术细节不必反复请求用户决策**。
3. 扩大到新的 F02～F08、H02～H04 阶段前，A 核对依赖、验收和风险，按仓库既有用户授权机制取得对应放行。F02～F04 的只读分析/非破坏性设计准备可提前进行，但不代表允许迁移、敏感权限修改或正式业务写入。
4. 新产品取舍、资金和归属规则、权限语义、可见性、数据保留、关键视觉方向、真实账号/环境、UAT 和上线，必须按既有 Gate 与用户裁决办理。
5. 遇到真实产品冲突：**仅暂停受影响项**→记录证据与影响范围→A 审核→用户裁决→批准后先更新上层 Authority→再调整施工；其他无关任务可继续。

- A 全局正式状态仅写 `main`：`README.md`、`CURRENT_PROJECT_STATE.md`、`NEXT_ACTION.md`、`PROJECT_STATE.json`、正式裁决记录。
- B 仅向 `feat/f01-foundation` 提交工程实现、工程过程记录；C 仅向 `design/h01-design-system` 提交设计成果、设计过程记录。**任何窗口不得以“通知 A”为由直接覆盖 main 的四份全局状态文件**。
- B/C 的阶段回报建议分别使用各自分支内的 `07_重建工作区/工程执行回报/` 与 `07_重建工作区/设计执行回报/`；路径不存在可在获得当前分支施工授权后创建。回报保存在原分支，A 使用 `ref=分支名` 读取，不需要提前合并 main。
- B/C 不得单方面修改对方所属文件；跨轨依赖通过明确的接口/组件交接卡处理。设计图不等于接口实现，接口草案也不等于已批准界面。

- 任何合并 main 前：A 比对提交、文件清单、授权、上层规则、测试记录、冲突和回滚方案，用户明确确认合并后方可实施。**工作分支自验通过不等于合并许可**。

## 5. 工作单与交付证据

每个可独立验收批次必须具备如下项目；没有实际证据应写 `NOT_RUN` 或 `BLOCKED`，严禁推定通过：

| 必填项 | 要求 |
|---|---|
| 身份 | 工作单 ID、窗口、执行分支、起点/当前 HEAD、日期、当前状态 |
| 权威 | 对应 PDM Final、Current IA/Low-Fi 页面/状态/动作与 Gate 施工单引用 |
| 范围 | 目标文件、变更摘要、受影响功能、未触碰范围、复用资产来源与去向 |
| 技术 | 技术选择记录、依赖和环境（不泄露凭据）、执行命令 |
| 质量 | 构建/测试/静态检查真实命令、输出结果、正反例、未运行及原因 |
| 追溯 | 分支提交 SHA、文件清单、风险/缺陷、回滚要点、待裁决问题 |
| 验收 | 执行者自验结论；A 独立验收状态；下一阶段放行条件 |

- 统一验收三层：`DESIGN_REVIEWED`（方案审查）→`IMPLEMENTED_TESTED`（按适用类型完成实现/可验证设计资产及实证）→`ACCEPTED`（A 审核通过，涉及用户视觉/产品选择时还需其明确批准）。阶段具体形式由 F/H 单决定，**高保真设计不得冒充代码运行验收**。
- 状态建议：`PLANNED / IN_PROGRESS / BLOCKED / READY_FOR_A_REVIEW / CHANGES_REQUESTED / ACCEPTED`。A 只依据 GitHub 已推送可检查成果判断，不依据 B/C 自报直接改 main 为 `COMPLETE`。
- 阻断项分类：`TECHNICAL`（B/C 内修）、`CROSS_TRACK`（A 协调）、`PRODUCT_DECISION`（用户裁决）、`ENVIRONMENT_APPROVAL`（用户许可）。只停影响单元，不扩张为全项目返工。
- **每个阶段的“下一步”仅是本窗口的局部施工顺序**，全局唯一下一步仍由 `main/NEXT_ACTION.md` 控制。
