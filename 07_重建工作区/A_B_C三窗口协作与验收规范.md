## 1. 总原则：一次布置，当前窗口一口气做完

1. **接到明确的阶段目标/施工单后，默认授权窗口在该目标完整边界内连续执行全部本职工作**。不再每做一个内部子步骤、补一个测试、写一份文件、A准备一份清单、修一次CI或合并一次，就向用户重新申请“确认执行”。任何“继续/接着干”都按当前唯一已下达完整任务推进到该窗口可以交付的终态，不是只完成第一小步。
2. A有权在**既有冻结产品规则、已建立工程路线图及安全隔离条件内**自行完成技术研判、拆批、结构建议裁定、确定施工文件边界、编制正式施工单、登记技术放行、安排B/C执行、复审整改、在全部门禁通过后按标准PR合并main和同步全局状态；上述**同一任务的内部技术步骤不再逐项问用户**。A完成自身所有准备工作后才说“下一步由B执行”。
3. B/C收到A已正式放行的**完整任务目标**后，必须尽可能一轮连做：阅读权威与最新main→分支隔离→实施/设计→全量自查和回归→修复失败→重新运行→固化资产/证据→最终同SHA成功CI或对应真实设计证据→完整交接报告→`READY_FOR_A_REVIEW`。遇到自身可解决问题继续闭环，不能每修一项都向用户申请下一步。
4. A接到B/C完整交接后，**一次复核至终态**：核对文件清单、Authority、环境/测试/资产证据，提出一份可执行整改清单；必要的技术整改由B/C按原任务继续，直到PASS或确实阻断。PASS后A可按仓库标准PR流程合并对应授权成果并更新main，无需要求用户再次点击“批准合并”。A不能把`B_SELF_TESTED`或`C_RENDERED`直接当`A_ACCEPTED`。
5. **窗口接力而非用户审批链**：A准备齐→给B/C“立即执行”完整工作单；B/C做完→给A“立即独立验收”；A验收合并→自动准备其职责内下一工作单。用户只接收节点完成报告及真正需要本人决定的事项，不承担开发经理式逐步传话审批。
6. 本版用户指令是**已确认路线内的持续技术执行方式授权**，替代“每个F/H新子批自动要求用户单次确认”的旧流程；但不等于无限开放生产、资金、隐私、真实第三方连接或增改产品Authority。技术批的实际施工范围仍由A书面限定和真实门禁控制，B/C不能自行跨过尚未验收依赖。

## 3. 持续执行的自动放行范围与必须停下的边界

**A可以在不额外问用户时继续安排**：
- 针对已确认PDM Final/IA/Low-Fi/F01～F08/H01～H04总体路线的**非生产技术实现与高保真迭代**，对先前未实现模块分批编写具体范围并放行，前提为依赖满足、没有引入新业务规则或新增外部高风险操作。
- 隔离一次性PG16/本地合成数据中安全追加迁移（只可新版本且需精确结构封印）、权限/会话/并发保护实测、有限业务合同与纯合成数据回归；原版本不可变，失败必须停止合并。
- 既有视觉方向内的样式、排版、图片清晰度、响应式与组件状态修正，C应把一批的完整资产返工到底，不能以“我已画一张图片”宣告完成。
- 工程签发、工作单补证、失败CI修复/复跑、A验收整改以及正式PR创建/正常合并及main指针更新（合并前已完成独立检查）。

**仅以下情况才集中向用户提交决策/许可（一次列清，不问可由技术自定的问题）**：
1. 现有PDM Final/Current IA/Low-Fi之间出现无法技术消解的**真实产品冲突或新的产品取舍**，例如权益、资金、价格、客户归属、权限语义与状态机；A先提交差异、各选项、推荐方案和影响，用户一次裁决。
2. 关键品牌视觉方向**确实没有已确认参照**、或要推翻已确认视觉方向；C先提交可在实际渲染中比较的完成稿，由A集中一次询问，不逐页重复确认。普通视觉美化不要求逐张用户签字；最终用户视觉验收仍依H01/H02的产品要求。
3. **真实生产部署、线上迁移/清库、真实账号或客户数据接触、真实资金动作、JYT/微信/飞书等第三方实际凭据及外部写入**：仍须相应环境/权限独立明确授权，不以此协作规范代替。
4. 不在冻结工程/设计范围内的**重大新增项目目标或不可逆破坏性变更**。A不能自行把准备文档解读为删除产品安全门禁。
5. 实际GitHub权限不足/工具拒绝或外部资源缺失且**已穷尽可用合法途径**，必须如实`BLOCKED`，说明已做、未做、谁能解除；不能假称合并或验收成功、不得绕过分支保护。

**内部技术参数、文件命名、正反例、隔离测试实现及一般缺陷修复不属于用户裁决。** 遇局部阻断保留其它合法任务继续，交接最后报告同时显示阻断项。

## 4. 工作单完整性、自动验收与合并

1. A正式施工/设计工作单必须一次写完整：任务ID及唯一负责人、main起点与指定分支、Authority逐项引用、目标文件/禁止目录、相关前批已验收实物、精确数据/权限/页面状态、技术依赖/锁与回滚、可操作的正反例及真实CI/截图验收、不可实现项/责任归属、`READY_FOR_A_REVIEW`交接格式。**不能只给B/C一个模糊口令而让其重新发明业务。**
2. 每个可独立验收单元都应保留真实提交SHA、GitHub CI/资产、文件列表、实际通过与实际未运行项；A应自动审查，不要求用户中途转发。问题用`A_CHANGES_REQUESTED`指定**完整**整改清单，B/C自行闭合并重新交A，用户不用逐项确认。
3. 只有`A_ACCEPTED`且GitHub验证head SHA、合并冲突、旧文件/业务边界、相关CI/真实性、目标分支与版本满足，A才能以**标准PR merge**合入main；**同任务已授权的验收后合并不再单独问用户**。PR创建工具短暂异常先合法重试/查当前结果；不可凭空宣布成功或改写main分支绕过既有PR保护。
4. A合并后同一动作链必须更新全局五项：`README.md`、`CURRENT_PROJECT_STATE.md`、`NEXT_ACTION.md`、`PROJECT_STATE.json`、`DECISION_REGISTER.md`；并记录合并PR、merge SHA、B/C验收SHA、同SHA证据、哪些仍未完成。文档对旧阶段的“待批准”字样是历史记录，不可当有效当前指针。
5. 触发下一阶段时：A应先把本阶段闭环并**继续完成自己的下一工作单/裁决/放行**，最后明确输出`NEXT_OWNER=A|B|C|USER`及`NEXT_TASK`。如还有A内工作未完成，不能把“下次A继续”伪装为已到B窗口。
6. `B`和`C`仅改各自技术/设计工作分支，`A`维护main；禁止强推/重置其他分支、未审合并和根据内存猜测HEAD。技术数据、证据及样例不带密钥/真实个人资料。
