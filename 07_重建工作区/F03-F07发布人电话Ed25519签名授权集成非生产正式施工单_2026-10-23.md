## 一、目标与当前代码事实

### 1.1 目标

在隔离 CI 中实现一个版本化的 F03→F07 签名授权适配器：

1. F07 为一次具体电话权限检查创建新挑战，绑定 request ID、随机 nonce、员工、操作、车辆、受众与短有效期。
2. F03 使用现有 F03 会话验证器读取**当前真实 PostgreSQL 16**中的员工、会话、角色、`publisher.phone.sensitive` 个人授权/拒绝、当前专项 Scope 绑定、专项授权配置及生命周期快照；只有所有当前事实都允许时才签发 Ed25519 断言。
3. F07 验证签名、密钥 ID、issuer/audience、nonce、请求/员工/能力/车辆/Scope 绑定、签发与到期时间，并在真实 PG16 中原子消费一次性挑战。
4. 验签成功后必须调用现有 `engineering/f07/publisher-phone-scope-runtime/guard.mjs` 的 `authorizePublisherPhone` 重新核验当前 F03 会话/个人授权和 F07 合成车辆/上游发布人/锁车事实。签名不能代替当前 Guard，也不能绕过撤权。
5. 所有失败默认拒绝，使用稳定拒绝码；不得返回电话号码、电话 Token、真实发布人资料或其他敏感字段。

## 三、协议与安全合同

### 3.1 当前事实读取

F03 签发端必须在每次请求中使用现有 `IsolatedAuth.withSession(..., {normalOnly:true})` 重新验证当前员工会话。签发前须核实：

- 会话正常、未受限、员工凭证启用、强制改密状态关闭；当前员工在职，非 System Admin、非 4S。
- 角色属于现有电话专项允许的 `sales`、`manager`、`store_manager`；不得从客户端接受 actor、role、permission、scope 或 enabled 状态。
- `public.permissions` 中存在精确 `publisher.phone.sensitive`；当前个人覆盖必须为 `allow`，个人 `deny` 永远优先。
- `employee_capability_scope_bindings` 与 `employee_data_scopes` 存在当前有效的 `publisher_phone_special` 绑定；Scope 归属和 reference 必须是当前员工，且 `granted_at/ended_at` 在当前有效窗口。
- `f03_publisher_phone_admin_test.employee_mode` 为 `CI_ONLY_F03_PERMISSION_CONFIG`、`enabled=true`、模式严格为 `LOCKED_ONLY` 或 `ALL_ACTIVE_JYT`；当前员工在职/角色/主角色/门店快照与授权时一致，生命周期审计水位没有发生导致失效的变化。
- 查询、会话、Scope 或审计事实任一不可用/不完整，一律不签发。不得回退到旧缓存、客户端字段或合成 F03 正向事实。

### 3.2 签名载荷与有效期

- 使用 Node.js `node:crypto` 的 Ed25519 `sign/verify`；对固定字段白名单做确定性规范化后签名，拒绝未知字段、重复/不规范类型和非规范编码。
- 每个 CI Job 运行时在内存中生成临时 Ed25519 密钥对；私钥不得写文件、环境变量、日志、数据库、Artifact、Issue 或仓库。公钥仅作为本次运行的验签输入，不作为正式带外信任根。
- 载荷至少绑定：协议版本、issuer、audience、kid、jti、challenge ID、nonce、request ID、员工 ID、能力 `publisher.phone.sensitive`、具体 action、vehicle ID、listing-cycle ID（如在挑战时已知）、scope mode、F03 当前授权事实摘要、`iat`、`exp`、`origin=CI_SYNTHETIC_ONLY`、`formalSourceSigned=false`。
- 断言 TTL 上限 15 秒；允许的时钟偏差最多 2 秒。禁止未来签发、已过期、超长 TTL、错误 issuer/audience/kid、字段错配或将签名用于另一个员工/请求/车辆/操作。
- F07 端的 challenge 必须由其自己生成，随机 nonce 至少 256 bit；挑战记录含 request ID、action、vehicle ID、audience、nonce 摘要、创建/到期时间、来源标记及 `consumed_at`。消费必须在真实 PG16 中原子执行，重复/并发重放最多一个请求成功。
- 签名授权只证明本次 F03 当前员工电话专项权限；F07 仍必须用现有 Guard 复查当前员工事实、F07 当前 JYT/wholesale/active 车辆、发布人映射与锁车状态。任何 F03/F07 复核失败都拒绝。

### 3.3 来源级别和密钥边界

- 每条断言必须显式标记 `CI_SYNTHETIC_ONLY`、`formalSourceSigned=false`、`productionReady=false`。
- 不实现正式密钥配置、密钥托管、长期密钥轮换、生产部署、正式 Issuer 注册或全局通用能力签发器。
- 不修改/批准 `TECH_ALIAS_PENDING_A`，不改变 F03 通用 current-facts 的拒绝语义。
- 不把本协议候选解释为 F05-7 旧 66 项 Oracle 的签署/成功证据，不改 Issue #106 的状态。

### 4.2 最低正反例

至少 24 个独立业务/安全断言与 12 个 HTTPS 黑箱断言；每项必须在最终 SHA 的真实测试中执行，零跳过。至少覆盖：

1. 正常 F03 当前员工会话签发，F07 正确验签并通过现有 Guard。
2. `LOCKED_ONLY` 有效当前锁可通过；无锁、过期锁、错误 listing cycle 必须拒绝。
3. `ALL_ACTIVE_JYT` 只允许当前 active JYT wholesale 车辆；其他来源、转名邦/4S、下架、缺 publisher 映射必须拒绝。
4. 个人 deny、专项撤权、Scope 绑定结束、员工停用、角色/门店快照变化、凭证撤销/epoch 变化后重新请求不得签发或必须被 Guard 拒绝。
5. F03 当前数据库不可用、权限表/Scope/生命周期事实缺失、F07 数据库不可用时全部 fail-closed。
6. 签名篡改、错误公钥/kid、issuer、audience、protocol version、员工、能力、action、车辆、请求 ID、challenge ID 或 nonce 不匹配必须拒绝。
7. 过期、未来签发、TTL 超限、缺字段/多字段/类型异常必须拒绝。
8. 同一 challenge 顺序重放与并发重放；最多一次消费成功，其余均拒绝。
9. 真实 HTTPS 黑箱验证 loopback TLS、固定 Host/Origin、HTTP method、Content-Type、query/body 大小限制、无缓存响应、拒绝不可信输入；证书信任必须在测试客户端中明确配置，不得以全局关闭 TLS 校验掩盖问题。
10. 对外响应/日志/Artifact 不包含任何电话号码、Token、私钥或原始凭证；成功结果仅返回授权判定与必要的非敏感审计 ID。
