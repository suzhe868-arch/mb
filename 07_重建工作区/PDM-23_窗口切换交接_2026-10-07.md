## 3. 本窗口最新讨论｜必须保存，但尚未定稿

### 3.1 客户侧：微信小程序消息能力

用户明确提出：

- 当前 V1 是微信小程序，不是独立原生 App。
- PC 主动通知使用概率很低，V1 暂时不考虑 PC 主动通知。
- 应重新核实微信小程序实际允许的消息方式，而不是简单写“客户侧主动消息关闭”。
- 小程序可考虑微信允许的订阅消息 / 服务通知类能力，但必须服从微信平台当前：
  - 类目；
  - 模板；
  - 用户授权；
  - 平台发送限制。
- 不能把微信小程序当成原生 App Push。
- 微信发送失败、用户未授权、模板不支持等情况不能改变 Lock / Waitlist / Transaction / Refund / Consultation 等业务事实。

### 3.2 员工侧：飞书作为主要主动通知渠道

用户倾向：

- 员工通知主要通过飞书。
- 飞书通知应该能够开启 / 关闭，而不是所有提醒永久硬绑飞书。

当前讨论形成的候选分层：

1. 公司级飞书通知总开关；
2. 员工个人飞书业务提醒开关；
3. 飞书业务总群 / 群告警开关；
4. 员工级“其 SLA 超时是否进入飞书总群通告”开关。

以上仍需下一窗口结合历史证据重新扫描后形成正式 Batch 4 候选，不得直接视为已批准。

### 3.3 员工级“是否进入总群超时通告”｜真实遗漏待恢复

用户明确回忆历史上讨论过：

> 某个员工（例如销售、经理、店长等）可以单独配置：当其负责的业务超时后，是否把该员工的超时发到飞书总群提醒。

当前理解候选：

- 关闭该员工的“总群超时通告”只影响总群投递；
- Consultation SLA / timeout 事实仍正常成立；
- 后台仍记录；
- 不改变 assignee / owner / responsible；
- 不自动关闭 Consultation；
- 不等于关闭该员工自己的个人飞书通知；
- 不等于关闭公司飞书总群功能。

本窗口已对当前仓库用“总群超时通告 / 飞书总群员工开关 / 不通知总群 / 经理店长总群提醒”等关键词检索，**未找到已固化的明确规则文字**。

因此当前状态必须标记为：

> **CONVERSATION_RECOVERED_CANDIDATE / HISTORICAL_RESCAN_REQUIRED / NOT_APPROVED / NOT_APPLIED**

不能假装它已经在仓库里存在，也不能因为用户记得就跳过历史重扫。

### 3.4 PC 与未来 App

当前讨论方向：

- V1 暂不建设 PC 主动通知 / 浏览器 Push / 桌面弹窗。
- PC 可以保留通知配置、日志、管理能力，但不把 PC 作为主要主动通知渠道。
- 未来若建设独立 App，可以把 App Push 作为新的 notification channel 扩展。
- 当前只“预留可扩展性”，不做 App Push 产品页面、配置中心或工程实现。

### 3.5 对原 P23-B3-16 的关系

已执行的 P23-B3-16 为：

> 客户侧主动消息继续默认关闭，除非已有明确 Authority；不新增通用客户消息 inbox / 已读未读状态机，不因员工飞书事件自动生成客户微信消息。

当前新讨论**不要求撤销 B3-16**。

正确关系应是：

- B3-16 继续有效，阻止无 Authority 的客户主动消息扩张；
- 如果 Batch 4 后续明确批准“微信小程序允许的订阅消息”作为 V1 合法客户渠道，则该批准本身成为新的明确 Authority；
- 仍不建设“通用客户消息中心”。
