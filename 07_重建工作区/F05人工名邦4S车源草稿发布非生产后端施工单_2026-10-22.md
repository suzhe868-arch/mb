## 三、任务目标与 API 合同

所有新 HTTP 路由只可在本任务明确的隔离 loopback TLS 测试运行器中挂载，例如：

- `POST /__ci__/f05-manual-vehicle/v1/drafts/auto-save`
- `GET /__ci__/f05-manual-vehicle/v1/drafts`
- `GET /__ci__/f05-manual-vehicle/v1/drafts/:draftId`
- `PUT /__ci__/f05-manual-vehicle/v1/drafts/:draftId`
- `DELETE /__ci__/f05-manual-vehicle/v1/drafts/:draftId`
- `POST /__ci__/f05-manual-vehicle/v1/drafts/:draftId/publish`

路径可以按现有规范微调，但业务语义不得缩减。禁止将这些路由接入默认/生产 `engineering/src/server.mjs`。

### 3.1 多草稿持久化

1. 每次“新增车源”开始独立录入，不自动选择或恢复其它 draft。
2. 空白 payload 且没有任何有效车辆资料时，不创建持久 draft；服务返回明确的 `persisted=false` 结果。
3. 开始填写有效资料后，服务端生成 draft ID 并真实写入 PostgreSQL；后续自动保存只更新请求明确指定的 draft。
4. 多条草稿相互独立；列表、详情和修改均按当前操作者身份、当前权限及当前数据范围过滤。
5. draft payload 允许不完整；不得创建正式 `vehicles`、`vehicle_listing_cycles`，也不得进入客户目录、正式 Matching、Recommendation、Priority、Lock 或 Transaction。
6. 使用乐观版本号/CAS 或等价机制防止并发覆盖；过期版本必须返回冲突并保留已提交数据。
7. 删除必须明确指定 draft 并提供二次确认；服务端提交时重验“从未发布、无正式 Vehicle/Cycle、无正式业务关系、当前操作者有权管理”。只允许物理删除纯草稿，不允许借草稿接口删除正式 Vehicle。

### 3.2 发布校验

正式发布时必须在服务端重新校验完整最低字段，一次返回所有缺失字段：

- `source_type`：只能为 `mingbang` 或 `four_s`；禁止人工创建 `wholesale/JYT`。
- 品牌、车系、有效本地具体 `vehicle_model_id`，且品牌/车系/车型的实际物理关系一致。
- 车型年款、表显里程、城市。
- 必须基于当前 PostgreSQL 真实车型主数据校验，不得以请求中的名称/ID 自报证明车型有效。

以下不属于发布硬门槛：

- 图片数量（允许 0 张真实图片发布）。
- 客户标价、内部批发价。
- VIN 本身是否填写。

### 3.3 VIN 与 MODEL_MISSING

- VIN 为空：允许发布，不执行 VIN 查重。
- VIN 非空：仅对当前正式名邦/4S 人工车辆执行完全一致的 VIN 查重；不得做模糊相似判断，不提供普通员工忽略重复继续发布的通道。
- VIN 重复时：阻止发布、返回明确冲突代码，并保留同一 draft ID 与所有已填写内容。只有在当前操作者对命中车辆拥有合法读取范围时才可返回可查看的车辆标识/链接，不得泄漏越权车辆资料。
- `MODEL_MISSING` 或车型链无效时：保留原 draft ID 与全部 payload，不创建 Vehicle/Cycle；补齐车型后仍返回并继续同一 draft，再次执行完整发布校验。

### 3.4 名邦/4S 身份与来源边界

**名邦员工发布名邦车源：**

- 复用现有 F05-2 当前 Employee Session、当前 active 状态、`vehicle.manage` capability、当前 Team/Object scope 与同事务发布/责任签发。
- Team、Employee、Vehicle、Listing Cycle、Event Key 等可信标识不得由客户端自报；由当前数据库身份、授权事实或数据库端 ID 生成机制决定。
- Manager/Store Head 不因角色本身自动得到超范围能力，必须验证当前 capability + scope。

**4S 成员发布 4S 车源：**

- 复用现有 F05-3A 当前 4S Employee Session、`pc.four_s.vehicle.manage`、当前有效的 System Admin 授权 license 和本人新车发布路径。
- 4S 成员只能发布/管理自己合法范围内的 `four_s` 车辆，不能切换成名邦车源；另一个 4S 账号、名邦员工或 System Admin 不能冒充该 4S 成员的业务 Actor。
- 不得创建新的 4S 组织层级，不得用 `created_by_employee_id`、静态角色、客户端 header 或旧上传事实推断当前授权。
- draft 阶段切换 `source_type` 时必须再次按当前操作者真实可发布范围校验；首次发布成功后不允许通过普通 draft API 修改已发布 Vehicle 的来源。

### 3.5 发布事务、幂等与恢复

- 必须复用现有 F05-2 / F05-3A 可信发布原语；允许为接入 draft 生命周期做最小、向后兼容的服务扩展及必要回归。
- 正式发布的 Vehicle、Listing Cycle、名邦责任或 4S 发布记录/许可绑定、必要的当前车辆事实、不可变审计以及 draft 状态必须具备同事务一致性；若采用两阶段持久化，必须证明崩溃恢复/重试可幂等收敛，不能出现对客户可见的半发布、重复 Vehicle、重复 Cycle 或无审计发布。
- 发布 ID、Listing Cycle ID、事件键由服务端/数据库生成或在可信事务内分配；不能信任客户端传入的 Vehicle ID、Cycle ID 或 Event Key。
- 并发重复发布最多产生一辆正式 Vehicle 和一个当前 Listing Cycle。相同意图重试只能得到同一发布结果；不同意图碰撞必须拒绝。
- 任一审计写入失败、责任/许可签发失败、车型验证失败或事务故障注入必须完整回滚；draft 与已填资料仍可恢复。
- 不自动创建 Demand、Match Result、Recommendation、Priority、Lock 或 Waitlist。若现有数据库触发器产生合法的受影响重算队列，应单独验证其预期行为，不得生成正式 Match/Recommendation/Lock。
