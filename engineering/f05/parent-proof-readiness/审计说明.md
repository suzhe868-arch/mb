## 核证范围

- 本目录仅做**官方 GitHub Actions GET 只读来源核对**、纯规则负例与可销毁 PostgreSQL 16 非超级用户安全回归。
- 五份 Source 原始脚本依次为：`engineering/f05/deterministic-matching-readiness-four-tier/ci-verify-workflows.mjs`、`engineering/f05/priority-arbitration-ttl-handover/ci-verify-68.mjs`、`engineering/f05/recommendation-visibility-grants/ci-verify-70.mjs`、`engineering/f05/consultation-assignee-sla/ci-verify-72.mjs`、`engineering/f05/pdm17-public-pool-owner-claim/ci-verify-72.mjs`；原旧 Source、工作流及签证代码**不修改**。
- 分别要求 64＋2＝66、64＋4＝68、68＋2＝70、70＋2＝72、70＋2＝72 个同SHA正式作业来源，且必须来自各原始 `feat/f05-7/8/9/10/10-d1...` Push 分支；任何本分支、PR事件、dispatch 事件或其他仓库来源不得替代。
- 运行接口限定 `https://api.github.com/repos/suzhe868-arch/mb` 的官方 GET；不读取真实客户、无生产数据库、无外部写入；GitHub 临时 Token 不落证据。
- 审计对象显式校验仓库、Workflow路径、提交、原分支、Run事件及完成结果、Job数与独立ID、成功状态、Artifact归属/体积/未过期/官方 SHA256 元数据。元数据不是对ZIP的独立复算，成功候选亦不是PG16原生签发证明。

## 安全边界与可信性

1. `candidate()` 可在合成测试里返回 `CANDIDATE_ONLY_REQUIRES_NATIVE_PG_LOG_INDEPENDENT_CHECK`；该纯函数**没有**核证身份，不返回 `VERIFIED_OFFICIAL`。
2. `assessSource()` 固定输出 `SOURCE_GAP`、`formal_parent_positive:false`，哪怕合成 fixture 内伪造满额成功；防止拿Mock回包自证原生父业务。
3. `audit` 入口需官方 `push` 运行、匹配仓库和完整40位SHA、有效只读 Token；本次独立分支的合法 Push 无法充当旧业务原分支 Push，保守结果 `SOURCE_GAP`。HTTP 401/403/429、分页不完整、跨版本、没有工件或有非成功作业时不得静默改成 PASS。
4. Node作业成功仅说明防伪代码与官方GET调用成功；PG16作业成功只说明一次性数据库非超级用户和失败回滚真实执行。两项独立 CI 皆不能解除历史五项失败。

## 执行与证据

- 工作流：`.github/workflows/f05-parent-proof-readiness-ci.yml`。只在指定B分支Push及目标main的PR时执行。
- Node：`node --test engineering/f05/parent-proof-readiness/tests/audit.test.mjs`；真实官方只读：在 GitHub Push 中 `node engineering/f05/parent-proof-readiness/audit.mjs audit`。运行产生 `f05-parent-proof-live.json`，固定保留来源缺口，不输出凭据。
- PG16：容器 `postgres:16`，每次新建一次性 `f05_parent_audit_ci` 与 `NOSUPERUSER/NOCREATEDB/NOCREATEROLE/NOREPLICATION` 专用角色；`tests/pg16.test.mjs` 验证实际角色、版本、回滚、权限拒绝。不可指向已有产品库。
- 两个上传工件均由 `actions/upload-artifact@v4` 强制非空；需以**最终HEAD**、官方 Run 和两份有效 Artifact 及原始日志为验收依据。未提供的官方 ZIP 自行复算绝不能写为已完成。
