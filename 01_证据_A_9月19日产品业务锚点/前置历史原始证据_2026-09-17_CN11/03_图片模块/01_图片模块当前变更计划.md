# 名邦汽车 V1｜图片模块当前变更计划

日期：2026-09-17  
状态：READY_FOR_IMPLEMENTATION  
范围：批发车图片首次入库、列表封面、详情按需吞图、一键转名邦、人工名邦/4S 图片生命周期、并发、失败与恢复。

> 本文件只记录本轮已经确认的最终业务规则与施工边界，不把尚未修改的 CN10 代码/契约写成已实现。

## 一、总体目标

把当前图片系统统一为三条清晰链路：

1. **普通批发车**：首次入库冻结图片快照；首张可用图立即本地化作为列表封面；其余图片在真实查看时按需吞到名邦服务端对象存储。
2. **一键转名邦**：已吞图片不重复下载，物理文件业务所有权转给新名邦车；未吞图片在转换时尽力迁移；车辆转换成功后完全进入普通名邦车图片生命周期。
3. **人工名邦 / 4S**：上传后即为名邦正式本地图，可新增、删除、排序；允许 0 图发布并使用默认占位图。

## 二、Change Set

### FIX-IMG-01｜批发车图片首次入库快照冻结

- 上游车辆首次入库时，读取当次 `images[]`，把图片身份、原始 URL、顺序一次性写入名邦数据库。
- 该图片集合从首次入库后即冻结。
- 后续上游新增图片、删除图片、改排序，均不再同步、不比对、不回写。
- 已冻结 URL 后续失效时，只按单张图片失败规则处理，不重新同步整车图片集合。

### FIX-IMG-02｜批发车列表封面必须本地化

- 批发车首次入库时立即尝试本地化上游排序第一张图片。
- 若第一张失败，则按上游原始排序继续尝试后面的图片，直到获得第一张可用本地图作为当前列表封面。
- 原始图片排序不因 fallback 改变。
- 所有图片均失败时，车辆仍正常入库、匹配、展示；列表/详情使用默认占位图。
- 图片不是批发车辆入库硬条件。

### FIX-IMG-03｜批发车其余图片按需吞图

- 除列表封面外，其余批发图片默认只保存首次快照 URL，不做全量预下载。
- 第一次进入详情：列表封面已在本地，立即处理第 2、3 张，并预取第 4 张。
- 用户继续滑动时，始终维持前方约 2 张的预加载窗口。
- 图片进入真实展示/预加载窗口才触发吞图。
- 第一次回源成功时，同一份响应数据同时：
  1. 返回当前客户展示；
  2. 写入名邦服务端对象存储。
- 不要求客户等待“先保存完成再重新请求本地”。

### FIX-IMG-04｜已吞图判定与本地优先

只有同时满足以下条件才算“已吞图”：

1. 图片已成功写入名邦对象存储；
2. 数据库已成功写入有效 `local_object_key` / 本地对象标识。

成功后：

- 正常展示永久优先使用名邦本地图；
- 不再访问原上游 URL；
- 不再核验上游是否删除、换链接或改排序；
- 上游 URL 可保留作来源审计与本地文件异常自愈备用。

异常边界：

- 客户已看到图片，但对象存储失败：本次客户照常看到；不得标记已吞图；以后再次查看可重新吞。
- 对象存储成功、DB 写入失败：短暂重试 DB；仍失败则删除刚保存的对象文件，恢复“未吞图”。

### FIX-IMG-05｜吞图失败、重试与展示

- 单张图片失败不影响整车，也不阻塞其他图片。
- 每轮单图最多自动尝试 3 次，采用退避，禁止连续猛打上游。
- 3 次仍失败：本轮停止，记录失败。
- 以后该图再次被真实查看时，可以开启新一轮最多 3 次尝试。
- 失败图片不占详情图集可见位置；DB 记录与原始排序继续保留。
- 以后某次成功吞图后，按原始位置重新出现在图集中。
- 整车无任何可用图片时才显示默认占位图。

### FIX-IMG-06｜首图 fallback

- 原排序第一张图不可用时，展示层使用后续第一张可用本地图临时顶替。
- 不修改 DB 原始排序。
- 原第一张以后成功本地化时，自动恢复为首图。

### FIX-IMG-07｜本地图片异常自愈

- 已吞图正常情况下绝不回源。
- 仅确认名邦本地对象损坏、丢失、404 时，允许使用保留的首次快照 `upstream_url` 做一次恢复尝试。
- 自愈期间使用下一张可用图或占位图，不阻塞整车。
- 上游地址也失效时，记录修复失败，不无限请求。

### FIX-IMG-08｜并发与 single-flight

- 同一图片同一时刻只允许一个真实下载任务。
- 建议唯一键：`vehicle_id + upstream_image_id`。
- 已下载：直接本地返回。
- 下载中：其他请求复用当前任务，不重复回源。
- 不同图片可以并行。
- 单车同时最多 3 张吞图任务，其余排队。

### FIX-IMG-09｜车辆上下架与批发图片资产

- 上下架、售出、不可用只改变车辆销售状态，不重置图片资产状态。
- 已吞本地图继续保留作为历史资产。
- 未吞图继续保留首次入库冻结 URL。
- 下架期间不主动继续吞。
- 重新上架后：已吞图直接复用，未吞图继续原按需逻辑。
- 不重新抓整套上游图片，不重新生成图片快照。

### FIX-IMG-10｜人工名邦 / 4S 图片

- 允许 0 图发布；0 图使用默认占位图。
- 上传成功后即为名邦正式本地图，不存在“未吞图”。
- 可后续补图、删图、拖动排序。
- 删除首图后，剩余排序第一张自动成为新首图。
- 删除到 0 图不影响车辆在售。
- 批发采集图片不允许人工修改原始排序。
- 业务层不设固定图片数量、单图大小、格式上限；只保留必要技术安全校验，确保获取内容确实为可接受图片。

### FIX-IMG-11｜一键转名邦图片迁移

触发一键转名邦时：

- 新名邦车创建与图片迁移结果解耦；新名邦车成功创建后不因图片问题回滚。
- 已经吞成功的图片不重新下载。
- 正在吞的图片复用当前 single-flight 任务，不重复下载。
- 未本地化图片进入转换阶段的全量迁移。
- 图片始终保持首次批发快照中的原始顺序。
- 新名邦车立即进入名邦本地图体系；已成功图片立即可用，尚未成功图片不占可见位置；全部不可用时显示占位图。

### FIX-IMG-12｜转换后图片失败不做复杂补偿

- 车辆本身未创建成功：才属于真正的“转换失败”。
- 新名邦车已经创建成功但部分图片未迁入：属于“图片没搬全”，车辆继续正常存在和销售。
- 不建立复杂的“失败图片无限重试 / 人工重跑迁移”机制。
- 迁移失败项保留日志/审计即可。
- 销售后续直接按普通名邦车方式手工上传缺失图片。

建议转换结果语义：

- `success`：车辆创建成功且目标图片全部完成本地化。
- `partial_failed`：车辆创建成功，但存在部分图片未迁成功。
- `failed`：车辆本身转换失败，未创建新名邦车。

### FIX-IMG-13｜一键转名邦后的资产所有权

- 一键转名邦时，原批发车已经吞成功的物理图片文件**不复制、不重新下载**。
- 这些物理文件的业务所有权直接从原批发车转移给新名邦车。
- 原批发车仅保留 `upstream_image_id / upstream_url / 原始排序` 等来源历史，不继续持有对应 `local_object_key`。
- 不允许原批发车和新名邦车长期共享同一物理文件引用。

### FIX-IMG-14｜转换后的名邦车彻底进入人工车生命周期

- `vehicle_conversion` 永久保留车辆来源关系。
- 图片进入新名邦车后可以继续保留来源元数据，但运行生命周期与普通人工名邦车一致。
- 销售可新增、删除、排序。
- 删除图片 = 删除业务图片记录 + 删除对应物理对象。
- 删除/排序/补图不回写原批发车，不重新触发上游图片同步。
- `content_hash` 只用于内容校验、防重复判断、幂等辅助；不做跨车辆物理文件共享。

### FIX-IMG-15｜服务端“本地”定义

- “吞到本地”统一指**名邦服务端对象存储/CDN**，不是客户手机/微信客户端缓存。
- 所有客户、销售共享已经本地化的图片资产。
- 客户端缓存只属于性能优化，不参与业务状态判断。

### FIX-IMG-16｜图片访问与车辆权限

- 图片访问不得绕过车辆查看权限。
- 数据库保存内部对象标识，例如 `local_object_key`。
- 客户端/员工端由名邦受控 HTTPS/CDN 地址访问图片，不直接暴露对象存储内部地址。
- 短时签名 URL、CDN Token、代理方式属于工程实现细节，本轮不固定具体时长/机制。

## 三、明确取消 / 不采用的旧方案

以下方案本轮明确不采用：

- 批发图片持续与上游做增删/排序同步；
- 已吞图继续根据上游变化删除或刷新；
- 批发车列表滚入可视区域时才第一次下载首图；
- 一键转名邦时重新下载已经吞成功的图片；
- 一键转名邦后构建复杂的失败图片人工重试/多轮迁移系统；
- 不同车辆/业务图片长期共享同一个 `content_hash` 物理对象；
- 名邦正式车删图后延迟垃圾回收作为默认生命周期；
- 图片失败阻塞车辆入库、发布或在售。

## 四、实现层需要核实/整改的已知点

根据本窗口此前对 CN10 的直接检查，至少存在以下实现/契约缺口，需要施工时重新以当前代码为准核验：

1. Starter 曾明确标记真实 image proxy / object-storage URL resolver 未完整实现。
2. 一键转名邦的真实 conversion worker/handler 未完整落地。
3. 人工车辆缺少完整的上传、删除、排序图片 API 闭环。
4. 0 图占位图规则虽已进入合同，但 Starter 读路径此前不会真实返回 placeholder。
5. 原有 `image_migration_jobs / image_migration_items / vehicle_images.migration_state` 的状态定义与本轮简化后的规则需要重新对齐。
6. 需要新增“首次入库首张可用图本地化”和“批发图片首次快照冻结”合同。
7. 需要新增按需吞图 single-flight、单车并发 3、每轮单图 3 次失败重试测试。
8. 需要补一键转名邦“已吞图片所有权转移，不共享物理文件”的 DB/API/事务约束。

这些属于 **TO_VERIFY / ENGINEERING WORK**，不得在施工前写成已实现。

## 五、DO NOT BREAK

- 不改变批发车 / 名邦车 / 4S 的既有来源语义。
- 不改变一键转名邦“原批发隐藏、新名邦立即上架”的主业务规则。
- 不把图片重新变成车辆发布硬条件。
- 不允许图片失败影响 Matching / Priority / Lock / Transaction 的正常业务状态。
- 不引入新的跨车辆图片共享生命周期。
- 不把客户端缓存当作服务端已吞图。

## 六、验收重点

至少覆盖：

1. 批发车首次入库冻结图片集合，后续上游变化不进入本地集合。
2. 首图成功本地化后列表不再回源。
3. 第一张失败时可用后续图片临时作为列表封面，不改原排序。
4. 详情第 2/3/4 张按需吞图及前向预加载窗口。
5. 同一图片 100 个并发请求只产生 1 次真实下载。
6. 吞图成功必须同时满足对象存储成功 + DB 成功。
7. 失败图片跳过可见图集，以后真实查看可重新尝试。
8. 已吞图正常不再访问上游；只有本地损坏允许自愈回源。
9. 上下架不重置图片状态。
10. 一键转名邦复用已吞图片，不重复下载。
11. 一键转名邦时正在吞的图片 single-flight 任务被转换流程复用。
12. 转换成功 + 部分图片失败不回滚新名邦车。
13. 转换失败图片后续由人工补图，不存在复杂迁移重试入口。
14. 已吞物理文件所有权转给新名邦车，原批发车不再持有 local object。
15. 转换后删图会删除新名邦车图片物理文件，不误伤原批发车。
16. 人工名邦/4S 0 图发布、补图、删图、排序均正常。
17. 图片 URL/对象地址无法绕过车辆查看权限。
