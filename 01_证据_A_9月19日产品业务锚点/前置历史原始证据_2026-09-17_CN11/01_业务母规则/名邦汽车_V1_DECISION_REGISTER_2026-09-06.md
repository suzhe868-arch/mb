## 【DEC-001】

**问题：** 客户微信身份、手机号、头像昵称分别承担什么职责？

**为什么会出现：** 需要同时满足稳定识别 customer、普通浏览低门槛、真正人工服务时获得联系电话。

**原规则/原设计：** 早期可能把手机号当身份主键，或进入即要求完整资料。

**发现的冲突：** 手机号会变更/复用；头像昵称强制会阻断普通浏览和收藏。

**讨论过程：**
- A：进入就完整授权资料，过重。
- B：微信身份稳定映射 customer_id；头像昵称持续引导但非硬门槛；手机号仅在人工服务动作触发。

**被否决方案：**
- 手机号作为 customer_id
- 头像昵称未完善禁止浏览
- 收藏前强制手机号

**最终确认：** 微信身份→customer_id；手机号是人工服务门槛；头像昵称是个人资料；授权成功自动继续原动作；拒绝手机号不创建正式人工服务对象。

**简化版：** 身份归身份，联系方式归联系方式；普通看车不强迫留电话，要销售服务时再要。

**Superseded / 禁止恢复：**
- 禁止恢复：手机号作为 customer_id
- 禁止恢复：头像昵称未完善禁止浏览
- 禁止恢复：收藏前强制手机号

**影响范围：**
- SSOT
- IA
- 客户端
- CRM
- 数据模型
- API
- 低保真

**当前状态：** CLOSED

## 【DEC-009】

**问题：** 为什么正式 recommendation 不再使用 REC 推荐参数 / 推荐专用链接？

**为什么发现：** recommendation 已经成为数据库中的正式客户↔车辆业务关系；如果微信 URL 再携带 recommendation 身份，会产生第二事实源。

**旧规则 / 原方案：** 曾考虑使用 REC 专用链接、REC URL 参数或推荐专用分享页，让客户通过该链接进入“被推荐车辆”。

**发现的冲突：** 数据库 recommendation 与 URL recommendation 会重复表达同一事实，并引入防伪、过期、撤销、转发扩散和权限泄漏问题。

**讨论过的方向：**
- 方案 A：保留 REC 作为正式推荐入口。
- 方案 B：recommendation 只存在系统内部；客户通过 C02 对应需求/推荐车源、C03 我的推荐等现有业务入口查看。
- 销售正式推荐后若仍需微信发送车辆，复用普通“分享车源”。

**被否决方向：**
- REC 专用链接
- REC 专用 URL 参数
- 推荐专用分享页
- recommendation 专属第二套微信分享能力

**被否决原因：** 正式推荐事实已经由 recommendation 对象完整表达，没有必要再让 URL 成为另一套业务事实源。

**用户最终确认：** 正式 recommendation 是 customer_id ↔ vehicle_id ↔ recommendation 的系统内部关系；不再使用 REC。客户通过现有推荐业务入口查看。需要微信发送时直接复用普通分享车源。

**Superseded / 禁止恢复：**
- 任何 REC 形式的推荐专用链接/参数/页面均不得因新窗口失忆恢复。

**影响业务对象：**
- recommendation
- customer
- vehicle
- demand（可选 source_demand）

**影响页面：**
- C02 帮我找车/推荐车源
- C03 我的推荐
- E01 车源雷达
- E03 客户业务历史

**其他影响：**
- API：普通分享与 recommendation 分离
- 价格权限：由 recommendation 对象授予，不依赖 URL

**简化版：** 推荐是系统里的正式业务记录，不是微信链接上的一个 REC 参数。

## 【DEC-010】

**问题：** 正式 recommendation 和普通“分享车源”是否是同一个事实？

**为什么发现：** 员工和客户都需要把车辆通过微信传播，但销售正式推荐同时承担 CRM 业务含义。

**旧规则 / 原方案：** 早期容易把“推荐”和“分享”混成一个动作，甚至想让分享链接承担 recommendation 身份。

**发现的冲突：** 微信群/朋友圈的普通传播不能自动制造正式 recommendation；正式推荐也不应该再造一套微信分享能力。

**讨论过的方向：**
- recommendation：系统内部正式业务关系。
- 普通分享车源：统一车辆传播能力，客户端/员工端共用，支持好友和朋友圈。
- 正式 recommendation 后若还要微信发送，直接复用普通分享。

**被否决方向：**
- 分享即 recommendation
- recommendation 专属分享能力
- REC 专用分享链路

**被否决原因：** 两者生命周期、权限和数据事实完全不同；混用会让来源归因、推荐历史和价格权限失真。

**用户最终确认：** 全系统只保留一套普通“分享车源”；正式 recommendation 与普通分享彻底分开。

**Superseded / 禁止恢复：**
- 不得恢复“分享即推荐”。
- 不得恢复 recommendation 专属微信分享链路。
- 不得因为普通分享创建 recommendation。

**影响业务对象：**
- recommendation
- share attribution context
- customer
- vehicle

**影响页面：**
- C01 / C01-01
- C02 / C03-02
- E01 / E02 / E03

**其他影响：**
- 普通分享支持好友/朋友圈
- 列表分享具体视觉位置留低保真

**简化版：** 分享只是把车发出去；推荐是销售正式告诉某个客户“我推荐这辆”。

**当前状态：** CLOSED

## 【DEC-011】

**问题：** 客户 B 分享车辆给 C 后，C 的 customer owner 如何计算？

**为什么发现：** 普通分享必须支持来源归因和老客转介绍，同时又不能破坏已有客户归属。

**旧规则 / 原方案：** 曾可能按“最后点击哪个分享链接”改变 customer owner，或让新客户跟随历史 owner。

**发现的冲突：** 如果普通分享能抢 owner，已有客户会被分享链接反复抢走；如果老客转介绍跟历史 owner，又会忽略已经完成的正式交接。

**讨论过的方向：**
- C 已是系统已有客户：现 owner 保持不变，只增加来源事实。
- C 是全新客户、B 是老客户：C 归 B 当前正式 owner，同时保存 B 作为来源客户/直接推荐人/转介绍链。
- B 后续从 A 转给 D：B 此后分享产生的新客户归 D，不归历史 owner A。

**最终确认：** 采用 A：只有当前 active System Admin 可管理其他 System Admin；员工角色无权管理；账号状态只保留 active/inactive，不普通物理删除；必须始终至少存在 1 个 active System Admin，停用最后一个 active Admin 必须阻止；全部变更留审计。不新增超级管理员第二层级。

**Superseded / 禁止恢复：**
- 禁止恢复：员工/经理/店长管理 System Admin
- 禁止恢复：V1 新增超级管理员/Owner 第二层级

**影响范围：** SSOT、IA、P05、P11、权限、DB/API、测试

**当前状态：** CLOSED
