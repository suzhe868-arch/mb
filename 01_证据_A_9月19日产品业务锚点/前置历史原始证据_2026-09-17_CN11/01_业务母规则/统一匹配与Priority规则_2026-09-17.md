# 统一匹配与 Priority 规则｜2026-09-17

> 本文件是 CR007 重审后的当前有效增量规则。与旧 Priority / 普通匹配描述冲突时，以本文件为准。

## 1. 总体模型

V1 只维护 **一套公共匹配引擎 + Priority 优先独占分支**。

- 普通客户与 Priority 客户使用完全相同的匹配条件和匹配等级。
- Priority 不是独立匹配系统，也不是锁车优先权。
- Priority 只是在公共匹配结果上增加：**Priority 客户优先 + 最多 24 小时的销售端独占窗口**。

## 2. Priority 客户资格

- Priority 资格是 Customer 级长期属性，不属于某一条 Demand。
- 仅 System Admin 主账号域可以对单个客户开启/取消，不支持批量。
- 不要求填写原因；系统自动记录操作人、动作与时间。
- 资格默认长期有效，直到 System Admin 主动取消。
- 资格本身不阻止进入公海；真正的 active Demand / active Priority / Lock / Transaction 等业务关系才构成公海保护。
- 客户进入公海后 Priority 资格保留；没有负责销售时不得产生车辆级 Priority。

## 3. 公共匹配规则

### 3.1 匹配等级

- `high`：已填写的硬条件全部明确满足；客户展示价不超过预算；已填写的内饰颜色偏好也满足。
- `acceptable`：硬条件满足，但客户展示价高于预算且不超过 5%，或内饰颜色偏好不满足。
- `confirmation_needed`：客户已填写某个硬条件，但车辆对应数据缺失或无法确定。
- `no_match`：任一硬条件明确不满足；或客户展示价超过预算 5%；或车辆没有可用客户展示价、只能“价格咨询”。

`high > acceptable`。`confirmation_needed` 不产生 Priority、不阻断其他客户匹配。

### 3.2 条件语义

- 同一字段多选：OR。
- 不同字段之间：AND。
- 客户未填写某条件：该项不限。
- 年款：按最低可接受年款；更新年款仍符合。
- 里程：核心按最高可接受里程；低于填写的最低里程仍可符合。
- 预算：使用**客户当前实际展示价**；默认允许上浮 5%，该比例为全局配置。
- 外观颜色：硬条件，可多选。
- 排量：硬条件，可范围/多选。
- 动力类型：硬条件，可多选。
- 车况排除要求：硬条件。
- 内饰颜色：软偏好。
- 变速箱、配置偏好、过户次数、城市/距离、排放标准、车源类型：不参与 V1 自动匹配判定。

## 4. Priority 触发与仲裁

车辆必须同时满足：

- 当前可售、当前 listing cycle 有效；
- 无 active Lock；
- 无 in-progress Transaction；
- 存在 active Demand；
- Priority 客户已绑定有效负责销售；
- 最终匹配等级为 `high` 或 `acceptable`。

匹配流程：

1. 先跑全部客户的公共匹配。
2. 若存在符合的 Priority 客户，普通客户暂不获得该车的新推荐。
3. 同一客户多条 Demand 命中同车时，先选最佳 `trigger_demand_id`；跨客户候选中该客户只出现一次。
4. 多个 Priority 客户同时符合时：`high > acceptable → Demand created_at 更早 → demand_id 更小`。
5. 若没有符合的 Priority 客户，则完全进入原普通匹配流程；普通客户可同时获得同一车辆的推荐。

Priority 客户之间没有等级；一个客户可同时拥有多辆车的 active Priority，不设数量上限；同一车辆同一时刻最多 1 个 active Priority。

## 5. Priority 生命周期

- 默认 TTL：24 小时（86400 秒），仅 System Admin 修改全局默认值。
- 创建时固化 TTL 快照；后续配置变化不影响既有 Priority。
- 不提供人工续期。
- 状态只保留：`active / ended`。
- 结束原因单独记录，至少包括：
  - `abandoned_before_recommendation`
  - `recommendation_cancelled`
  - `expired`
  - `converted_to_lock`
  - `vehicle_unavailable`
  - `demand_inactive`
  - `priority_customer_disabled`
  - `match_invalidated`

同一 `listing_cycle` 内，某客户因放弃/取消/过期结束过该车 Priority 后，不得再次**自动**获得同车 Priority；新的 listing cycle 重新计算。销售主动重新推荐时仍必须重新通过当前匹配条件与车辆状态校验，不能直接人工制造 Priority。

## 6. Priority 与 Demand

- Priority 资格来自 Customer；Demand 只记录本次匹配原因。
- Priority 保存 `trigger_demand_id`，且必须属于同一 `customer_id`。
- 若触发 Demand 失效，先检查同一客户其他 active Demand：
  - 仍有符合 Demand：切换 `trigger_demand_id`，原 `expires_at` 不变；
  - 没有符合 Demand：结束 Priority。
- 车辆、价格或 Demand 的关键匹配字段变化时立即重新判定；变成 `confirmation_needed` 或 `no_match` 时结束独占。

## 7. 可见性

### Priority 尚未正式推荐

- 客户本人：不可见。
- 负责销售：可见。
- 具备 `priority.view` 的 Employee：在原组织/数据范围内可见。
- 其他客户、普通销售、旧推荐链接、历史链接、分享链接：不得穿透。

### 销售正式 Recommendation 后

- 对应客户获得该车辆客户端可见权。
- Priority 独占仍持续到自身结束条件，不重新计时。
- 其他客户与普通销售仍受 Priority 隔离。

`priority.view` 仅是穿透查看能力，不授予推荐、锁车、成交或修改车辆权限。

## 8. Priority 与 Recommendation

- Priority 创建时**不自动创建正式 Recommendation**。
- 销售判断合适后，走原正式 Recommendation 流程；此时可将 `recommendation_id` 回填到 Priority。
- Priority 与 Recommendation 不是同生命周期：Priority 可以没有 Recommendation，Recommendation 可以在 Priority 结束后继续存在。
- Priority 到期只结束独占保护；已经正式发出的 Recommendation 继续有效、客户继续可见。
- 其他客户后续取得新 Priority 时，旧 active Recommendation 不删除，只暂时被 Priority 可见性压制；新 Priority 结束且车辆仍可售、Recommendation 仍 active 时恢复可见。
- 销售取消 Recommendation 不反向撤销已有 Lock / Transaction。
- 车辆进入 Transaction / 成交，或车辆下架、外部售出、管理员隐藏/不可售时，相关未结束 Recommendation 自动结束并记录原因。
- 新 listing cycle 不恢复旧 Recommendation。

## 9. Priority 与 Lock / Transaction

- Priority 不是 Lock 竞争条件。
- Lock 创建不读取“别人是否有 Priority”作为额外拒绝原因；能到达 Lock 动作的前提由可见性和原权限/数据范围保证。
- 车辆已有 active Lock 或 in-progress Transaction 时不得新建 Priority。
- Priority 客户成功 Lock：Priority 以 `converted_to_lock` 结束。
- Lock 后续取消/过期：旧 Priority 不恢复；若 Recommendation 仍 active，原客户仍可见，但不再享有独占。

## 10. 释放与重新匹配

Priority 结束后，只要车辆仍开放且无 Lock / Transaction：

- 车辆恢复普通开放状态；
- 重新匹配**所有有效客户 Demand**，不是只匹配 Priority 客户；
- 若新的候选中存在 Priority 客户，再按本文件的 Priority 仲裁产生新的独占；
- 否则走原普通客户并行推荐流程。

## 11. 公海与交接

- active Priority 属于公海保护条件。
- Priority 客户资格本身不属于保护条件。
- 客户正常移交或负责销售离职时，active Priority 不取消，随客户业务关系交接；新负责销售取得业务可见范围，原销售失去当前权限。

## 12. 权限最小化

- 删除 `priority.override` 及“人工转让/覆盖 Priority”的设计。
- 不提供人工创建 Priority API。
- 仅保留 `priority.view` 作为 Employee 的敏感穿透查看权限。
- System Admin 的客户 Priority 资格开关属于 System Admin 域，不复用 Employee `priority.view`。
- 销售放弃、正式推荐、取消推荐继续复用现有匹配/Recommendation 业务权限与责任范围，不新增复杂 `priority.manage` 体系。

## 13. 触发事件

以下事件触发重新匹配或 Priority 重算：

- 新车辆进入可售状态；
- 车辆关键匹配字段/客户展示价变化；
- 新建或修改 active Demand；
- Demand 状态变化；
- System Admin 开启 Priority 客户资格（立即扫描该客户全部 active Demand × 当前可售车辆）；
- 客户重新绑定负责销售；
- Priority 释放/到期；
- Lock 结束且车辆重新开放。

系统应事件驱动；定时任务只做过期兜底，不作为唯一匹配触发方式。
