# 1. V1 产品目标与总体架构

名邦汽车 V1 的核心成交链：

**车源进入 → 客户看车/提交找车申请 → 找车权益判断/开通 → 正式 demand → 销售整理匹配描述 → 词典/确定性规则标准化 → 结构化条件匹配 → 车源雷达 → 销售推荐 → 客户咨询/明确车辆意向 → 锁车 → 意向金记录（如有）→ 交易 → 成交/取消 → CRM 与历史数据沉淀**

V1 产品端收敛为：

1. **客户微信小程序**
2. **统一员工/销售端小程序**
3. **PC 管理后台**

外部技术服务：

4. **金鱼塘采集/检测程序**：外部独立运行，通过名邦固定 API 与名邦后端通信，不直接写数据库。

辅助触达：

5. **飞书**：员工重要主动提醒。
6. **微信服务号**：作为客户触达/回流辅助能力，不复制 CRM/车源主数据；能力受微信当期接口限制。

# 2. 账号、角色与权限模型

## 2.1 账号体系

### 客户账号
- 微信客户账号。
- 可浏览、找车、收藏、咨询、查看自己的需求/推荐/交易相关信息。
- 微信身份稳定映射 `customer_id`；头像、昵称、手机号均不是客户唯一身份主键。
- 不同 `customer_id` 即使手机号相同也不得自动合并；V1 不建设复杂客户合并功能。
- 同一微信客户更换手机号时继续使用原 `customer_id`，只更新当前联系电话并保留必要修改历史；不得改变 owner、权益或已有业务。
- 正式客户业务档案不提供普通物理删除能力；账号注销、隐私处理、测试/垃圾数据清理由独立合规/高权限数据治理处理。

### 员工账号
统一员工/销售端账号体系包含：
- 普通销售
- 经理
- 店长
- 4S 成员

4S 成员不再维护独立“4S 端”业务系统。

员工账号必须保留在职/离职等任职状态；员工离职后账号与历史业务关系不得物理删除。离职只改变当前任职/接客能力，并触发客户交接流程，不能抹除历史贡献与责任记录。

员工身份连续性：
- 同一现实员工离职后重新入职，确认身份一致时复用原 `employee_id`，不创建第二个员工身份；
- 重新入职只恢复员工身份，不自动拿回离职时已经完成交接的客户或活跃业务；
- 普通销售/经理/店长/4S成员之间角色变化继续使用同一 `employee_id`；当前角色、权限点和数据范围变化不得改写历史操作时的角色/责任事实；
- 若角色变更会使员工失去当前客户/活跃业务的处理资格，必须先完成对应交接，再使该角色变化正式生效；
- 4S成员转为名邦销售或反向变化，不自动改变其历史上传车辆的来源类别。

### System Admin
- **System Admin 与员工账号完全分开建模。**
- System Admin 不属于销售/经理/店长/4S 成员角色树。
- 不进入自动接客池，不承担客户归属、锁车、交易等日常销售业务。
- 同一个真人如既管系统又卖车，应拥有两个独立身份/账号：System Admin 后台账号 + 员工/销售业务账号。
- System Admin 账号只由**当前有效的 System Admin** 管理；普通员工、经理、店长、4S 成员均无权新增、停用或修改 System Admin。
- System Admin 账号状态只保留 `active / inactive`；不提供普通物理删除。
- 系统必须始终至少保留 1 个 `active` System Admin；停用最后一个有效 System Admin 的操作必须被阻止。
- System Admin 的新增、权限/状态修改、停用等操作必须完整留审计。

## 2.2 权限模型

统一采用：

**角色默认权限 + 独立权限点 + 数据范围 + 对象状态**

“进入某个页面/内部模式”不等于获得业务权限。

至少以下能力为独立敏感权限点：
- 查看内部价格
- 查看批发车源电话
- 单车客户展示价覆盖
- 一键转名邦
- 修改客户等级
- 编辑非本人车辆
- 调价
- 上下架
- 其他后续敏感业务能力

前端权限只负责“显示什么”；后端必须再次校验“能不能读/能不能执行”。

## 2.3 经理/店长数据范围与个人销售身份

- 经理不是只管理某几个销售的客户。
- 经理在其门店/授权团队数据范围内，按权限管理客户、需求、咨询、推荐、锁车、交易、名邦车源及允许管理的 4S/批发业务。
- 店长默认覆盖本店数据范围，仍受具体敏感权限点控制。
- **经理、店长仍保留个人销售身份，可以拥有并管理自己的正式客户，也可以成为客户正式负责人、找车需求负责人、咨询负责人或交易负责人。**
- 角色决定管理范围，不取消个人销售身份。
- 经理、店长是否参加自然新客户自动分配，由个人“开启接客”状态决定。

## 2.4 4S 成员

默认可以：
- 浏览平台允许其浏览的车源；
- 查看被授权可看的价格；
- 上传 4S 合作车源；
- 编辑、调价、上下架自己上传的 4S 车源。

默认不能：
- 管理名邦客户 CRM；
- 修改客户归属；
- 管理公海；
- 查看/处理名邦客户咨询；
- 管理找车需求；
- 代表名邦客户推荐、锁车、交易；
- 修改其他人上传的 4S 车源。

批发电话、内部敏感价格等能力继续由后台独立权限控制。


## 2.5 客户微信身份、个人资料与手机号服务门槛

客户进入名邦小程序后，通过微信身份建立并识别名邦客户账号。系统持续以：

**微信身份 → `customer_id`**

识别同一个客户后续的浏览、收藏、回访、找车、咨询、候补、交易等业务行为。

必须分开理解：
- **微信身份**：用于建立客户账号、识别同一客户和维持登录态；
- **手机号**：用于 CRM 联系以及需要销售人工服务的高意向业务；
- **客户昵称/称呼、头像**：属于客户个人资料和展示信息。

头像、昵称、手机号都不是客户唯一身份主键。

### 头像和昵称：持续引导完善，但不强制
头像/昵称采用用户主动选择/填写，不得理解为系统后台静默读取：
- 头像由客户主动选择微信头像或按微信当期能力完成选择；
- 昵称由客户主动填写/选择；
- 业务字段统一称“客户昵称/称呼”，不把业务模型永久绑定为某个微信平台字段。

统一资料完善提示文案：

**“完善头像和昵称，方便后续为您提供更顺畅的服务。”**

不得使用“方便顾问识别您”“让销售知道您是谁”“方便识别您的微信身份”等容易产生被监控/被识别感的文案。

客户未完善头像昵称时，仍可正常：
- 进入小程序；
- 浏览车辆；
- 搜索/筛选；
- 查看车辆详情；
- 收藏车辆。

### 首次进入小程序的资料完善提示
客户首次进入流程：

**建立微信身份 → 检查头像/昵称 → 未完善则显示资料完善提示 → 客户可完善或关闭/暂时跳过 → 正常进入小程序。**

推荐主按钮文案：**“使用微信头像和昵称”**。

必须同时允许：
- 关闭；
- 暂时跳过。

客户选择完善后：
- 引导选择头像；
- 引导填写/选择昵称；
- 保存到客户个人资料；
- 后续可在“我的 → 个人资料”修改。

客户关闭/跳过后不影响任何普通浏览能力；后续可在适当业务节点继续轻量提醒。

### 收藏车辆与资料完善
收藏属于低门槛行为：

**客户点击收藏 → 收藏立即成功。**

收藏本身：
- 不要求手机号；
- 不强制头像/昵称；
- 不得因客户拒绝资料完善而撤销已经成功的收藏。

如果头像或昵称仍未完善，收藏成功后可再次使用统一资料完善提示，并提供“去完善 / 稍后或关闭”。

资料完善主动提醒必须频控：
- 同一客户头像/昵称未完善时，**每天最多主动提醒 1 次**；
- 客户资料已经完善后停止此类主动提醒；
- 客户主动进入“我的 → 个人资料”不受该主动提醒频控限制。

### 手机号采用“业务触发时授权”
原则：**手机号是人工服务门槛，不是浏览门槛。**

以下行为不要求手机号：
- 进入小程序；
- 浏览车辆；
- 搜索/筛选；
- 查看详情；
- 收藏。

第一次执行需要销售人工跟进的高意向动作时检查手机号，至少包括：
- “我要这辆车”；
- 登记候补；
- 提交帮我找车；
- 联系/咨询顾问；
- 后续其他明确需要人工服务的动作。

统一流程：

**客户点击业务动作 → 检查手机号 → 已有则直接继续 → 无手机号则触发微信手机号授权 → 授权成功保存手机号 → 自动继续原业务动作。**

不得要求客户授权成功后重新点击一次原按钮。

头像/昵称即使仍未完善，也不能阻断上述高意向动作；手机号授权并成功提交业务后，可以继续使用统一资料完善提示，但客户拒绝完善头像/昵称不得影响已经创建的业务对象。

### 客户拒绝手机号授权
客户拒绝手机号授权时：
- 不创建“我要这辆车”对应的明确车辆意向/咨询；
- 不创建候补；
- 不提交正式帮我找车申请/意向；
- 不进入需要人工顾问处理的咨询；
- 停留当前页面；
- 仍可继续浏览和收藏。

V1 **不新增“手机号授权失败/拒绝后持久化保存找车表单草稿”的产品要求**，也不为此建立独立草稿业务对象；拒绝授权时只按上述规则不创建正式人工服务对象。具体页面临时输入状态由前端交互自然处理，不把“失败后持久化保存”作为产品能力或审核相关依赖。


最终分层原则：
- **微信身份负责识别客户是谁；**
- **头像和昵称负责完善客户资料，持续引导但不强制；**
- **手机号负责建立现实中的人工联系方式，只在需要人工服务时强制。**

# 3. 三类车源与车源归属

V1 统一车源池包含：

1. **批发车源**
   - 来源：金鱼塘（JYT）外部采集程序。
   - 不在名邦后台人工新建。
2. **名邦车源**
   - 名邦员工人工上传/由批发车一键转名邦产生。
3. **4S 合作车源**
   - 4S 成员人工上传，或名邦销售上传时选择“发布到 4S 合作资源”。

重要规则：
- 金鱼塘“保障金车源”仅作为上游属性，不映射成 4S 合作车源。
- 名邦销售上传可选择“名邦车源 / 4S 合作资源”，选择 4S 合作资源时不要求指定某一家 4S 店。
- 4S 成员不强制绑定具体 4S 门店，自己上传的车辆以 `created_by` 等所有权信息控制编辑权限。
- 名邦销售上传的名邦车辆属于公司/平台资产，不属于销售个人资产；保留创建人和修改历史。
- 正常业务车源不物理删除；测试/错误/垃圾数据仅由高权限管理员按清理规则处理。

---
补充冻结：
- 人工车在草稿阶段可修改“名邦车源 / 4S合作资源”发布目标；第一次正式发布成功后，来源类别属于 provenance，不作为普通编辑字段自由切换；确属录入错误只能由有权限人员按数据纠错留痕修正。
- 人工车 VIN 仍为可选字段；若正式发布时填写的 VIN 与另一条现存名邦/4S人工车辆 VIN 完全一致，普通发布应阻止明显重复并提示检查已有车辆；纯草稿仍可保存。不得用“车型+年份+里程相似”自动猜测去重。
- 不同来源即使疑似同一真实车辆也不自动合并 vehicle_id；重复曝光由人工隐藏/下架其中一条。批发→名邦的唯一正式转换关系仍是一键转名邦 conversion relation。


# 4. 金鱼塘接入与 API

## 4.1 外部程序职责

金鱼塘采集/检测程序运行在外部独立程序/机器，负责：
- 采集新增/更新车源；
- 从名邦获取当前在售批发车源标识；
- 检测这些车辆在金鱼塘是否仍有效；
- 把确认下架的车辆回传给名邦。

名邦后台服务器不负责逐台访问金鱼塘进行下架检测。

## 4.2 禁止直写数据库

旧方案“外部采集程序直接 INSERT / UPDATE 名邦数据库”正式废弃。

统一链路：

**金鱼塘 → 外部采集/检测程序 → 名邦固定 API → 名邦后端业务层 → 数据库**

外部程序不得持有名邦数据库账号。

## 4.3 固定三个车源同步业务 API

后台位置：

**车源管理 → 金鱼塘同步 / API 管理**

V1 对“外部采集/检测程序提交或获取车源数据”固定三个业务接口：

### A. 新增/更新车源 API
外部程序提交完整车辆资料。

后端按金鱼塘业务键判断：
- 不存在 → 新增；
- 已存在 → 更新；
- 价格变化 → 更新当前价格并记录价格历史；
- 原已下架、再次有效 → 同车重新上架并创建新的 `listing_cycle`。

### B. 批量下架 API
外部检测程序批量提交已确认失效的 `car_code`：
- 名邦按键批量标记上游下架；
- 不物理删除；
- 若车辆正在锁车/交易：标记供应异常，但**不得自动取消锁车或交易**。

### C. 获取当前在售批发车源 API
供外部检测程序获取名邦数据库当前仍在售的金鱼塘车辆标识。

V1 简化：
- 一次全量返回当前在售列表；
- 当前 1 万～几万规模不做分页；
- 后续规模显著扩大再增加分页/增量。

边界说明：原“授权程序提交金鱼塘上游登录 Token”方案已由 CR007 Collector 架构废弃。车源同步仍固定三个业务 API；JYT 凭证由 Collector 自行管理，不进入名邦 API/后台。

## 4.4 唯一性与幂等

名邦内部车辆主键：
- `vehicle_id`

金鱼塘上游幂等唯一：
- **`(source_platform, car_code)`**

不得因同一金鱼塘车辆改价/更新而生成第二辆重复批发车。

同一 `car_code` 下架后再次有效：
- 仍是同一 `vehicle_id`；
- 新建新的 `listing_cycle`；
- 保留历次上架、下架、价格变化和累计在售历史。

## 4.5 鉴权、开关、日志

V1：
- 一套名邦车源同步 API Token/API Key（外部采集/同步程序调用名邦三个固定车源 API；不是 JYT 上游登录 Token）；
- 三个车源同步业务接口分别具有独立启停开关；
- 不给外部程序数据库账号。

轻量 API 日志至少记录：
- 调用时间
- 接口名
- 成功/失败
- 提交/返回/处理数量
- 新增数
- 更新数
- 改价数
- 下架数
- 耗时
- 错误摘要

不建设复杂运维/调度中心。

## 4.6 上游字段白名单

- 员工备注
- 名邦人工档案
- 已转名邦关系

# 5. 图片架构（2026-09-17 图片模块重审冻结）

> 图片模块当前权威规则以 `15_CHANGE_CONTROL/CR-007/图片模块重审_2026-09-17/02_图片模块_Decision_Register.md` 为准。与本节以前版本冲突的图片规则仅在图片模块范围内被本轮结论覆盖；`TO_VERIFY / ENGINEERING WORK` 不代表已经实现。

## 5.1 普通金鱼塘批发车：首次快照 + 首图本地化

- 上游车辆首次入库时读取当次 `images[]`，把图片身份、首次 `upstream_url` 与原始顺序写入名邦数据库；该集合形成**首次冻结快照**。
- 后续上游新增图片、删除图片、换链接或调整排序，不再重新同步整车图片集合；单个冻结 URL 后续失效只按单图失败/恢复规则处理。
- 批发车首次入库即尝试把原始排序第一张图片本地化到**名邦服务端对象存储/CDN**；第一张失败则依原始顺序继续尝试后面的图片，直到取得第一张可用本地图作为列表封面。
- fallback 只改变当前展示封面，不修改数据库原始图片顺序；原第一张以后成功本地化时恢复为首图。
- 全部图片失败或上游 0 图都不阻塞车辆入库、匹配或销售；无可用图时使用统一默认占位图。
- 客户端不直接暴露上游地址或对象存储内部地址；统一经名邦受控 HTTPS/CDN 地址访问。

## 5.2 批发车其余图片：按需吞图

- 除列表封面外，其余图片默认只保存首次冻结 URL，不做全量预下载。
- 第一次进入详情时：列表封面已在本地，处理第 2、3 张并预取第 4 张；继续滑动时维持前方约 2 张的预加载窗口。
- 图片进入真实展示/预加载窗口时才触发回源；第一次回源成功的同一份响应数据同时用于当前 viewer 返回和服务端对象存储持久化，不要求客户等待“先落盘再重新请求”。
- **已吞图**只在“对象存储成功 + 数据库有效 `local_object_key` 写入成功”同时成立时成立；之后正常展示永久本地优先，不再访问上游 URL。
- 客户已看到但持久化失败时，本次展示不回滚，图片仍视为未吞；对象存储成功而 DB 最终失败时必须删除刚保存的对象，避免孤儿文件。
- 单图单轮最多自动尝试 3 次并退避；3 次仍失败则本轮停止，后续该图再次被真实查看可开始新一轮。
- 失败图片暂不占详情可见图集位置，但来源记录和原始排序保留；未来成功后按原始位置恢复。
- 同一图片同一时刻只有一个真实下载任务（single-flight）；不同图片可并行，单车同时最多 3 个吞图任务，其余排队。
- 已吞本地图只有在确认名邦本地对象损坏、丢失或 404 时，才允许使用保留的首次 `upstream_url` 做一次受控自愈；不得因此重新同步整车图片集合。

## 5.3 上下架与图片资产

- `visible/hidden`、下架、售出或其他车辆销售状态变化不重置图片资产状态。
- 已吞本地图作为名邦服务端资产保留；未吞图保留首次冻结 URL。
- 下架期间不主动继续吞图；重新上架后复用已有本地图，未吞图继续原按需逻辑。
- 图片增删、吞图、本地化或恢复均不新建 listing_cycle。

## 5.4 一键转名邦

授权人员执行“一键转名邦”后：

1. 创建独立名邦车辆（新的 `vehicle_id`）并建立永久 conversion relation；
2. 车辆创建成功与图片迁移结果解耦，图片问题不得回滚已经创建成功的新名邦车；
3. 原批发车已吞成功的物理图片**不复制、不重新下载**，其业务所有权转给新名邦车；原批发车只保留 `upstream_image_id / upstream_url / 原始排序` 等来源历史，不继续持有对应 `local_object_key`；
4. 正在吞的图片复用现有 single-flight 任务；尚未本地化的图片才进入转换阶段的迁移；
5. 图片保持首次批发快照原始顺序；已成功图片立即可用，失败图片不占可见位置；全部不可用时使用占位图；
6. 转换后新名邦车彻底进入普通人工名邦车图片生命周期，可新增、删除、排序；删图删除其业务图片记录与对应物理对象，不回写原批发车。

转换结果语义：

- `success`：车辆创建成功且目标图片全部完成本地化；
- `partial_failed`：车辆创建成功，但存在部分图片未迁成功；
- `failed`：车辆本身转换失败，未创建新名邦车。

转换图片失败不建立复杂的失败图片人工重跑/无限重试工作流；车辆已经成功创建后，缺失图片由销售按普通名邦车方式手工上传补齐。

原有价格映射、`biz_status=normal` 转换前置条件、幂等、原批发隐藏、新名邦初始可见性、favorites/recommendation 历史不迁移等非图片业务规则保持不变。

## 5.5 名邦/4S 人工上传图片

- 人工车辆允许 0 张图片先发布；也允许 0 张真实图片正式发布。0 图使用统一默认占位图，图片不是发布硬条件。
- 上传成功后图片立即属于名邦正式服务端本地图，不存在“未吞图”。
- 正式发布后仍可补图、删图、拖动排序；删除首图后剩余排序第一张自动成为新首图；删除到 0 图不影响车辆继续在售。
- 批发采集图片原始排序不可人工修改。
- 业务层不设固定图片数量、单图大小或格式上限；只保留防止非图片内容、危险内容或资源滥用所需的技术安全校验。

## 5.6 本地定义、内容去重与访问权限

- “本地/已吞”统一指**名邦服务端对象存储/CDN**，不是客户手机或微信客户端缓存；所有客户和员工共享已经服务端本地化的资产。
- `content_hash` 只用于内容校验、防重复判断和幂等辅助，不形成跨车辆长期共享同一个物理对象的业务生命周期。
- 数据库存内部对象标识（如 `local_object_key`）；客户端/员工端只能获得名邦受控 HTTPS/CDN 地址。
- 图片访问不得绕过车辆查看权限；hidden、Priority、Recommendation、Lock/Transaction 等车辆可见性规则继续由 Vehicle Read/Visibility 决定。
- 短时签名 URL、CDN Token、代理实现方式和具体时长属于工程实现细节，不在产品规则中写死。

# 6. 车源状态与生命周期

V1 不使用一个巨大 `vehicle_status` 同时表达所有事实。

至少分开：

## 6.1 上游/资源事实状态
例如：
- 批发：`active / offline`
- 人工资源：`available / unavailable / sold_external`

## 6.2 名邦平台展示状态
- `visible`
- `hidden`

`platform_visibility = hidden` 只表示名邦客户实时展示被暂停，不等于资源已失效：
- 不修改上游/人工资源事实状态；
- 不创建新的 listing_cycle，恢复 visible 也不创建新 listing_cycle；
- 收藏关系和业务历史继续保留；客户公开 Feed、公开搜索和普通分享不得暴露 hidden 车辆；
- `hidden` 不退出统一 Matching Engine：只要 `source_status=active`、`biz_status=normal` 且无有效 Lock/进行中 Transaction，普通 Demand 与 Priority Demand 都可以继续匹配；
- hidden 车辆被正式 Recommendation 给目标客户后，系统在同一事务内自动建立 Recommendation 来源的 customer visibility grant；该客户可查看详情，其他客户仍不可见；Priority 本身不创建客户可见性；
- Recommendation 结束时结束其 grant，但不得因此取消已有 Lock/Transaction；已有业务关系继续保留必要详情访问；
- 有权限员工/PC 仍可按数据范围查看和管理。

## 6.3 名邦业务状态
核心：
- `normal`
- `locked`
- `trading`
- `completed`

## 6.4 供应异常
采用独立标记/异常记录，不再使用“供应异常待确认”人工状态。

系统发现已锁车/交易车辆出现：
- 上游下架
- 4S 撤回
- 重大价格变化
- 重大车况变化
- 其他供应风险

则：
- 自动标记供应异常；
- 自动通知对应销售；
- **不需要人工确认异常按钮**；
- **不自动取消锁车/交易**；
- 不删除意向金；
- 不覆盖原锁车价格快照。

供应异常解除继续采用确定性自动规则：
- 系统能够明确确认原风险事实已经恢复时，自动清除“当前供应异常”标记；
- 无法确定风险已经恢复时，当前异常继续保留，不允许系统猜测性关闭；
- 相关 lock / transaction 已经结束后，不再作为“当前进行中业务异常”持续展示，但异常历史永久保留；
- V1 不增加人工“确认异常 / 标记已解决”业务流程。

## 6.5 listing_cycle 与重新上架

`listing_cycle` 只在车辆经历**真实不可售/失效 → 再次真实可售**时新建。普通编辑、改价、里程/车况/图片变化、平台 hidden/visible 不新建。

开始时间优先级：
1. 能获得可信的真实本次上架/重新上架时间 → 使用该时间；
2. 无可靠时间 → 使用名邦首次检测到本轮从不可售变为可售的时间；
3. 人工名邦/4S车辆以正式“发布/重新上架”成功时间为本轮开始时间。

批发车：同一 `(source_platform, car_code)` 重新有效时仍为同一 `vehicle_id`，新建 listing_cycle。
人工名邦/4S车：确认是同一真实车辆重新可售时复用原 `vehicle_id`，新建 listing_cycle，不重复建车。

收藏关系按 customer + vehicle_id 保存，因此真实同车重新上架仍保持收藏；旧推荐、旧锁车/交易等继续作为历史，不迁移为新周期业务。

## 6.6 一键转名邦后的原批发车
原批发记录：
- 继续允许接收金鱼塘后续 API 更新，仅用于维护上游历史；
- `platform_visibility = hidden`；
- 标记“已转名邦”；
- 后续金鱼塘再次上架不得自动恢复客户展示；
- 不得覆盖已经生成的独立名邦车辆；
- 与新名邦车辆通过永久 conversion relation 连接，但两个对象始终是不同 `vehicle_id`。

## 6.7 人工车上下架
名邦/4S车辆：
- 可先发布、后补资料；外部已售 ≠ 名邦成交；名邦真实成交必须由内部交易完成产生；
- 正常业务历史不物理删除。

人工“下架”必须区分：
1. **暂停展示**：资源仍真实可售，仅 `platform_visibility = hidden`；不结束当前 listing_cycle，恢复展示仍为原周期。
2. **资源已失效**：如 4S 撤回、不再出售、外部已售，写 `source_status = unavailable / sold_external`，结束当前 listing_cycle；以后真实重新可售才开启新 listing_cycle。

从未正式发布、从未产生 listing_cycle 且无任何正式业务关系的纯草稿，可由创建人或有权限管理者物理删除；第一次正式发布后进入不可物理删除边界。

# 7. 批发价格与客户价格权限

## 7.1 原始价格数据与基础价格回退

金鱼塘批发车保留：
- `upstream_list_price`
- `upstream_wholesale_price`
- `base_wholesale_price`

V1 基础价格回退规则正式冻结：
1. 有 `upstream_wholesale_price` → `base_wholesale_price = upstream_wholesale_price`；
2. 无 `upstream_wholesale_price`，但有 `upstream_list_price` → `base_wholesale_price = upstream_list_price`；
3. 两者都没有 → 不生成明确客户展示价，客户侧显示“价格咨询”。

原始字段始终按来源原样保存，不因回退逻辑互相覆盖或改写。金鱼塘 `price_label` 永远表示上游标价：原文写入 `upstream_list_price_label`，解析金额写入 `upstream_list_price_cents`；它不会被重命名或覆盖成真实批发价。真实批发价只使用 `upstream_wholesale_price_cents`，基础批发价按 `COALESCE(upstream_wholesale_price_cents, upstream_list_price_cents)` 派生。

## 7.2 客户展示价

批发车可由后台配置统一客户加价规则。

系统保留：
- 上游原始标价
- 上游原始批发价
- 系统规则计算展示价
- 单车覆盖价（如有）
- 最终客户展示价
- 价格历史

### 统一阶梯加价的有效性边界
- 启用中的阶梯规则不得出现价格区间重叠；
- 一套准备正式启用的阶梯规则必须完整覆盖其声明允许的 `base_wholesale_price` 范围；存在空档时后台禁止启用并明确提示配置缺口；
- 如果当前系统**完全没有任何有效启用的客户加价规则**，且该车又没有单车覆盖价，则批发车客户侧统一显示“价格咨询”，不得直接把 `base_wholesale_price` 当客户展示价暴露；
- 单车覆盖价继续拥有最高优先级。

### 单车客户展示价覆盖
V1 保留。

优先级：
**单车覆盖价 > 统一阶梯加价计算结果 > 其他客户展示逻辑**

单车覆盖价只改变客户展示价：
- 不修改上游原始标价；
- 不修改上游原始批发价；
- 不篡改历史。

权限：
- 独立权限点；
- 后台可按角色/具体员工账号授权；
- 普通销售/店员也可以被授权；
- 无权限者前端不显示入口，后端拒绝执行；
- 所有操作记录原规则价、覆盖价、操作人、时间、原因、历史；
- 可恢复按统一规则计算。

## 7.3 名邦/4S价格

人工车源可以保存：
- 客户标价
- 内部批发价（可为空）

客户标价为空：
- 客户端显示“价格咨询”。

**有没有内部批发价都允许锁车。**

名邦/4S不参加金鱼塘批发车的统一阶梯加价规则。

## 7.4 服务费/预计到手价体系

V1 **彻底取消**以下整套体系：
- 服务费
- 物流费报价
- 检测费报价
- 过户费报价
- 其他费用报价
- 预计到手价/到手价测算
- 后台费用规则
- 锁车费用快照

客户侧核心价格只保留当前有效车辆展示价。
成交时记录实际车辆成交价。

## 7.5 批发车客户查价权限

批发车价格查看采用 customer + vehicle + listing_cycle 权限/额度体系：
- 每日允许解锁若干“新的批发车辆”，基础额度由后台配置；
- 同一车辆当前 listing_cycle 成功解锁后，本周期后续重复查看、改价、覆盖价变化均不重复消耗；
- 真实重新上架进入新 listing_cycle 后需要新的授权；
- 收藏、普通分享均不能绕过查价额度；
- **正式 recommendation** 会授予该客户该车当前 listing_cycle 的价格查看权限，不消耗每日额度；recommendation 的推荐销售、客户 owner、demand 负责人后来变化或离职，不撤销已经取得的本周期权限；
- recommendation 发生时若车辆为“价格咨询”，也立即授予本周期价格授权；本周期后续出现数字价格时可直接查看，无需再消耗额度；
- 老 listing_cycle 的 recommendation/解锁权限不得泄露新 listing_cycle 的受保护当前价格；历史推荐可以保留推荐时不可变价格快照，但当前价仍按当前周期权限判断。

销售临时增加当天查价次数：
- 加的是 customer-day quota 事实，不属于某个销售个人；同日 owner 变化、原销售关闭接客或离职都不撤销；
- 次日临时增加失效，重新按当日当前基础/等级规则计算；有权限的新 owner 可继续追加。

当天基础额度/等级权益被调低时不追缴已经解锁车辆，不重新锁回；剩余额度公式：
`remaining = max(0, current_today_base_quota + today_temp_additions - today_consumed_new_vehicle_unlocks)`。

客户等级可以承载每日查价额度/权益，但不得改变车辆价格计算公式，不形成“不同等级同车不同售价”。

误成交被纠正且确认恢复的是原 listing_cycle 时，原周期查价权限继续有效，不再次消耗额度。

推荐记录至少保留推荐时价格快照；锁车保留锁车时客户有效展示价快照，后续任何价格变化不得覆盖历史快照。

# 8. 客户注册、归属与转介绍

## 8.1 客户正式归属唯一

一个客户同一时间只能有一个正式归属销售：`customer_owner_sales_id`。

更换归属时：
- 只直接改变 customer owner，历史归属永久保留；客户来源、推荐人和历史服务贡献不覆盖；
- 普通 owner 变化**不自动改写**已有 active demand、pending/processing consultation、当前候补、当前 lock、进行中 transaction 等已固化业务负责人；确需转交时对具体活跃业务执行正式 reassignment 并留历史；
- 离职/失去业务资格属于特殊交接场景，必须同步检查并处理活跃业务负责人。

客户完整业务历史属于公司客户档案：新 owner 在正常数据范围内可查看必要历史；原销售以后是否可看，由其当前角色、权限点和数据范围决定，不因“历史上服务过”自动永久拥有访问权。

## 8.2 新客户分配优先级

1. 已有客户：保持现有正式归属，不因点击其他销售分享链接而改变。
2. 新客户通过在职且有资格的销售分享进入：归该销售；历史分享者已离职/无资格时只保留来源归因，当前 owner 从合格接客池产生。
3. 新客户通过老客户分享进入：优先归老客户当前正式 owner；同时保存直接推荐人/推荐链。
4. 自然注册：在“在职 + 开启接客 + 具备名邦客户业务资格”的员工池内轮询分配；普通销售、经理、店长可按个人接客状态参与，4S成员默认不参与。

接客池运行约束：
- 正常运营状态必须至少存在 1 名合格接客员工；后台关闭/停用最后一名合格接客员工时应阻止并提示先指定替代人员；System Admin 不能作为兜底销售。
- 极端数据异常导致池为空时，不得创建 owner/负责人为空的 consultation、waitlist、find-car application 等正式人工服务对象；记录配置异常并向客户提示暂时无法分配顾问。

### 公海 / 无正式 owner 客户重新产生高意向业务
客户处于公海或 `customer_owner_sales_id = null` 时再次主动触发“我要这辆车 / 登记候补 / 提交帮我找车 / 联系顾问”等高意向人工服务：
- 必须先原子化完成 owner 分配，再创建对应正式业务对象；
- owner 分配成功后，具体业务负责人再按 recommendation → demand → owner 等已冻结优先级固化；
- 不允许创建 `responsible_sales_id = null` 的正式人工服务对象；
- 分配与创建必须做事务/幂等保护。

## 8.3 推荐/转介绍

V1只保存数据：
- 直接推荐人
- 来源客户
- 来源销售
- 首次进入来源
- 推荐链

不做：
- 积分
- 返佣
- 奖励
- 裂变等级

## 8.4 员工离职与客户交接

销售/经理/店长离职后，客户不是离职员工个人资产，客户与业务历史继续归公司/门店保留。

离职后必须继续保留：
- 客户资料；
- 客户画像；
- 客户跟进记录；
- 找车需求；
- 推荐；
- 咨询；
- 锁车/交易历史；
- 意向金/退款事实；
- 原员工历史贡献、操作与责任记录。

离职流程：
**员工离职 / inactive → 原正式归属客户进入“离职待交接” → 经理/店长处理。**

处理方式：
- 批量转给指定员工；
- 合适客户放入公海；
- 正在进行 active/paused demand、当前有效 Priority、pending/processing consultation、当前有效候补、当前锁车、进行中 transaction 等活跃业务的客户，必须先完成相应 owner/业务关系/业务负责人交接；refund pending 作为客户公海保护事实保留，但 refund 本身不设独立负责人；
- 离职交接不仅处理 `customer_owner_sales_id`，还必须同时检查并处理当前活跃业务负责人及 Priority 业务关系；
- 至少包括：active/paused demand 的 `demand_responsible_sales_id`、当前 active Priority、pending/processing consultation 的 `consultation_responsible_sales_id`、当前有效候补负责人、当前 lock 负责人、进行中 transaction 的 `transaction_responsible_sales_id`；active Priority 不取消而随客户业务关系交接给新销售；deposit/refund 仅保留操作人和资金事实，不单独交接负责人；
- 业务负责人变更必须保留原负责人、转交时间、操作人、原因和历史，不得覆盖历史责任事实；
- 经理/店长是交接处理人，不自动成为全部离职客户或全部活跃业务的新负责人。

## 8.5 离职交接批次与后续再次分配

员工离职时，必须创建固定的“离职交接批次”（例如 `employee_departure_handover`），保存至少：
- `handover_batch_id`
- `departed_employee_id`
- `departed_at`
- 该员工离职当时正式归属的客户清单

即使后续客户发生 `A → B → D` 等多次归属变更，系统仍须永久知道该客户来源于哪个离职员工、哪个离职交接批次。

后台需要支持按离职员工/交接批次查看和筛选，例如：
- 原客户数；
- 已重新分配；
- 公海；
- 待处理；
- 当前负责人；
- 是否有有效需求；
- 最近跟进时间；
- 是否锁车；
- 是否交易中；
- 是否存在其他活跃业务。

新员工入职后，经理/店长可从指定离职交接批次中筛选并再次批量分配客户，不默认动用接管员工原本自有客户。

# 9. 客户等级、标签、画像与跟进

## 9.1 客户等级与业务权益

客户等级由后台动态配置：
- 可新增、改名、排序、启用/停用；
- 历史不物理删除。

V1取消复杂等级审批流程。

改为：
- “修改客户等级”是独立权限点；
- 有权限员工直接修改；
- 无权限不能改；
- 全部修改留审计。

客户等级与业务权益分层建模。找车核心代码不得写死“普通客户 / 粉丝客户 / VIP客户”等等级名称，而应读取等级对应的权益配置。

V1 至少支持以下找车权益：
- `can_use_find_car_matching`：是否可在客户提交找车条件后直接开通/激活正式持续找车服务（生成 active demand）；实际规则匹配仍须等待销售匹配描述形成并完成确定性解析。

当前默认业务配置：
- 普通客户：`can_use_find_car_matching = false`；
- 粉丝客户：`can_use_find_car_matching = true`；
- VIP 客户：`can_use_find_car_matching = true`。

这些是后台可配置的默认等级权益，不是写死在代码里的等级枚举。等级改名、新增等级或调整权益时，不应修改找车核心代码。

除等级自动获得权益外，后台还允许对具体客户**人工开通正式找车服务**。因此客户当前有效找车资格按以下逻辑判断：

**等级已授予正式找车权益，或客户级人工开通正式找车服务 → 具备正式持续匹配资格。**

客户级人工开通必须保留操作人、时间、来源/原因及审计历史。

## 9.2 “代淘中”

**彻底取消。**
- 不作为客户等级；
- 不作为业务状态；
- 不因本轮增加找车权益而恢复“代淘客户/代淘中”等旧概念；
- 客户是否具备正式找车服务资格由权益层判断；
- 客户是否正在正式找车由实际 `active` 正式需求判断；
- 仅有待确认找车申请，不等于“正在持续匹配中”。

## 9.3 标签

### 系统事实标签
由真实业务自动产生，例如：
- 名邦成交客户
- 某车型车主
- 二次购车等真实事实

普通销售不能随意伪造/删除。

### 运营标签
有权限员工可维护，例如：
- 价格敏感
- 急购
- 偏好黑色等

## 9.4 销售客户称呼备注

- 保留客户原始姓名/微信昵称；
- 销售可以记录自己使用的客户称呼/备注名；不同销售的记录互不覆盖，并保留备注人、时间和修改历史；
- 客户 owner 发生交接时，原销售留下的称呼类备注**必须向新 owner 可见**，用于延续沟通习惯；新 owner 可以沿用或新增自己的称呼，但不得覆盖/删除原备注历史；
- 后续再转交给其他销售时，同样可查看历史负责人留下的称呼记录；
- 客户看不到员工内部称呼备注；
- 真正的业务背景、客户画像和每次沟通内容仍分别写入客户画像/CRM跟进，不用称呼备注承载。

## 9.5 客户画像 / 客户背景档案

V1 正式增加客户画像/背景档案，绑定 `customer_id`，属于长期 CRM 信息，不属于某一条找车需求。

可保存：

### 基础背景
- 职业/工作情况
- 家庭情况
- 当前车辆

### 用车与购买动机
- 使用场景
- 换车/买车原因
- 主要使用人

### 决策关系
- 最终决策人
- 关键影响人（配偶、父母、朋友、公司相关人员等）

### 长期偏好
- 品牌
- 价格
- 配置
- 颜色
- 沟通方式等

### 关键顾虑与自由补充
- 销售对客户的核心判断
- 无法完全结构化的长期背景信息
- 可保留一个人工维护的“客户画像摘要”

V1 不要求 AI 自动总结客户画像。原则是先完整保存原始事实和人工认知，再为 V1.1/V2 的 AI 总结、意向判断等能力提供数据基础。

## 9.6 客户跟进记录 / 客户跟进时间线

V1 正式把客户跟进升级为 CRM 模块。每个客户拥有独立、不断追加的跟进历史。

每条跟进至少记录：
- 跟进时间
- 跟进员工
- 跟进方式：电话 / 微信 / 到店 / 面谈 / 其他
- 跟进内容
- 下一步计划
- 下次跟进时间（可选）
- 创建时间
- 修改/审计历史

允许关联：
- `demand_id`
- `vehicle_id`
- `consultation_id`
- `transaction_id`

客户画像、客户跟进、需求备注必须严格区分：
- 客户画像：这个客户长期是什么样的人；
- 客户跟进：每一次联系发生了什么、下一步做什么；
- 需求备注：某一条具体找车任务有什么特殊情况。

跟进记录是追加式历史时间线，不是不断覆盖的“最新备注”；原始历史原则上不物理删除。

V1 不强制 AI 自动总结跟进历史，后续版本再考虑自动总结、意向判断、销售建议等能力。

# 10. 找车需求与确定性规则匹配

## 10.1 正式需求状态

正式 `demand` V1 只保留：
- `active` 有效
- `paused` 暂停
- `completed` 已完成
- `cancelled` 已取消

不做自动 `expired` 过期状态。

客户等级/找车权益与 demand 状态是两层不同事实，不能混成一套状态。

## 10.2 找车申请、正式 demand、多需求与找车权益

**所有客户都可以表达找车诉求，但不是所有客户提交后都会立即进入正式持续匹配系统。**

V1 区分：
1. **找车申请 / 找车意向**：客户提交的原始诉求；
2. **正式找车需求 `demand`**：持续找车服务的业务任务容器。

客户提交“帮我找车”前必须满足手机号服务门槛。手机号授权成功后先保存找车申请，再判断正式找车资格。

### 已具备正式找车权益
等级权益允许或客户已被人工开通：
**申请保存 → 创建/激活正式 demand → active → 进入“待销售整理/确认匹配条件”阶段。**

只有销售匹配描述已经保存，并且确定性规则解析出可执行的标准匹配条件后，规则引擎才正式开始持续匹配。

### 尚未具备正式找车权益
**申请保存 → pending / 等待服务确认 → 不创建/不激活正式 demand → 不启动持续匹配。**

客户可查看/修改尚未激活申请、联系顾问、查看权益说明，但不得显示“持续匹配中”。

后台有权限员工开通正式找车服务后：
**申请 → 创建/激活 demand → active → 待销售整理/确认匹配条件 → 条件 ready 后启动匹配。**

申请可采用轻量生命周期 `pending / activated / closed`；`activated` 必须关联实际 `demand_id`。一个申请最多激活为一个 demand，重复激活必须幂等。

一个客户可以同时存在多条独立正式 demand，也可以存在尚未开通的申请。

客户侧“帮我找车”Tab 因此按**找车工作区**理解，而不是整个页面只能拥有一个互斥状态：
- 同一客户可同时看到多条 active demand、pending application、paused demand 和已结束需求；
- active demand 按各自匹配准备度显示“顾问整理中 / 持续匹配中”等真实状态；
- pending application 作为“待服务确认”区域展示；
- `paused` 仍是当前正式 demand 的暂停状态，单独展示为“已暂停”，**不得与 completed/cancelled 一起归为已结束历史**；
- `completed / cancelled` 才进入“已结束/历史需求”；
- 推荐结果继续按实际 demand 关联展示。


每条 demand 有独立：
- `demand_responsible_sales_id`

默认继承创建/激活当时客户正式归属销售；允许后续正式改派；需求负责人改变不自动改变客户正式归属。

### 匹配准备度与 demand 状态分开
为避免把“正式服务已开启”和“规则引擎已具备合法输入”混成一个状态，V1 单独保存匹配准备事实。技术字段可在状态机阶段确定，例如：
- `pending_definition`：尚无销售确认后的匹配描述，不能启动规则匹配；
- `ready`：已完成规则解析，可正常执行匹配；
- `ready_with_confirmation_needed`：已经有可执行的确定条件，但部分规则冲突/关键字段 unknown，需要人工确认。

这不是新的 demand 主状态。`active / paused / completed / cancelled` 仍只描述 demand 生命周期。

规则引擎启动前提是：`demand = active` 且销售匹配描述已经形成并完成确定性解析。

`ready_with_confirmation_needed` **不等于整个 demand 停止匹配**：系统可以使用已确定条件继续计算；涉及未确认硬条件的车辆必须进入“待确认候选”，不得自动判为高匹配。

### 已 active demand 与后续权益变化
正式 demand 一旦已经 `active`，后续客户等级下降、等级权益调整或客户级找车权益失效，**不得自动暂停、取消或结束该 demand**。

权益层只控制“能否新建/激活正式持续找车服务”；已经进入 demand 状态机的业务必须通过 pause / resume / complete / cancel 等正式动作改变状态并留审计。

## 10.3 四层找车信息模型

V1 明确区分四层：

### 1）客户原始找车需求
客户自己提交的文字和首填结构化条件。

用途：
- 保存客户当时怎么表达；
- 客户/销售查看；
- 业务留档；
- 绑定找车申请和后续 demand。

**客户原始表达不直接作为自动匹配主输入。**

### 2）销售匹配描述
销售与客户沟通后整理出的“系统实际应该找什么车”的业务描述，是 V1 自动匹配的主要输入。

例如：
“19年上牌 A6L 45/2.0T高功，原版，补漆不限，黑色优先，15万公里以内”。

### 3）系统解析后的标准匹配条件
后台匹配词典 + 确定性规则把销售匹配描述解析成标准化结构化条件。

### 4）正式 demand
`demand` 不是一段文字，而是持续找车服务的业务任务容器，继续承担：
- customer_id；
- demand_responsible_sales_id；
- active / paused / completed / cancelled；
- 销售匹配描述；
- 标准匹配条件；
- 匹配历史；
- 推荐历史；
- 跟进关联；
- 业务生命周期。

## 10.4 销售匹配描述、标准条件与需求说明

### 销售匹配描述
参与自动匹配。销售修改后：
**保存 → 重新规则解析 → 更新派生标准条件 → 重跑受影响车源 → 更新车源雷达。**

### 标准匹配条件
V1 自动匹配的当前统一字段按 `统一匹配与Priority规则_2026-09-17.md` 收口：
- 品牌 / 车系 / 车型范围；
- 年款最低要求；
- 客户展示价预算（默认允许上浮 5%）；
- 最高可接受里程；
- 外观颜色（硬条件，可多选）；
- 排量（硬条件，可范围/多选）；
- 动力类型（硬条件，可多选）；
- 车况排除要求（硬条件）；
- 内饰颜色（软偏好）。

变速箱、配置偏好、过户次数、城市/距离、排放标准、车源类型不参与 V1 自动匹配判定。客户未填写的字段视为不限；客户已填写而车辆事实缺失时为 `confirmation_needed`。同字段多选为 OR，不同字段为 AND。

### 需求说明 / 需求背景
原“需求内部备注 / 需求跟进说明”界面统一收窄为 **需求说明** 或 **需求背景**。

它描述这条找车任务的业务背景，**不参与匹配**，例如：
- 客户月底资金到位；
- 家庭成员对某内饰有意见；
- 之前看过某辆车但嫌里程高。

需求说明与销售匹配描述、统一 CRM 跟进必须分开。

需求说明至少保留：
- demand_id
- 内容
- 创建/修改员工
- 创建时间
- 修改历史

## 10.5 统一 CRM 跟进与 demand 相关跟进

不新建“需求跟进表”。

正式找车需求详情必须显示该 demand 的**相关跟进**：
- 客户详情：查看客户全部跟进；
- demand 详情：按 `demand_id` 过滤统一 CRM 跟进时间线；
- demand 详情提供“+ 记录跟进”；
- 新建记录进入统一客户跟进时间线，同时关联当前 `demand_id`。

## 10.6 V1 匹配核心：确定性规则，不使用 AI

V1 找车匹配明确不使用 AI：
- 不让 AI 理解客户话术；
- 不让 AI 理解车况；
- 不让 AI 判断车型版本；
- 不用 AI 自动生成匹配条件。

采用：
**标准车型数据 + 后台匹配词典/规则词典 + 确定性解析规则 + 结构化字段比较。**

匹配主流程：
**客户原始表达 → 销售沟通整理 → 销售匹配描述 → 规则标准化 → 结构化条件 → 统一公共匹配 → `high / acceptable / confirmation_needed / no_match` → Priority 客户优先分支（如有）→ 车源雷达 → 销售人工推荐。**

Priority 不是第二套匹配算法；普通客户和 Priority 客户共享同一匹配结果。

## 10.7 匹配词典 / 规则词典

后台维护可持续增量完善的匹配词典，不要求上线前一次性导入全部规则。

可维护：
- 车型别名；
- 动力/版本别名；
- 驱动别名；
- 配置别名；
- 车况词；
- 其他业务同义表达。

匹配词至少保存：
- 匹配词；
- 标准映射结果；
- 品牌；
- 车系；
- 年款/适用范围；
- 启用状态；
- 备注；
- 创建人；
- 修改人；
- 修改时间；
- 审计历史。

后台提供“测试匹配”：输入字符串，展示当前规则会解析成哪些标准事实。

### 规则作用域与优先级
优先级：
1. 具体车型 + 具体年款；
2. 车系 + 年款范围；
3. 车系规则；
4. 品牌规则；
5. 全局通用规则。

同一优先级出现互相冲突：
- 不自动猜；
- 进入规则冲突/待确认。

一个匹配词允许映射多个**可确定**结构化事实，但不得推断无法确定的字段。

例如在明确适用范围内：
- `quattro / 四驱 / AWD` 可归一到 `drivetrain = AWD`；
- `45 / 45 TFSI / 2.0T高功 / 高功` 可按对应车型/年款规则归一。

映射必须带品牌/车系/年款或其他适用范围，禁止全局粗暴写死。

## 10.8 新增/修改规则后的受影响范围重算

新增或修改匹配词后：
- 重新解析受规则影响的当前在售车源；
- 重新计算相关 `active demand`；
- 更新相关车源雷达结果。

**不得无脑全库重算。**

重算范围依据规则作用域，例如：
- 指定品牌；
- 指定车系；
- 指定年款/范围；
- 相关车辆；
- 相关 active demand。

上游原始文字/Source Data 永远保留；规则只能产生名邦自己的派生结构化字段，不能覆盖原始事实。

## 10.9 车况标准体系

车况匹配不得只保存“精品/一般”等单一等级。核心结构化事实至少可拆分：
- 原版/覆盖件是否更换；
- 原漆/漆面；
- 补漆数量；
- 钣金；
- 结构件；
- 重大事故；
- 泡水；
- 火烧；
- 原始车况描述。

原始描述永久保留。

### 原版与原漆必须分开
- **原漆**：车身金属覆盖件没有补漆；
- **原版**：没有覆盖件更换，且没有结构件切割/更换等结构性问题。

因此：**原版 ≠ 原漆。**

例如“必须原版、补漆无所谓”：
- 原版 = 硬条件；
- 补漆 = 不限。

“必须原漆”才要求补漆面数为 0。

## 10.10 unknown 不是不匹配

所有硬条件统一使用三值/可确认语义：
- **明确符合** → 正常进入候选；
- **明确不符合** → 不匹配；
- **信息未知/无法确认** → 待确认候选。

适用于：
- 价格；
- 年份；
- 里程；
- 车型版本；
- 配置；
- 驱动；
- 车况；
- 其他硬条件。

系统不得用猜测把 unknown 自动填成符合或不符合。

## 10.11 候选分层

匹配结果核心使用候选层级，不只看单一分数：
1. `high`：硬条件满足，客户展示价不超预算，已填写内饰颜色偏好也满足；
2. `acceptable`：硬条件满足，但展示价高于预算且 ≤5%，或内饰颜色偏好不满足；
3. `confirmation_needed`：已填写硬条件对应的车辆事实缺失/无法判断；
4. `no_match`：硬条件明确不满足、展示价超过预算 5%，或车辆没有可用客户展示价。

预算统一使用客户当前实际展示价。`confirmation_needed` 不产生 Priority、不阻断其他客户。

匹配记录可保存：
- demand_id
- vehicle_id
- candidate_tier
- score/priority（可选排序字段）
- match_reason
- mismatch_reason
- unknown_reason
- created_at
- recalculated_at
- workflow_status（new/reviewed/recommended/rejected/invalid 等）

历史不删除。

## 10.12 价格咨询、锁定车辆与候补

价格匹配统一使用客户当前实际展示价。车辆没有可用客户展示价、只能“价格咨询”时，本轮直接 `no_match`，待后续产生明确客户展示价后再由价格变化事件触发重算。客户未填写预算时不做预算上限比较，但仍要求车辆存在可用客户展示价。

已被其他客户正式锁定的车辆仍可产生匹配结果，但必须标记已锁定；销售可为其他客户登记候补意向。

# 11. 车源雷达、推荐与客户机会

## 11.1 车源雷达

车源雷达不是若干独立功能按钮，而是围绕：
**某个客户 / 某条正式 active demand**
聚合展示与其相关的车源动态。

雷达事件包括：
- 新上架；
- 重新上架；
- 价格变化；
- 下架；
- 供应异常；
- 与当前需求产生新匹配/重算结果。

呈现逻辑类似：
“张先生｜宝马530需求｜6个新动态”
并聚合显示新匹配、改价、重新上架、下架等数量和明细。

销售阅读逻辑是：
**哪个客户的哪条正式找车需求现在出现了新的车源机会？**

普通匹配不逐车飞书轰炸。

系统自动匹配只进入车源雷达，**不直接推荐客户**。

## 11.2 正式推荐

链路：**规则匹配/销售判断 → 推荐给客户 → 正式 recommendation 记录**。自动匹配只进入车源雷达，不自动推荐客户。

推荐支持客户上下文和车辆上下文双向入口，底层统一 recommendation 对象。

推荐客户选择必须按当前上下文处理：
- 从 demand / 车源雷达进入时，系统已经知道 customer_id、demand_id、vehicle_id，点击“推荐给客户”后直接创建 recommendation，不得再次选择客户；
- 从某个客户 CRM 进入时，系统已经知道 customer_id，“客户 → 推荐车辆 → 选择车辆”后直接创建 recommendation，不得再次选择客户；
- 只有从 E02 普通车辆上下文进入、当前只知道 vehicle_id 而不知道目标 customer 时，才执行“推荐给客户 → 选择客户 → 创建 recommendation”。

原则：**已知客户上下文直接继承；只有未知客户时才选择客户。**

对象与边界：
- 一条 recommendation 最多关联 0/1 条 `source_demand_id`；demand/雷达上下文推荐则写该 demand，销售主动 CRM/库存推荐可为空；不得把一条 recommendation 绑定多条 demand；
- 同一车辆可以在候选层同时匹配多条 demand；同一客户多 Demand 命中时先选最佳 `trigger_demand_id`，跨客户 Priority 仲裁只算一个候选；
- 同一 `listing_cycle` 内，同一客户+车辆最多一条 active Recommendation；新 listing_cycle 重新开始；
- recommend_reason 可选；Recommendation 使用最小 `active / ended` 生命周期，并支持因其他客户 active Priority 暂时压制客户端可见性；
- 车辆 normal 可推荐；locked 可推荐但必须明确已锁/可候补；trading/completed/offline/unavailable/platform-hidden 不得新建客户正式推荐。

最小业务字段：customer、vehicle、recommend_sales、recommended_at、source_demand_id（可空）、不可变推荐时价格快照、可选推荐原因及必要技术审计。

价格权限：
- **正式 recommendation 授予客户当前 listing_cycle 的批发价格查看权限；普通分享不授予。**
- 推荐销售后来离职、owner/demand负责人变化，不撤销本周期已取得权限；历史 recommender 永久保留原推荐归因。
- 历史 recommendation 当前价格展示必须服从当前 listing_cycle 的价格权限，不能借历史推荐泄露新周期价格。

历史与终态：
- completed/cancelled demand 仍保留历史推荐，但不得再创建新的 `source_demand_id` 指向已结束 demand；以后再次推荐可作为无 demand 推荐或关联另一条 active demand。

## 11.3 客户机会

客户机会只是“当前确定性规则命中结果 + 去重/冷却事实”，不是 consultation、任务或独立业务对象，不设置 pending/closed、负责人或关闭按钮。当前仍命中的机会跟随当前 customer owner；条件不再命中即从当前机会消失。

V1 只保留 3 类：
1. **长期未登录/未有效浏览**：默认 7 天，可后台配置；
2. **单日高频浏览但没有明确车辆意向/咨询或真实沟通/CRM跟进**：默认 >40 次，可配置；
3. **连续多日浏览但没有咨询或真实沟通/CRM跟进**：默认连续 3 天，可配置。

“有效活跃”只计客户主动业务行为，例如搜索/筛选、车辆详情、正式推荐回看、收藏/取消收藏、查看找车业务、我要这辆车、联系顾问、候补、提交找车等；token刷新、心跳、后台轮询、系统任务、员工代改资料等不计。

规则：
- 不逐条飞书；仅在 E01 工作台展示；
- 匿名用户不生成具名机会；
- 不展示造成过度监控感的完整浏览流水，只展示必要聚合事实；
- V1 不做 AI 意向评分；
- 必要历史行为/冷却事实可保留以实现去重，但不形成机会生命周期。

# 12. 客户咨询与“我要这辆车”

## 12.1 “我要这辆车”

客户车辆详情在车辆正常可售时，核心 CTA 为：
**收藏 ｜ 我要这辆车**

“我要这辆车”表示客户对当前具体车辆产生明确购买意向。

执行前必须经过手机号服务门槛：
- 已有手机号 → 继续；
- 无手机号 → 触发微信手机号授权；
- 拒绝授权 → 不创建正式人工跟进业务对象，仍可浏览。

授权成功后：
- 创建咨询/明确车辆意向记录；
- 不自动锁车；
- 不自动创建交易；
- 不自动创建正式找车 demand；
- 不依赖客户是否拥有持续找车权益。

普通浏览详情产生的“我要这辆车”原则上由 `customer_owner_sales_id` 负责，并在咨询创建时固化 `consultation_responsible_sales_id`。

## 12.2 咨询顾问

“咨询顾问/联系顾问”放在顾问信息或其他内容区域，不与“我要这辆车”争抢主 CTA；首次人工联系执行手机号服务门槛。

状态固定：`pending / processing / resolved / invalid`。其中 `resolved`、`invalid` 为终态，不复活；客户之后再次明确咨询（即使同客户+同车辆）创建新的 consultation。

同一客户 + 同一车辆已有 `pending/processing` consultation 时，再次点击“联系顾问/我要这辆车”等应复用当前咨询，不重复创建；“我要这辆车”可记录更强的明确车辆意向事实，但仍在同一咨询体系。

每条咨询创建时固化唯一 `consultation_responsible_sales_id`：
1. 来源正式 recommendation → 当前仍具备业务资格的推荐销售；历史推荐销售已离职/无资格时不得成为新业务负责人；
2. 明确关联 active/paused demand → demand 负责人（需当前有资格）；
3. 普通车辆浏览/我要这辆车/顾问咨询 → customer owner；
4. owner 为空/无资格 → 先从合格接客池原子分配 owner，再创建咨询。

咨询创建后普通 owner/demand负责人变化不让负责人自动漂移。只有 `pending/processing` 咨询需要在离职/资格丧失等场景正式 reassignment；`resolved/invalid` 历史负责人永久保留原事实。

SLA：
- 从 consultation 创建到**第一次真实人工服务动作**计时；打开页面、已读、改状态、转派均不算有效处理，转派也不重置 SLA；
- 默认阈值 15 分钟，可后台按分钟配置；创建时固化本次 deadline，后续修改默认阈值不追改已创建咨询；
- first real human service action（实际联系/有效回复/新增真实 CRM 跟进等）后停止首次响应 SLA；consultation 可继续保持 processing。

咨询与交易状态独立：transaction completed 不自动把 consultation 改成 resolved；由销售按真实处理结果结束。

# 13. 飞书、公告与夜间免打扰

## 13.1 飞书员工映射

每个当前需要个人通知的员工建立 **名邦 employee_id ↔ 当前飞书接收身份** 映射，优先统一飞书应用/通知服务 + user_id/open_id 等映射，不强制一人一个 Webhook。

员工更换飞书账号或重新绑定：只更新当前通知路由，employee_id、业务负责人和历史业务均不变；旧映射保留必要审计，已发送历史不迁移/重发。员工 inactive 后不得继续把新的个人业务通知推给其旧飞书身份。

## 13.2 通知职责

客户侧不建设通用“消息中心/已读未读”业务体系。客户业务变化主要通过各业务页面、历史和公告查看。

飞书只承担员工重要事项主动提醒；名邦数据库始终是业务事实唯一权威来源。

## 13.3 个人飞书

可推对应员工的重要个人事项：
- 新明确咨询；
- 候补车辆释放；
- 锁车到期提醒；
- 供应异常；
- 交易重要变化。

**取消“重要匹配机会个人飞书”**；普通匹配和客户机会只在工作台/车源雷达查看。普通浏览、点击、埋点不逐条推送。

## 13.4 客户服务超时

- consultation 首次响应 SLA 默认 15 分钟，后台可配置；创建 consultation 时固化本次 deadline；
- 达到 deadline 且仍未发生真实有效人工服务动作 → 直接向飞书大群发送“服务已超时”告警；不再销售→经理→店长逐级升级；
- 同一 consultation 同一首次响应阶段原则上只告警一次；
- 告警至少含客户、负责销售、咨询摘要、已超时时长、业务入口。

## 13.5 夜间免打扰

默认 **23:00 ～ 次日 08:30（业务时区 UTC+8）**，后台可配置。

夜间所有主动飞书通知（包括紧急业务/P0）暂停，但业务、SLA、异常、incident、日志照常运行和入库。

08:30 恢复时重新判断事件当前是否仍有效：
- 夜间已解决/失效 → 不机械补发；
- 仍重要的业务异常可逐条恢复发送；
- 普通机会/信息不主动轰炸，可按业务需要聚合；
- 金鱼塘持续 incident 继续按其独立重复告警节奏执行。

## 13.6 通知幂等与失败

同一业务事件、同一阶段原则上只通知一次。

建议发送状态：
- pending
- deferred
- sent
- failed
- skipped
- deduplicated

飞书发送失败必须记录：
- 消息类型
- 接收对象
- 发送时间
- 成功/失败
- 失败原因

V1不建设复杂消息运维中心。

## 13.7 客户微信小程序主动通知边界

V1 **不做客户侧微信小程序订阅消息提醒体系**。

明确不做：
- 小程序订阅消息授权流程；
- 模板/发送资格管理；
- 容易让客户误以为“打开一次即可长期推送”的通知开关；
- 依赖小程序订阅消息实现客户离开后的长期主动提醒。

客户业务变化主要在小程序自身业务页面/状态中查看；员工重要主动提醒继续使用飞书体系。

微信服务号继续保留为未来客户触达/回流的辅助能力，但不作为 V1 核心通知依赖。

## 13.8 客户小程序公告

V1 增加轻量“客户小程序公告”能力。该能力只在客户主动打开/进入小程序时展示，**不属于微信小程序订阅消息或离线主动推送体系**。

展示规则：
- 用户进入客户小程序时，系统检查当前是否存在已启用且处于有效期内的公告；
- 同一客户对同一条公告**每天最多自动展示 1 次**；
- 当天已经自动展示过，再次打开小程序不重复自动弹出；
- 第二天再次进入时，如果公告仍然有效，可再次自动展示；
- 用户可主动关闭公告；
- 后台将公告停用后，立即停止自动展示；
- 同一时间存在多条有效公告时，V1 每次进入最多自动弹出 1 条，由后台排序/发布时间决定优先展示项，避免连续弹窗。

展示频控原则：
- 已登录客户的每日展示记录以后端为准，不只依赖本地缓存；
- 至少记录 `announcement_id`、`customer_id`、`last_shown_at` 等频控事实；
- 未登录场景可使用本地缓存做轻量频控，登录后以客户账号维度为准。

客户可在“我的”中的公告入口主动查看当前可见公告；主动查看不受“每天最多自动展示 1 次”限制。

V1 不建设：
- 复杂人群定向投放；
- 复杂多级优先级算法；
- 阅读率/营销分析中心；
- 基于公告的微信订阅推送；
- 复杂营销自动化。


## 13.9 车源同步 / Collector 异常、incident 与持续告警

名邦车源同步 API、Collector 电话连接/请求等集成链路只要发生错误：
- 立即记录异常；
- 直接通知**飞书群**；
- V1 不要求在报警前先精确区分鉴权失败、网络错误、Collector 不可用等原因。

名邦不测试、不监控 JYT 上游登录 Token；JYT 凭证及其健康状态属于 Collector 内部责任。上述集成异常不增加独立运维收件人体系，只使用现有飞书群。

### 持续故障归并 incident
同一持续故障不得每次失败都新建事件。保存持续 `incident`，至少包含：
- incident_id；
- 首次失败时间；
- 最近失败时间；
- 最近报警时间；
- 报警次数；
- 当前状态；
- 恢复时间。

服务重启后也不能把同一持续故障重新当作第一次故障。

### 持续告警节奏
同一 incident：
- 第一次发现：立即报警；
- 2 分钟后仍未恢复：再次报警；
- 之后每 5 分钟一次；
- 持续超过 30 分钟：改为每 15 分钟一次；
- 恢复成功：结束 incident，停止重复报警，并发送一条“已恢复正常”。

这是“同一业务事件同一阶段原则上只通知一次”的**明确例外**。

### 夜间免打扰
仍遵循 23:00～08:30：
- 夜间异常和 incident 继续记录；
- 健康检测继续执行；
- 不主动发送飞书；
- 08:30 若仍异常，立即补发严重异常提醒；
- 之后继续按持续告警节奏；
- 夜间已恢复的故障不机械补发无意义的异常轰炸，可保留恢复事实。

产品层只冻结“错误立即记录并按上述节奏告警”。具体某类上游实时调用是否采用熔断、连续多少次失败触发熔断，由技术阶段作为保护实现确定，不作为当前产品前置条件。

# 14. 锁车、候补、意向金、交易、退款

## 14.1 正式锁车

- 同一辆车同一时间只能有一个有效正式锁；同一客户可同时锁多辆不同车辆；
- 正式 transaction 必须来源于当前有效 lock；进入 transaction 时原 lock 原子关闭，车辆业务状态进入 trading；
- 锁车负责人/业务负责人就是本次 lock 负责人，保存实际操作人用于审计；普通 customer owner 变化不自动改 lock 负责人，正式交接才改变；
- 锁车保存当时客户有效展示价快照：有数字保存数字，无数字保存明确“价格咨询”事实，不得写 0/假价格；后续价格变化不得覆盖；
- 客户已有自己当前有效 lock 时，客户详情 CTA 为“收藏｜查看锁车进度”，不得重复候补/重复我要这辆车。

## 14.2 无意向金锁车

每笔无意向金正式锁必须有 `expires_at`。
- V1 默认锁车时长 **2 小时**，后台可配置；有权限员工创建锁车时可调整具体到期时间；
- 到期前默认 **30 分钟**提醒，可后台配置；
- lock 创建后 `expires_at` 固化，后台修改默认时长不追改已有 lock；
- 无确认意向金且到期 → 自动释放并更新业务状态；
- 锁释放/到期/取消只通知相关有效候补负责人，不自动关闭所有候补，也不自动把候补升级为正式锁。

## 14.3 已收意向金

意向金仅表示线下真实收款事实，不设置“未结/已结/部分”等独立意向金状态。
- 同一 lock 可存在多笔实际意向金收款事实；总额按事实派生；
- 每笔记录金额、收款时间、方式、操作人、备注、可选凭证；deposit/意向金没有独立业务负责人，只有操作人；
- 只要当前 lock 已确认存在意向金收款事实，就不得因 expires_at 自动释放；后续按进入交易、取消和实际退款事实处理。

V1 只记录线下收款事实，不做在线支付。

## 14.4 候补意向

车辆被其他客户正式锁定时，客户 CTA：**收藏 ｜ 登记候补**。登记前执行手机号服务门槛。候补是独立业务对象，不是 consultation，不自动锁车。

负责人优先级：
1. 来源正式 recommendation → 推荐销售（必须当前仍具业务资格）；
2. 明确关联 active/paused demand → demand 负责人；
3. 普通车辆详情 → customer owner；
4. owner 为空/无资格 → 先分配合格 owner 再创建。
负责人创建后固化，普通 owner/demand负责人变化不自动漂移，正式 reassignment 留历史。

唯一与终态：
- 同一 customer + vehicle 同时最多一条当前有效候补；重复点击/提交复用现有候补；
- 当前有效候补允许由**该候补负责人**主动结束；具备对应数据范围和管理权限的经理/店长也可以结束。人工结束必须填写原因并保留操作人与历史；
- V1 客户端不新增“客户自己取消候补”按钮；客户明确表示不再等待时，由上述有权限员工在员工端/后台结束候补；
- 人工结束不新增候补主状态，只作为当前有效候补的结束事实/结束原因保存；
- 旧候补结束后历史保留，未来若车辆状态允许且客户再次明确登记，可新建一条候补；
- 车辆真实 `completed`、资源 `offline/unavailable/sold_external` 时，所有当前有效候补自动结束并保留历史；单纯 `platform_visibility = hidden` 不结束候补；
- 候补客户后来取得该车正式 lock 时，只结束该客户自己的当前候补；其他候补保持有效；
- 当前 lock 释放/到期/取消不自动结束其他候补，只通知相关负责人；
- 误成交被纠错后，因误成交已经结束的候补不自动复活，仍需重新登记。

## 14.5 交易负责人

每笔 transaction 必须有唯一 `transaction_responsible_sales_id`，默认继承本次 lock 负责人；与 customer owner、demand 负责人相互独立。普通 owner 变化不自动改写；离职/资格丧失等正式交接才转移并留历史。意向金/退款不设独立业务负责人，只记录实际操作人。

## 14.5A 退款主体与业务链完整性

- 一张退款单必须且只能绑定一个主业务对象：`lock_id` 或 `transaction_id` 二选一，不允许都空，也不允许同时填写。
- Lock 侧退款用于尚未进入 Transaction、但已经存在有效意向金收款事实的 Lock；如果该 Lock 已经生成 Transaction，退款必须归入对应 Transaction，不再同时以 Lock 为主体。
- Transaction 侧创建退款单时，Transaction 必须处于 `completed` 或 `cancelled`，且仍存在可退余额。
- `refund.customer_id` 必须与所绑定 Lock/Transaction 的客户完全一致；创建与退款支付都在同一业务对象范围内校验。
- Recommendation、Consultation、Lock、Waitlist、Transaction 的来源引用必须保持同一客户/车辆业务链：不能把 A 客户的 Lock 关联到 B 客户的 Demand/Recommendation/Consultation，也不能让 Transaction 引用另一客户或另一车辆的 Lock。
- 数据库负责结构性组合外键/XOR 兜底；金额可退余额、状态资格等跨表派生条件由应用事务在写入前校验。

## 14.6 交易

状态只保留：`进行中 / 已成交 / 已取消`。

- transaction 必须由当前 lock 创建；创建 transaction 时原 lock 原子关闭；同一车辆同一时间最多一笔进行中 transaction；
- `cancelled` 为终态，不复活；客户后来再次购买同一车辆，必须在当前资格允许时重新 lock → 新 transaction；
- 取消交易后 `biz_status` 固定从 `trading` 回到 `normal`；当前 `source_status` 与 `platform_visibility` 原样保留。车辆是否重新可展示/可售由三条状态轴和当前可见/权限事实共同派生，不恢复旧 lock；
- completed 成交记录实际成交价、成交时间、交易负责人、客户真实购车事实；历史交易主价格永远是**实际成交价**，不随后来车辆展示价/批发价/重新上架价格漂移；
- completed/cancelled transaction 默认历史只读，纠错留痕；
- transaction completed 不自动完成客户其他 active demand，也不自动关闭/解决其他 consultation。即使某 transaction 关联某 demand，也由销售根据真实服务目标决定 demand 是否 completed。

## 14.7 换车

**V1彻底取消“换车”专用功能/状态/关联关系。**

需要换另一辆车：
- 取消原锁车/原交易；
- 新车辆按正常流程重新锁车；
- 不建立 change-car 专用关系。

## 14.8 退款

退款是实际线下退款事实，主状态只保留：`pending / refunded`。
- 可以存在多笔实际退款分次事实；在应退金额未全部实际退完前整体保持 `pending`，全部完成后为 `refunded`；
- 不增加 `partial / non_refundable` 等退款主状态；若没有实际应退款事实，则不创建 refund 对象；
- 当场已经全部退完可以直接记录为 refunded；
- refund 没有独立负责人，只记录实际操作人；
- transaction cancelled 与 refund pending 可以同时成立；
- `refund = pending` 保护 customer 不进入公海，但**不占用车辆**；`refunded` 后退款本身不再构成公海保护。

## 14.8A 锁车/资金/交易关联视图原则

员工端可把 lock、意向金收款事实、transaction、refund 及操作/负责人历史聚合在同一关联视图，但不新增统一“大业务单”或统一大状态。
- lock / transaction 各自有负责人；
- deposit / refund 不设独立负责人，只有操作人；
- 关联视图只负责串联事实与操作跳转。

## 14.9 成交撤销/纠错

普通销售不能撤销 completed。授权经理/店长/System Admin 等按权限可直接执行纠错，必须填写原因并留完整审计；V1 **不做二级审批流**。

- 原 completed transaction 不物理删除，标记失效/撤销；实际成交价等历史事实保留；
- 被撤销 completed 不再计入真实成交统计、事实标签或未来模型样本；
- 车辆根据当前真实 source/visibility/biz 事实决定是否恢复可售；
- 若确认 completed 本身纯属误操作、车辆真实资源从未失效，则恢复原 listing_cycle 的连续性：不创建新 listing_cycle、不计今日新增、不顶到最新上架；原周期查价权限继续有效；
- 因误成交已经自动结束的候补不复活。

只有车辆后来真实经历不可售 → 再次可售，才建立新的 listing_cycle。

# 15. 公海

V1 保留**半自动公海**：销售可认领；经理/店长可手动放入/重新分配；保留完整归属、认领、转移历史。经理/店长不得绕过保护条件。自动接客开关只影响未来自动新客分配，当前有权限员工的公海手动认领独立存在；认领成功直接设置 owner，不新增申请/审批。

以下客户**绝对不得**被手动放入公海：
- `pending` 找车申请；
- `active` 或 `paused` demand；
- 当前有效 Priority；
- `pending` / `processing` consultation；
- 当前有效 waitlist；
- 当前有效 lock；
- `进行中` transaction；
- `refund = pending`。

历史上仅有已收意向金事实、但当前 lock/transaction/refund 等均已结束时，不单独构成公海保护。`resolved/invalid` consultation、已结束候补、`refunded` refund 本身也不再保护。

### 疑似长期未跟进客户
这是**派生候选列表，不是客户状态/业务对象，不自动进公海、不发飞书**。必须同时满足：
1. 客户近期存在后台配置窗口内的**有效主动活跃**；
2. 距最后一次真实 CRM 跟进超过后台配置阈值；
3. 当前不存在任何上述公海保护业务。

长期完全不活跃、正常成交后沉默等客户，不因销售没有周期性跟进而自动进入候选。有效活跃采用与客户机会一致的真实客户主动行为定义，后台心跳/轮询/员工代操作不算。管理者只是在候选列表中人工判断是否真正放入公海。

# 16. 员工车辆详情：客户安全默认 + 临时内部模式

这是 V1 最新安全交互规则。

## 16.1 默认状态

E02-01 员工/销售车辆详情与 C01-01 使用同一套固定顶部导航功能规则：
- 有合法上一页：**返回 ｜ 分享车源 ｜ 车型名称 / 车辆标题**；
- 外部直达且无合法上一页：**主页 ｜ 分享车源 ｜ 车型名称 / 车辆标题**；
- 员工端“主页”回 E02 车源；
- 微信官方胶囊继续保留，自定义导航避让；
- 不采用首屏压图按钮、下滑后再切换导航或两套返回并存。

员工/销售打开车辆详情：
**默认就是客户安全模式。**

旧方案“默认销售内部详情 → 点客户展示模式”正式废弃。

默认页面可直接给客户看：
- 图片
- 车型
- 基础参数
- 客户可见车况
- 客户可见档案/报告
- 客户展示价/价格咨询
- 其他客户可见信息
- 图片支持点击进入全屏预览，作为客户安全能力直接使用

不显眼展示：
- 内部价格
- 查看批发价
- 编辑模式
- 内部信息入口

## 16.2 内部模式入口

员工需要内部能力时：
**长按车辆价格区域约 3 秒**

流程：
1. 触发长按；
2. 后端验证当前账号是否为员工；
3. 根据当前车辆逐项检查权限；
4. 临时进入内部模式；
5. 按权限返回并展示内部字段/操作。

长按只是一种 UI 触发，不是权限。

## 16.3 高频销售动作与内部敏感能力分层

形成统一原则：**高频销售动作放外面；敏感经营数据和管理操作放里面。**

员工车辆详情在客户安全默认状态下必须保留两个日常核心能力：
- **推荐给客户**
- **锁车**

两者都不要求先长按进入内部模式，但执行时仍必须由后端校验员工身份、权限、数据范围和当前业务状态。

“推荐给客户”不得挤占或破坏底部更高优先级的强业务 CTA（例如当前状态下的锁车，以及有权限时的一键转名邦等）。推荐可以进入车辆详情上方快捷操作区域等位置；**具体视觉位置留到员工端低保真阶段决定，不在 SSOT 中冻结具体坐标。**

必须进入内部模式后才可按权限展示/执行的敏感能力包括：
- 查看内部价格 / 批发价
- 查看批发车源电话
- 编辑车辆
- 编辑车况
- 调价
- 上下架
- 单车客户展示价覆盖
- 一键转名邦
- 其他敏感经营/管理操作

进入内部模式不等于获得全部权限，各能力继续独立授权。

4S成员进入内部模式也不能突破“只能管理自己上传车辆”等数据范围。

## 16.4 后端安全边界

客户安全请求时：
- 后端原则上不返回内部价格、内部备注、员工敏感数据或无权限操作信息；
- 禁止“后端全部返回，只靠前端 CSS 隐藏”。

## 16.5 正式 recommendation 与普通“分享车源”

### A. 正式 recommendation

正式 recommendation 是系统内部业务关系：

**customer_id ↔ vehicle_id ↔ recommendation**

它不是微信链接，不使用 REC 专用链接、REC 专用 URL 参数、推荐专用分享页或第二套微信分享能力。

客户正式收到 recommendation 后，通过现有业务入口查看：
- C02“帮我找车”中的对应 demand / 推荐车源；
- C03“我的推荐”；
- 其他既有业务历史入口。

销售在正式 recommendation 之后如果还需要通过微信把车辆发给客户，直接复用普通“分享车源”，不创建 recommendation 专属分享能力。

### B. 普通“分享车源”

全系统只保留一套普通“分享车源”，适用于：
- 客户端与员工/销售端；
- 车辆 Feed / 列表；
- 车辆详情；
- recommendation 创建后销售希望继续通过微信发送车辆的场景。

普通分享必须支持：
- 分享给微信好友/客户；
- 分享到朋友圈。

车辆 Feed / 列表上的分享按钮具体视觉位置留到低保真决定，不在业务规则中写死。

### C. 分享来源归因

普通分享必须安全携带轻量来源归因上下文，产品层需要能够识别：
- employee sharer；
- customer sharer；
- source employee；
- source customer；
- direct referrer；
- referral chain。

具体技术实现可在 API 阶段选择 `share_token`、signed share context、share attribution id 等方式；**具体字段名称不是不可改变的产品规则**。

来源归因上下文只用于：
- 来源归因；
- 转介绍；
- 新客户 owner 判断；
- 推荐链追踪。

绝不能因为分享来源上下文自动授予：
- recommendation；
- 批发查价权限；
- 员工身份；
- staff mode；
- 内部价格；
- 编辑权限；
- 锁车权限；
- 其他业务权限。

### D. 分享后的 customer owner

- 已有客户点击任何其他人分享的车辆，现有正式 owner 不改变，只记录来源事实；
- 新客户从当前在职且具名邦客户业务资格的员工分享进入，可归该员工；
- 新客户由老客户 B 分享进入时，优先归 **B 当前正式 owner**，并保存 B 作为来源客户/直接推荐人及完整转介绍链；
- 如果 B 后续已经从 A 正式转交给 D，则 B 此后分享产生的新客户归 D，而不是历史 owner A；
- 历史分享者/对应 owner 已离职或失去业务资格时，保留历史来源归因，当前 owner 从合格接客池产生。

### E. 分享与批发查价权限

普通分享只表示“车辆传播 + 来源归因”，**本身不赠送任何批发查价权限**。

正式 recommendation 可以给予对应客户：
- 该 recommendation 对应车辆；
- **当前 listing_cycle**；
- 免费价格查看权限；
- 不消耗客户当天普通批发车查价额度。

该权限只限这一辆正式推荐车辆，不能使客户回到 C01 后自动看到全部批发车价格。

普通客户自行查看其他批发车，继续使用后台配置的每日“新批发车查价额度”。

价格权限核心始终围绕：

**customer + vehicle + listing_cycle**

不能因为打开分享链接、从微信外部进入或仅打开过小程序获得全局批发价格权限。

### F. 分享标题与图片

分享标题和默认图属于配置/视觉层：
- 车辆详情标题可用车型/车辆标题相关模板；
- 优先首张可用真实车图；
- 无图使用统一默认图；
- 首页使用统一品牌分享标题/图片。

具体营销文案不写死进核心业务规则。

## 16.6 临时性

内部模式仅对：
- 当前员工
- 当前车辆
- 当前详情页面

临时有效。

离开详情、返回、重新打开、分享/推荐后、长时间后台恢复等场景重新回到客户安全默认状态。

# 17. 客户与员工小程序关键 IA / 交互

> 页面编号在新聊天中可以重新编号；旧 C/S/F/A 历史编号不作为唯一事实源。以下按功能结构为准。

## 17.1 全局一级 Tab

客户小程序底部固定 3 个一级 Tab：
1. **车源**
2. **帮我找车**
3. **我的**

旧 5 Tab 方案废弃。

### 客户首次进入与个人资料完善

客户首次进入时，建立微信身份后检查头像/昵称。未完善时可以弹出轻量资料完善提示，但必须允许关闭/暂时跳过，不得阻断进入车源、帮我找车或我的。

“我的”中需要提供**个人资料**入口，供客户主动维护头像和客户昵称/称呼。头像/昵称未完善时的主动提醒按客户维度每天最多 1 次；该提示属于 Overlay/弹层，不新增一级页面。

若同一次进入同时命中公告和资料完善提示，V1 不连续叠加多个强弹层；按低保真阶段确定的单一弹层优先策略展示，另一项改为轻入口或延后展示，不改变任何业务资格。

### “帮我找车 / 我的找车”同一 Tab 动态状态

“帮我找车”和“我的找车”不是两个一级入口，而是同一个 **帮我找车** Tab 根据客户当前找车业务状态动态切换内容。

至少考虑以下业务状态：

**状态 A：从未提交找车申请/需求**
- 默认直接展示“帮我找车”首填表单。

**状态 B：已提交申请，但尚未获得正式找车权益**
- 显示“需求已提交 / 等待服务确认”；
- 可查看和修改申请、联系顾问、查看找车权益说明；
- 不显示持续匹配状态，不启动正式自动匹配。

**状态 C：已拥有正式找车权益且存在 active demand**
- Tab 内容默认表现为“我的找车”；
- 如果仍为 `pending_definition`：显示“顾问正在确认/整理找车条件”等真实状态，不得显示“持续匹配中”；
- `ready` 后：显示“找车中 / 持续匹配中”；
- `ready_with_confirmation_needed`：可以显示持续匹配，但应提示“部分条件待顾问确认”，相关结果按待确认候选处理；
- 同时展示当前需求、找车进度、我的顾问、新增找车需求等。

**状态 D：已经产生正式推荐车源**
- 继续在“我的找车”内展示推荐车源、需求详情、找车进度、历史记录、已结束需求、顾问和新增需求。

**状态 E：没有有效正式需求，仅有历史需求**
- 展示历史需求，并提供“新增找车需求”；
- 不新增独立一级 Tab“我的找车”。

页面判断依据必须使用“有效找车资格 + 找车申请状态 + 正式 demand 状态”，不得使用已废弃的“代淘客户/代淘中”概念。

### 客户进入小程序时的公告检查

进入客户小程序后，在不改变 3 个一级 Tab 的前提下执行轻量公告检查：
- 有符合条件且当天未自动展示的公告 → 最多弹出 1 条公告；
- 无有效公告、公告已停用、或当天已展示 → 直接进入正常业务页面；
- 公告属于 Overlay/弹层能力，不新增一级 Tab，也不改变车源首页业务结构。

## 17.2 车源首页

展示：
- 在售车源总数
- 今日新增车源数
- 城市/地区入口
- **顶部 Banner / 运营位 `HOME_TOP`：单个 Banner 区域，可轮播 3–5 张；首屏展示，页面下滑后让位于车源内容；主要承载名邦自有车源、服务与活动。**
- Banner 内容由 PC 后台轻量配置管理：placement、图片、标题、可选跳转、排序、启用/停用、生效时间、失效时间。V1 仅注册 `HOME_TOP` 与 `VEHICLE_DETAIL` 两个 placement；不得扩展成任意运营位/广告位平台，也不建设广告计费、人群定向、CPC/CPM、复杂投放计划或推荐算法。
- 来源快捷切换
- 搜索
- 主筛选
- 独立排序入口
- 车辆 Feed

### 在售 Feed
- `normal`：进入
- `locked`：继续进入，并明确标记“已锁定”
- `trading`：不进入普通 Feed
- `sold/completed`：不进入
- `offline/unavailable`：不进入
- `platform_visibility = hidden`：不进入

已锁定车辆：
- 仍可进入详情；
- 他人锁定可登记候补；
- 自己锁定可进入相关锁车/交易进度。

已售/已下架车辆：
- 退出普通 Feed；
- 历史详情仍可从收藏、推荐、锁车/交易等已有业务入口访问；
- V1不因此新增独立“浏览历史”。

### 来源快捷切换
客户“车源”Tab 的来源快捷切换固定只保留 3 个：
- **批发车源**
- **名邦车源**
- **4S店车源**

默认规则：
- **批发车源默认选中**；
- 客户进入“车源”Tab 时，默认直接看到批发车源 Feed；
- 原来的“全部车源”客户侧来源入口正式取消，不得恢复为默认来源或独立快捷切换项；
- 客户切换到名邦车源 / 4S店车源时，继续继承当前搜索词、筛选条件、地区条件和排序条件，不重置用户上下文。

### 批发车源页顶部双入口
当当前来源为“批发车源”时，批发 Feed 上方固定保留两个来源机会入口，顺序固定：
1. **名邦车源**
2. **4S店车源**

这两个顶部入口与来源快捷切换用途不同：
- 来源快捷切换：直接把整个主 Feed 切换到对应来源；
- 顶部双入口：客户浏览批发车源时，持续露出当前条件下的名邦 / 4S 车源机会。

条件继承：
- 客户当前搜索词、品牌/车系、价格、年份、里程、更多筛选、地区和排序条件，同时作用于批发 Feed、名邦顶部入口预览、4S 顶部入口预览；
- 若某来源存在完全符合当前条件的在售车辆，入口预览按当前排序规则取第一辆/首个结果作为预览；
- 若没有完全符合当前条件的车辆，入口仍然保留；只要该来源仍有在售车辆，就直接按当前条件选取最接近的车源作为预览，不额外展示“暂无完全匹配 / 为您展示相近车源”等提示文案；
- “最接近”在 V1 使用确定性 fallback，不使用 AI，也不调用正式 demand 匹配引擎。优先级固定为：**车型/车系相关性 > 品牌相关性 > 年份接近度 > 价格接近度 > 里程接近度 > 地区接近度 > 颜色/其他普通筛选接近度 > 当前排序作为最终 tie-breaker**；
- fallback 首要目标是保持车型/品牌意图，不得仅为了满足年份、价格等次要条件而优先跳到完全无关品牌/车系；
- 若该来源当前一辆在售车辆都没有，入口仍然保留并展示空状态，不得伪造车辆、不得为了保持卡片完整而展示不存在的资源；
- 顶部入口不得因为“无完全匹配车辆”而消失。

- 品牌
- 车系
- 车型
- 关键词
- 里程表达式

识别如：
- 3万公里

- 更多

来源不塞进“五个主筛选”。

### 排序

V1 固定排序项：
- **最新上架（默认）**
- 综合排序
- 价格从低到高
- 价格从高到低
- 年份从新到旧
- 里程从少到多

原则：筛选决定“哪些车留下”，排序决定“留下来的车按什么顺序出现”。

### 品牌/车系
- 品牌单选；
- 车系单选；
- 可只选品牌；

## 17.3 地域逻辑

客户和员工每次**新鲜进入** C01/E02 车源主列表，地区默认均为**全国**。
- 定位仅用于帮助客户/员工快速选择城市，不得自动套用地域筛选；
- 用户主动选择某城市/全国后，该选择只属于当前查询上下文；
- 从车辆详情使用“返回”时恢复进入详情前的完整查询上下文（来源、搜索、筛选、地区、排序、滚动位置等）；
- 从外部/直达入口或点击“主页”重新进入主列表时视为新鲜进入，地区回到全国，不做跨新鲜入口的持久地域状态。

## 17.4 三类车源搜索、条件继承与排序优先

客户侧不再使用“全部车源”作为默认混合 Feed。三类来源通过“批发车源 / 名邦车源 / 4S店车源”快捷切换分别浏览，其中**批发车源为默认来源**。

统一条件原则：
- 当前搜索词、筛选、地区和排序是同一套客户查询上下文；
- 切换来源时继承上述条件；
- 在批发车源页，顶部名邦 / 4S 两个入口预览也使用同一套条件；
- 不得因为来源切换或点击顶部入口而静默清空客户已经设置的查询条件。

默认排序：
- 客户进入车源 Tab 时默认使用**最新上架**；
- “综合排序”继续保留为可选项；
- 客户主动选择价格、年份、里程或综合排序后，以客户当前选择为准。

当客户主动选择“综合排序”时，继续使用既有综合业务排序逻辑：
- 用户主动搜索时，相关性优先；
- 同等匹配下继续遵循来源/地域等业务优先规则；
- 综合排序只作用于当前正在浏览的来源或入口预览结果，不得重新把三类来源混成“全部车源”默认 Feed。

批发页顶部名邦 / 4S 入口的完全匹配、相近车源与空状态规则按 17.2 执行。

## 17.5 客户车辆详情

### 固定自定义顶部导航

C01-01 从首屏开始就使用固定自定义顶部导航，不采用首屏按钮覆盖车辆大图、下滑后再切换吸顶的两阶段导航，也不得同时显示微信返回和另一套自定义返回。

功能结构固定：

- **有合法上一页：返回 ｜ 分享车源 ｜ 车型名称 / 车辆标题**
- **从微信好友、朋友圈、二维码等外部直接进入且没有合法上一页：主页 ｜ 分享车源 ｜ 车型名称 / 车辆标题**

规则：
- “返回 / 主页”占同一个导航位置，二选一；
- “分享车源”固定存在；
- 顶部直接显示当前车辆车型名称 / 车辆标题；
- 微信右上角官方胶囊继续保留；
- 自定义导航必须避开微信官方胶囊；
- 客户端“主页”回 C01 车源；
- 不在车辆详情底部新增“首页”按钮；
- 不增加长期显示的“店铺主页”大按钮；
- 首屏导航不得压在车辆大图上。

图标样式、字号、间距等视觉细节留到低保真。

客户安全详情至少包括：
- 4:3 图片轮播；
- 点击任意照片进入全屏预览；
- 完整车型/年款/里程/排量/变速箱/颜色/地区等；
- 当前客户价格/价格咨询；
- 车况描述；
- 服务/购买说明（不含已取消的到手价费用报价）；
- 当前名邦销售顾问；
- 收藏；
- 顾问咨询入口；
- **可选日期辅助区**：由 `vehicle_detail.show_listing_dates` 控制，默认关闭；开启时显示“上架时间 + 第二时间”。上架时间取当前 listing cycle `started_at`；名邦/4S人工车第二时间显示“上传时间”（系统首次创建/上传事实），批发/JYT车第二时间显示“平台收录时间”（`first_seen_at`），不得把首次收录时间伪称为上游真实上传时间；
- **详情运营位 `VEHICLE_DETAIL`**：复用 P12 Banner 后台；没有当前有效内容、停用、未到生效时间或已过失效时间时整个模块不渲染、不留空白。

### 核心 CTA
车辆正常可售：
**收藏 ｜ 我要这辆车**

车辆已被其他客户正式锁定：
**收藏 ｜ 登记候补**

不在底部同时摆“咨询顾问 / 我要这辆车 / 锁车”三个并列主按钮。

“咨询顾问”放在顾问信息或其他内容区域。

客户侧不直接提供“正式锁车”按钮；“我要这辆车”只创建明确车辆意向/咨询，由销售后续根据业务办理锁车。

“我要这辆车”、登记候补、咨询顾问等人工服务动作均执行手机号服务门槛。

收藏不执行手机号服务门槛，也不要求头像/昵称。点击收藏后必须先完成收藏；若客户资料未完善，可在收藏成功后按“每天最多主动提醒 1 次”的频控提示完善资料，拒绝完善不得回滚收藏。

车况必须区分车源方描述与名邦实际检测结果；没有实际检测不得暗示已检测。

档案/报告可包括出险、4S维保、里程、第三方检测；行驶证、绿本、保单等原件不直接展示客户。

### V1 极简复制白名单

复制只服务真实高频业务沟通，**不是“所有可见字段都可复制”**。复制动作只能使用当前页面已经经过权限/数据范围校验后合法可见的值，不得通过剪贴板动作请求、恢复或暴露更高权限数据。

V1 仅专门支持以下复制对象：
1. 车辆名称 / 完整车型；
2. 车况描述；
3. PC 车源管理 VIN（PC 可使用轻量复制图标/系统复制交互）；
4. 客户手机号；
5. 客户原始姓名 / 客户昵称 / 微信昵称；
6. 销售自定义客户称呼 / 备注名；
7. 客户画像摘要（只复制已经存在的人工维护核心摘要，不自动拼接全部画像结构化字段）；
8. 客户原始“帮我找车”要求；
9. 销售整理后的找车描述；
10. 需求说明 / 业务背景。

移动端普通业务文本采用长按复制，成功轻量提示：**“已复制”**。客户手机号同时支持“点击拨打 + 长按复制”。微信昵称与微信号严格区分，本轮不新增微信号字段。

以下字段不专门提供复制交互：年款、里程、颜色、地区、上架/上传/收录日期、客户等级、标签、负责人、单条普通 CRM 跟进、锁车/交易编号、普通状态、普通系统 ID、各画像子字段、各结构化找车条件等。此前提出的“标准整车摘要复制”由本极简白名单取代，不进入 V1。

### 图片全屏预览与保存

客户和员工端都支持：
- 点击图片进入现有全屏图片预览；
- 左右滑动整组图片；
- 当前序号；
- 双指缩放；
- 双击放大/还原；
- 关闭返回原图片位置；

## 17.6 “帮我找车”客户首填表单

客户不需要理解系统内部的“硬条件 / 可接受范围 / 偏好”。首填目标是用尽量简单的方式表达：**我想找什么车。**

所有客户都可以填写，但“提交找车需求”属于需要人工服务的高意向动作，提交前必须通过手机号服务门槛。授权成功后先保存**找车申请/找车意向**，再根据客户当前有效找车资格决定是否立即创建/激活正式 `demand`：
- 有正式找车权益 → 直接创建/激活正式 demand；销售匹配描述完成解析后再进入持续规则匹配；
- 无正式找车权益 → 显示“需求已提交 / 等待服务确认”，暂不进入持续匹配，待后台人工开通后再创建/激活正式 demand。

### 当前冻结字段

**想找什么车**

**车辆价格预算**
- 最低价格 —— 最高价格

**补充条件（可选）**

上牌年份：
- 最低年份 —— 最高年份
- 尽量使用年份选择器，不建议纯手填

里程范围：
- 最低里程 —— 最高里程

车况要求（单选）：
- 原漆或极少补漆
- 原版补漆较多
- 有覆盖件更换
- 不限车况

颜色偏好（多选）：
- 黑色
- 白色
- 灰色
- 银色
- 蓝色
- 红色
- 其他
- 不限

地区偏好：
- 结构化地区选择优先；
- 同时允许表达“江浙沪”“全国均可”等自然区域描述。

**其他要求**
- 自由文本，例如：“必须哈曼卡顿、不要白内饰、最好一手车等。”

最后操作：**提交找车需求**。

### 提交后的权益分流

提交按钮对所有客户开放，但提交结果按有效找车资格分流：

- 已具备正式找车权益：保存申请后直接创建/激活正式 demand；随后由销售整理/确认匹配描述，准备度 ready 后才进入持续规则匹配；
- 尚未具备正式找车权益：保存申请并进入等待服务确认，不得显示“持续匹配中”；
- 后台人工开通后，从该申请创建/激活正式需求；
- 客户等级与正式需求状态必须分开：等级/人工授权决定“能不能进入正式持续匹配”，`active / paused / completed / cancelled` 只描述正式 demand 的生命周期。

### 输入方式原则
**可以标准化的尽量选择；个性化内容才自由输入。**

自由输入：
- 想找什么车
- 其他要求

结构化选择/输入：
- 价格预算
- 年份
- 里程
- 车况
- 颜色
- 地区

# 19. 批发电话、publisher 缓存与上游登录凭证边界

## 19.1 批发电话权限与按需获取

- 客户端永远不显示上游电话；
- 批发电话为独立 `can_view_wholesale_phone` 权限；
- 不在车源同步时批量获取电话；
- 只有授权销售实际需要时才获取。

流程：
**车辆读取 `upstream_publisher_id` → 按 `(source_platform, publisher_id)` 查名邦本地 publisher 电话缓存 → 有缓存直接使用 → 没有缓存才调用 Collector → Collector 再向 JYT 获取该发布人电话 → 成功后写入/更新 publisher 缓存。**

“最新电话”直接按同一 `publisher_id` 调用 Collector，成功后覆盖该发布人的当前缓存；失败保留旧号码。电话缓存按发布人维护，`car_code` 只作为车辆唯一标识，**不参与电话查询**。

合法获得当前有效号码后，员工端提供**“拨打”**动作：
- 继续复用现有批发电话查看/获取权限，不新增 `can_call_wholesale_phone`；
- 点击“拨打”只调起手机系统拨号确认，由员工最终确认；
- 有有效本地缓存时直接使用缓存号码，不因拨号重新调用 Collector/JYT；
- “最新电话”与“拨打电话”是两个独立动作；
- 客户端永远不存在该拨打入口；
- 本轮不把上游电话加入复制白名单。

## 19.2 publisher 电话缓存历史

每个 publisher 至少保留：
- publisher_id；
- 当前电话；
- 当前联系人（如上游提供）；
- 最近获取时间；
- 当前号码状态；
- 历史号码。

销售发现号码失效/联系人变化时，可主动“最新电话”：
- 新号码成为当前号码；
- 旧号码进入历史；
- 不直接覆盖删除旧事实。

电话获取/使用日志至少记录：
- 操作人；
- 时间；
- 车辆；
- publisher；
- 关联客户/需求（有上下文时）；
- 获取/使用结果。

## 19.3 名邦 API Token 与 Collector 内部鉴权必须严格分开

### A. 名邦 API Token
用于：
**外部采集/检测程序 → 名邦固定三个车源同步业务 API**。

它保护名邦自己的 API。

### B. Collector 内部鉴权
用于：
**名邦后端 → Collector 电话接口**。名邦只保存/引用 Collector 连接所需的内部鉴权信息；JYT URL、JYT Token、Header/调用细节均由 Collector 自己管理。

两类凭证必须分开存储、分开权限、分开日志，绝不能混用。

## 19.4 JYT 凭证边界

- 名邦不保存、不展示、不轮换 JYT Token；
- JYT 凭证只存在于 Collector；
- 名邦后台只能管理 Collector 连接参数与内部鉴权状态/secret reference；
- 名邦普通日志不得出现 Collector 内部密钥或任何 JYT 凭证；
- Collector 连接修改与测试必须留审计。

1. 客户接口不得返回内部敏感字段再靠前端隐藏。

4. 金鱼塘原始字段/原始文字不得被员工或匹配词典覆盖。
5. 同车更新/改价不得重复新增车辆。
6. 锁车/交易中的供应异常不得自动取消业务。
7. 已收意向金的锁不得自动过期释放。
8. 单车价格覆盖不得改写上游原始价格。
9. 分享链接不得携带员工内部权限。
10. System Admin 与员工业务账号不得混成同一账号模型。
11. 普通业务通知失败不得影响业务事实本身。
12. 正常业务数据不得物理删除历史。
13. 员工离职不得删除客户、跟进、画像或历史业务；必须保留离职交接批次来源。
14. 客户画像、统一 CRM 跟进、需求说明不得合并成一个反复覆盖的总备注。
15. 员工车辆详情“推荐给客户 / 锁车”是外层高频动作；敏感经营能力仍进入内部模式并做后端权限校验。
16. V1 不建设客户微信小程序订阅消息提醒体系。
17. 客户小程序公告只在用户主动进入小程序时展示，不得实现成离线订阅推送。
18. 未具备正式找车权益的客户提交找车申请后，不得直接进入 active demand 或持续匹配。
19. 找车核心代码不得用“普通/粉丝/VIP”等等级名称写死权限。
20. 找车申请/意向与正式 demand 必须分层；pending 申请不得伪装成持续匹配中。
21. “代淘中/代淘客户”不得恢复。
22. 存在 pending 找车申请的客户属于公海保护对象。
23. 已 active demand 不得因后续等级/权益变化被系统自动暂停、取消或结束。
24. 客户正常浏览不得强制手机号、昵称、头像；手机号只在需要人工服务的业务动作触发。
25. 手机号授权成功后必须自动继续原业务动作；拒绝授权不得创建对应正式人工服务对象。
25A. 头像/昵称只能持续引导完善，不得作为进入、浏览、搜索、详情、收藏或高意向业务提交的硬性门槛；统一提示文案为“完善头像和昵称，方便后续为您提供更顺畅的服务。”
25B. 收藏必须先成功，再可提示完善头像/昵称；拒绝完善不得撤销收藏。同一客户资料未完善时每天最多主动提醒 1 次。
25C. 微信身份负责稳定映射 `customer_id`；头像、昵称、手机号均不得作为客户唯一身份主键。
26. 客户侧“我要这辆车”不得自动锁车、自动创建交易或自动创建 demand。
27. 客户侧候补是独立业务对象，不得被实现成咨询或自动升级锁车。
28. 名邦普通销售/经理/店长底部导航固定“工作台 / 车源 / 客户 / 我的”；4S 成员共用同一员工端但按既有权限隐藏无权使用的客户业务入口，不得另造独立 4S IA。
29. 客户机会不是咨询，不产生咨询 SLA，不逐条推送普通浏览，不做 AI 意向评分。
30. 客户原始找车表达不得直接作为 V1 自动匹配主输入；自动匹配主输入是销售匹配描述经确定性规则解析出的结构化条件。
31. V1 找车匹配不得使用 AI 理解话术、车型版本、配置或车况；unknown 不得靠猜测补齐。
32. 匹配核心不得退化为单一分数模型；候选必须区分高匹配/可接受/待确认/不匹配，评分仅可用于同层排序。
33. 明确不符合与信息 unknown 必须分开；unknown 硬条件进入待确认候选而不是直接淘汰或自动判符合。
34. 匹配词典必须有作用域和优先级；同优先级冲突不得自动猜。
35. 新增/修改匹配词只重算受影响范围，不得无脑全库重算；规则不得覆盖上游原始文字。

37. 客户跟进始终使用统一 CRM 时间线；demand 页面仅按 demand_id 过滤关联跟进，不得另建重复跟进系统。

## CR-006 authoritative vehicle master addendum

- Model identity is ID-based; names are display/snapshot/search text, not identity.
- JYT `model_id` is retained and resolves through a source mapping to local `vehicle_model_id`.
- JYT unknown model never causes vehicle loss. It stores vehicle/source facts, leaves `vehicle_model_id=NULL`, and enters `pending/conflict`.
- Pending/conflict JYT vehicles may degrade-display if other visibility rules pass, but model-master-dependent precise filters/recommendation evaluate unknown/not-positive until resolved.
- Model source profile enrichment never silently overwrites conflicting or human-locked local facts.
- Manual formal publish requires a valid concrete model identity.
- Customer/staff common filters include brand/series, customer display-price range, model year, mileage, energy, displacement, exterior color, gearbox, region, source and sort including model-year descending.

## CR-006.2 authoritative alignment

### Lock and customer ownership

- A Mingbang or 4S manually supplied vehicle may be locked whether or not `internal_wholesale_price_cents` is present. Lock validation uses vehicle business state and competing active lock/transaction truth only.
- `/admin/customers/{id}:reassign-owner` requires `crm.owner.reassign`. Public-pool put/claim remains `crm.public_pool.manage`.

### Employee manual vehicle publishing

- E02 keeps the visible “发布车辆” entry. E02-02 has no manual save-draft control and no preview control.
- Field changes are automatically persisted as one unfinished draft; navigation away flushes the last pending change. Re-entry offers exactly “继续上次” and “放弃重新发布”.
- Formal publish performs one server validation and returns the complete missing-field list. Required business inputs are source type, brand, series, concrete valid `vehicle_model_id`, model year, mileage, and city. Vehicle images are optional for formal publish; a manual vehicle may publish with zero real images and uses the unified default placeholder until real images are added.
- Customer list price may be empty and renders as “价格咨询”. Internal wholesale price, VIN, exterior/interior color, description, tags, and archive documents are optional.
- A manually supplied vehicle cannot enter formal listing first and then complete required publish fields later. Normal authorized editing after a valid formal publish remains available.

### Vehicle detail, color and condition

- “车辆信息” is a fixed 3×3 grid: 上牌时间 / 表显里程 / 变速箱；排量或能源 / 车身|内饰 / 车辆位置；电池容量 / 纯电续航 / 总功率. The former 厂家类型 / 车辆类型 / 新车指导价 row is removed.
- `sub.tags` appears above `description` in the 车况 area. Source tags retain JYT provenance; manual selected tags retain manual provenance and are not promoted to verified inspection facts.
- UI money formatting converts cents to yuan and renders compact 万 text, for example 128000 yuan stored as 12800000 cents renders `12.8万`; no “元” suffix is appended.

### Edit routing by source type

- Internal mode shows the same “编辑” control for `wholesale`, `mingbang`, and `four_s`.
- `wholesale` routes to E02-05, a read-only projection of collected source data. Sensitive phone/internal-price fields remain independently permission-filtered. Client and backend reject PATCH mutation with `SOURCE_TYPE_READ_ONLY`; the database guard permits source-fact mutation only for the JYT ingest origin.
- `mingbang` and `four_s` route to writable E02-02 subject to `vehicle.edit`, ownership/data scope, optimistic version, and normal state checks.

### Banner and phone

- `HOME_TOP` and `VEHICLE_DETAIL` each return 0..5 effective banners: 0 hides the region, 1 renders a still image, and 2..5 render a carousel; values beyond five are truncated by effective sort order.
- Internal phone actions are “拨打” and “最新电话”. “拨打” uses a valid publisher cache and calls Collector only when no cache exists. “最新电话” bypasses the local cache read and calls Collector by publisher identity. A failed refresh preserves the old number. All Collector fetches for the same publisher share one single-flight key.
- P03 manages only Collector Base URL, relative Phone Path, internal-key status/secret reference, timeout and “发送测试”; JYT Base URL/Token/Header/callCode details stay inside Collector.
- Phone requests are keyed by `publisher_id / upstream_publisher_id`; `car_code` is not used for phone lookup. Collector/JYT runtime details remain external implementation evidence, not Mingbang configuration.
