# C1｜批发电话 / Collector 边界

当前冻结：

- 批发电话由 Collector / 采集端负责向上游获取，名邦端不直接绕过 Collector 调 JYT。
- 采集端电话接口业务形态：`POST /integrations/jyt/phone`，输入 `{car_code}`，返回 `{phone}`，内部 Key 鉴权。
- 名邦普通查看 / 拨打优先使用 `publisher_phone_cache`；缓存已有 phone 时可直接用，不因普通查看主动打上游。
- “获取最新电话”绕过普通缓存读取，通过 Collector 获取；成功后覆盖当前缓存。
- `publisher_phone_history` 只做审计 / 历史。
- 不同上游发布人可以并发；同一发布人的“获取最新电话”采用 single-flight 合并。
- 普通查看 / 拨打不调用上游。
- 上游 `user.id` 统一映射为：
  > `upstream_publisher_id`
- R11 / R12 后电话当前唯一身份维度统一为 `upstream_publisher_id`。
- 电话查看 / 拨打 / 获取最新电话继续是独立敏感能力并保留审计。
- 名邦侧配置 Collector Base URL、内部 Key，并支持连接测试。

# C3｜隐藏 / 客户可见性

当前冻结：

- “隐藏”与“下架”严格不同。
- 隐藏：
  > 车辆仍然是有效在售车，只是暂时不进入客户端公开 Feed。
- 下架：
  > 当前真实在售结束 / 当前不可售。
- 隐藏车辆在员工后台仍可管理。
- 隐藏 / 恢复显示属于员工车辆详情 → 内部操作区的正式动作。
- 受权限、数据范围、当前车辆状态控制。
- 不采用车辆列表卡片“随手快捷隐藏”作为正式主操作。
- 适用场景包括资料待检查、临时不公开、客户专属可见性等。
- 上传后可以进入“立即公开 / 暂不公开”的业务选择。
- 隐藏与 Matching / Priority / 客户专属可见性的精确历史边界必须在 Phase 1.5 历史遗漏扫描中回查原 C2/C3 文件。

# D1. R1_账号员工组织角色权限

# R1｜账号 / 员工 / 组织 / 角色 / 权限｜滚动合并当前版

## 1. 模块状态

- `BUSINESS_REVIEW = COMPLETE`

- 不自动启动 DB / API / Worker / Storage / Tests 等工程施工。

---

## 2. 员工身份体系

员工统一采用四类主角色：

- 普通销售
- 经理
- 店长
- 4S 成员

同一员工同一时刻只有一个主角色，不允许同时作为名邦销售/经理/店长和 4S 成员。

同一自然人在员工体系中只保留一个 `employee_id`：

- 调店复用原 `employee_id`；
- 升降职复用原 `employee_id`；
- 离职后重新入职复用原 `employee_id`；
- 历史操作、历史责任、历史客户关系不得因角色变化而改写。

---

## 3. System Admin 独立身份域

System Admin 与员工账号完全分离：

- 不属于普通销售 / 经理 / 店长 / 4S 成员角色树；
- 不自动进入接客池；
- 不自动承担客户、锁车、交易等销售业务；
- 不因为是 System Admin 自动获得员工业务管理权；
- 同一真人如既做系统管理又做销售业务，需要两个独立身份；
- System Admin 只能由 active System Admin 管理；
- 系统至少保留 1 个 active System Admin，不能停用最后一个。

---

## 4. 组织与数据范围

### 4.1 名邦员工

名邦员工同一时刻只有一个主归属门店。

跨门店 / 跨团队管理不通过多重正式归属实现，而通过：

> **权限 + 数据范围授权**

员工调店继续复用原 `employee_id`，历史记录保留原发生时的门店、角色和责任事实。

同一门店允许存在多个店长。

跨店管理不新增“区域经理 / 总经理”等额外角色层级，继续通过权限和数据范围解决。

### 4.2 4S 成员

系统不存在“4S 店组织”层级。

4S 成员是独立合作员工账号，可代表某一家合作 4S 店或长期合作方，但不挂在系统中的 4S 组织下面。

---

## 5. 权限模型

统一采用：

> **角色默认权限 + 员工个人权限覆盖 + 数据范围 + 对象状态**

其中：

- 角色默认权限决定基础能力；
- 员工个人明确授权 / 禁用可覆盖角色模板；
- “明确禁止”优先于角色模板默认允许；
- 个人授权不能突破本人数据范围；
- 数据范围决定“能对哪些对象操作”；
- 具体权限决定“能做哪些敏感动作”；
- 当前对象状态继续参与最终校验。

角色、权限、数据范围变更原则上立即生效，旧登录态不得继续保留已撤销能力。

---

## 6. 禁止自我提权与越级授权

任何员工都不能：

- 给自己提升角色；
- 给自己增加敏感权限；
- 自行扩大自己的数据范围；
- 授予别人超出自己授权边界的能力；
- 通过中间人绕过上述限制。

本人的角色、敏感权限、数据范围如需调整，必须由另一名具备相应授权能力且范围足够的管理人员处理。

---

## 7. 员工管理边界

### 普通销售

不能管理员工或权限。

### 经理

在授权团队范围内进行日常管理，例如：

- 接客状态；
- 业务交接；
- 日常人员状态管理。

经理不能：

- 自行提升角色；
- 修改超出自身范围的敏感权限；
- 创建或管理店长；
- 越级扩大数据范围。

### 店长

可在本店范围内管理员工，包括：

- 新增员工；
- 在职 / 离职；
- 普通销售 ↔ 经理角色调整；
- 接客状态；
- 数据范围。

敏感权限仍继续按独立授权规则处理。

---

## 8. 角色模板

角色模板是实时默认权限，不是员工入职时复制一次的永久快照。

因此：

- 模板新增默认权限 → 现有同角色员工同步生效；
- 模板取消默认权限 → 现有同角色员工同步失去；
- 员工个人明确授权 / 禁用继续保留；
- 如果模板变更会让员工失去正在负责业务所必需的资格，必须先完成业务交接，再使降权正式生效。

---

## 9. 离职、停用、复职

员工进入 `inactive / 离职` 后：

- 立即失去员工端访问；
- 当前业务权限立即失效；
- 旧登录态失效；
- `employee_id`、历史操作、历史客户关系和审计记录全部保留。

尚未完成业务交接时，由有管理权限的在职人员处理，不允许离职员工继续操作。

重新入职：

- 复用原 `employee_id`；
- 按新的当前角色、权限和数据范围重新授权；
- 不自动恢复离职前权限；
- 不自动拿回已经交出去的客户或业务；
- 接客状态默认关闭；
- 旧登录态不得复活。

---

## 10. 接客状态

普通销售、经理、店长可以自行开启 / 关闭自己的接客状态。

经理 / 店长可在授权范围内调整下属接客状态。

正常接客池不得出现“没有任何合格接客员工”的状态，因此不能关闭最后一名合格接客员工。

员工从 inactive 恢复 active 后，接客状态默认关闭，需要本人或管理人员重新开启。

---

## 11. 角色切换与调店

员工切换到与原角色不兼容的新角色前：

> **原角色下仍在进行中的业务必须先处理或交接。**

员工从 A 店调到 B 店前：

> **A 店仍在进行中的客户及业务必须先完成交接。**

调店后：

- 当前权限和数据范围按 B 店重新生效；
- 历史记录不改写。

---

## 12. 4S 成员权限边界

4S 成员：

- 不能管理员工；
- 不能管理同类其他 4S 成员；
- 默认只管理自己有权管理的 4S 车源；
- 默认不获得名邦 CRM、找车、咨询、锁车、交易等客户业务能力；
- 不能执行“一键转名邦”；
- 不能查看名邦内部价 / 批发价。

4S 成员停用后的车辆责任承接由 R2 / R9 处理。

---

## 13. 车辆管理边界（R11 回补后的当前规则）

名邦员工管理人工车辆时：

> **不再以“是否本人上传”作为权限边界。**

在本人正常数据范围内，可管理：

- 自己上传的名邦车；
- 其他名邦员工上传的名邦车；
- 名邦员工上传的 4S 合作车；
- 4S 成员上传的 4S 合作车。

因此，不再把“是否本人上传”作为额外权限门槛。

但是下列敏感动作仍继续独立权限控制：

- 上游电话；
- 隐藏 / 恢复；
- 调价；
- 上下架；
- 客户展示价覆盖。

原则保持：

> **数据范围决定能管哪些车；具体敏感权限决定能执行哪些敏感动作。**

---

## 14. 内部模式与内部价格（R11 回补后的当前规则）

内部模式本身不设置独立“进入权限”。

名邦员工进入内部模式后：

> **可查看内部价 / 批发价，不再另设单独查看权限。**

4S 成员不能查看名邦内部价 / 批发价。

进入内部模式不等于获得全部敏感操作能力。实际按钮和动作仍按：

- 当前角色；
- 数据范围；
- 具体敏感权限；
- 当前车辆状态；

进行裁剪和后端复核。

---

## 15. 审计

以下关键变化必须保留审计：

- 角色；
- 权限；
- 数据范围；
- 在职 / 离职状态；
- 重要授权变化。

至少保留：

- 操作人；
- 操作时间；
- 修改前；
- 修改后。

不强制每次填写修改原因，除非具体业务模块另有要求。

## 16. 当前明确废弃的旧方向

以下旧规则不得重新进入当前主线：

1. “编辑非本人上传车辆”本身作为独立敏感权限；
2. 名邦员工查看内部价 / 批发价必须额外独立权限；
3. 进入内部模式就自动获得全部敏感操作权限；
4. System Admin 自动拥有员工业务管理权；
5. 4S 店组织层级；
6. 同一员工同时挂多个正式主归属门店；
7. 员工可自我提权或越级授权。

## 2. 三类车源

当前车源类型：

1. 批发车源（JYT / 上游同步）；
2. 名邦车源；
3. 4S 合作车源。

名邦车源与 4S 合作车源属于人工车源体系。

## 3. 批发车上游事实

JYT 上游原始车辆事实和原始价格：

> **只读。**

普通人工不能直接改写。

上游同步可更新：

- 上游价格；
- 里程；
- 图片；
- 描述；
- 其他上游事实。

但上游更新不得覆盖名邦本地业务字段、人工隐藏状态、客户业务关系等本地业务事实。

---

## 4. 批发车转名邦后的生命周期

批发车成功“一键转名邦”后：

- 原批发车自动退出当前客户可售展示；
- 新名邦车进入独立名邦车生命周期；
- 上游后续再次同步同一车辆时，不能重新生成一台新的可售批发车；
- 继续保留必要的上游来源与历史关联。

因此：

> **已完成转名邦的批发车不能因为上游再次出现而复活为可售批发车。**

---

## 5. 一键转名邦权限（R11 回补后的当前规则）

普通名邦销售默认可以对批发车执行：

> **一键转名邦**

该动作不再另设独立权限门槛。

4S 成员不具备该能力。

具体转换后的价格与图片规则分别由 R4 与图片模块负责。

---

## 6. 批发车内部详情（R11 回补后的当前规则）

普通名邦销售可以进入批发车内部编辑 / 详情入口查看完整详细参数。

但：

- JYT 上游原始车辆事实只读；
- JYT 上游原始价格只读；
- 普通员工不能人工覆盖这些上游事实；
- 名邦本地业务字段和业务动作继续按自身规则处理。

“进入批发车内部详情”不等于获得修改上游事实的能力。

---

## 7. 上游下架

批发车以上游当前在售状态为重要在售依据。

上游确认下架后：

- 名邦侧该批发车同步退出正常可售；
- 不再正常展示；
- 不再参与正常匹配；
- 不再新增普通销售业务。

已经存在的 Lock / Transaction 等进行中业务事实不得被直接删除，继续按 R8 处理。

---

## 8. 上游下架后重新出现

同一个上游 `car_code` 下架后重新变为在售：

- 默认复用原车辆身份，不重复创建同一车辆记录；
- 开启新的 `listing_cycle`；
- 重新同步当前最新上游内容；
- 旧周期内容继续作为历史保留。

价格、里程、图片、描述等正常变化可以更新。

如果品牌、车系、具体车型、年款等核心身份信息发生明显冲突：

> **不得静默覆盖，标记异常并人工核实，防止上游复用 `car_code`。**

已经完成“一键转名邦”的车辆继续按第 4 条处理，不恢复成批发车。

---

## 9. 人工隐藏与上游更新

批发车被名邦人工隐藏后：

- 上游普通更新可以继续更新资料；
- 不能因为上游更新自动恢复客户展示。

只有名邦侧主动执行“恢复显示”，车辆才重新公开。

因此：

> **人工隐藏状态与上游内容同步分离。**

---

## 10. 隐藏与真实下架

“隐藏”和“真实下架”是两个不同业务状态。

### 隐藏

只是暂时不对客户公开。

隐藏 → 恢复显示：

> **不创建新的 `listing_cycle`。**

### 真实下架

代表当前一轮真实在售结束。

真实下架 → 后续重新上架：

> **开启新的 `listing_cycle`。**

历史仍属于同一个车辆身份。

---

## 11. 不做无依据的跨来源自动去重

没有 VIN 等可靠唯一身份依据时：

> **不能仅凭品牌、车型、年款、里程、图片相似就自动认定两个来源记录是同一实体车。**

因此不做“名邦 > 4S > 批发”的通用自动去重优先级。

只有存在明确业务关联时才确认同一实体关系，例如：

> **批发车一键转名邦。**

这种明确转换关系由系统自身维护。

---

## 12. 4S 合作车源不存在 4S 组织层级

系统不存在“4S 店组织”。

4S 成员是独立合作员工。

4S 合作车源可能来自：

- 4S 成员本人上传；
- 名邦员工上传并选择为 4S 合作车源。

---

## 13. 取消 4S 周期性在售确认机制

当前正式规则：

> **4S 车当前不执行定期在售确认流程。**

已废弃：

- 4S 定期确认在售；
- 超期自动暂停；
- 名邦代确认等配套机制。

车辆状态只因真实业务事件变化，例如：

- 人工下架；
- 隐藏；
- 成员停用；
- 当前车辆真实失效；
- 其他明确生命周期操作。

---

## 14. 4S 成员停用

4S 成员停用 / 停止合作后：

- 其本人名下仍在售的 4S 车源先暂停正常展示和匹配；
- 已存在的 Lock / Transaction 等存量业务不自动取消；
- 存量业务继续由名邦处理；
- 名邦可以重新指定当前负责人 / 管理责任并恢复仍有效车辆的业务；
- 不需要重新创建车辆；
- 车辆仍保持 4S 合作车源来源，除非后续按 R9 的当前规则主动修改 `source_type`。

---

## 15. 4S 车辆“接管”的正确含义（R11 回补）

名邦员工本来就在其正常数据范围内具备人工车辆管理能力。

因此 4S 成员停用后的“接管”是：

> **当前负责人 / 管理责任承接。**

不是：

> 名邦在 4S 成员停用之后才第一次获得车辆编辑能力。

车辆可管理范围继续由 R1 的数据范围与敏感操作权限决定。

---

## 16. 名邦员工上传的 4S 合作车源

名邦员工上传并选择为 4S 合作车源的车辆：

- 属于名邦公司业务资产；
- 不归属于任何 4S 成员；
- 创建销售可管理；
- 其他名邦员工在自身数据范围内也可管理；
- 经理 / 店长继续按角色、权限和数据范围管理；
- 4S 成员不会因为车辆类型是“4S 合作车源”就自动获得该车权限。

---

## 17. 4S 车负责人变化不自动改变来源

4S 成员停用、离职或责任移交后：

> **只改变当前负责人 / 管理责任，不自动改变车源来源。**

如果确实需要修改 `source_type`，按 R9 当前规则由有车辆管理能力的员工执行并审计。

---

## 18. 人工车发布与审核

当前业务不恢复“人工车辆必须审核后才能上架”的旧方向。

人工名邦 / 4S 车辆满足当前发布条件后可正式发布。

具体人工发布条件与档案规则由 R9 负责。

---

## 19. 当前明确废弃的旧方向

以下旧规则不得恢复：

1. 4S 店组织层级；
2. 4S 周期性在售确认；
3. 无 VIN 时按车型/里程/图片等自动认定跨来源同一实体车；
4. 已转名邦的批发车因上游再次出现而重新成为可售批发车；
5. 人工隐藏的批发车因普通上游更新而自动恢复展示；
6. 普通名邦销售进入批发详情后可人工改写 JYT 原始事实；
7. 普通名邦销售执行一键转名邦必须额外独立权限；
8. “4S 成员停用后名邦才获得车辆编辑能力”的解释。

---

## 20. 当前结论

`BUSINESS_REVIEW = COMPLETE`

本文为 R2 当前滚动合并版。

后续模块如反向修改 R2，继续按“保留非冲突内容、只替换冲突项”滚动更新。

# D3. R3_车型主数据与JYT车型映射

# R3｜车型主数据 / 车型字典 / JYT 车型映射｜当前版

## 1. 模块状态

- `BUSINESS_REVIEW = COMPLETE`
- 当前阶段：Phase 1｜业务重审
- 本文仅用于业务规则收口与主线合并
- **不自动启动 DB / API / Worker / Storage / Tests 等工程施工**
- 后续工程实现统一进入 Phase 2｜全项目工程闭环

---

## 2. 本地车型字典正式结构

本地车型字典采用：

> **品牌 → 车系 → 具体车型**

例如：

> 奥迪 → A6 → 2024款 45 TFSI 臻雅型

“年款”不是独立目录层级，而是具体车型自带的结构化字段。

例如：

- 具体车型：2024款 45 TFSI 臻雅型
- 年款字段：2024款

年款字段主要用于批量筛选、批量选择和车型查询。

### 2.1 车型年款与上牌时间严格分离

必须区分：

- **车型年款**：具体车型自身属性
- **首次上牌 / 首次登记时间**：具体车辆自身属性

例如：

> 一台“2024款 奥迪A6 45 TFSI”可以在 2023、2024 或 2025 年首次上牌。

两者互不推导、互不覆盖。

---

## 3. JYT 车型资料处理原则

JYT 第一次传入车辆时，只要已经提供完整车型资料，就直接保存并正常使用。

例如：

> 2024款 奥迪A6 45 TFSI 臻雅型

JYT 已明确提供的以下资料，首次入库即保存：

- 品牌
- 车系
- 年款
- 具体车型名称
- 排量
- 变速箱
- 排放
- 能源类型
- 其他 JYT 已明确提供的车型级资料

即使本地车型字典还没有完成正式映射，JYT 车辆仍然可以正常入库、发布、展示、搜索、筛选、参与业务和销售。

> **本地车型字典未完成映射，不能阻塞 JYT 车辆正常业务。**

---

## 4. 本地车型字典映射的真实作用

本地车型字典映射解决的是：

> **“这个 JYT 车型，在名邦自己的车型体系里正式归到哪个车型节点。”**

它不是用来重新补充或重新证明 JYT 已经提供的车型资料。

因此：

- JYT 负责提供并保存车辆自身取得的车型资料；
- 本地车型字典负责正式归属、结构化管理、筛选和后续统一维护。

---

## 5. 自动映射规则

### 5.1 完全一致

JYT 的完整车型名称与本地具体车型完全一致：

> **自动建立映射，不需要人工确认。**

### 5.2 找不到完全一致项

> 车辆仍正常发布，后台进入 **“车型字典归属待确认”**。

### 5.3 不做模糊猜测

> **完全一致自动映射；不完全一致进入人工确认。**

---

## 6. 本地字典缺项处理

本地缺少品牌、车系或具体车型时，不阻塞 JYT 车辆正常发布。

后台统一提示：

> **车型字典归属待确认**

管理员：

> **缺哪一级，补哪一级。**

补齐后建立正式映射。

---

## 7. 同一 JYT 车型只生成一条待处理任务

同一个 `upstream_model_id`：

> **只生成一条待确认任务。**

确认一次后：

- 现有同 ID 车辆统一建立本地归属；
- 后续同 ID 自动沿用；
- 不逐车人工处理。

---

## 8. 映射完成后不反向覆盖 JYT 原始资料

本地映射不得覆盖车辆已从 JYT 获取并保存的：

- 完整车型名称
- 年款
- 排量
- 变速箱
- 排放
- 能源类型
- 其他上游车型资料

本地车型字典负责：

- 品牌归属
- 车系归属
- 具体车型归属
- 筛选
- 搜索
- 车型管理
- 统一结构化引用

---

## 9. 映射冲突处理

同一个 `upstream_model_id` 后续内容与已确认映射明显冲突：

- 车辆业务继续；
- 不自动修改既有映射；
- 标记 **“车型映射冲突”**；
- 由有权限人员人工确认。

> **不阻塞卖车，但不能静默改乱车型主数据。**

---

## 10. JYT 名称规则

当前业务前提：

> **JYT 对同一品牌、车系、车型采用固定标准写法。**

因此：

- 不设计车型名称别名机制；
- 不设计同义词映射机制；
- 不为“同一车型多个 JYT 编号”设计额外复杂机制。

---

## 11. 本地车型节点修正

车型节点挂错品牌或车系：

> **直接修正节点归属。**

所有引用车辆跟随正确层级，不逐车修改。

---

## 12. 重复车型合并

重复车型节点：

> **保留一个正确节点，其余合并进去。**

合并时：

- 车辆引用迁移；
- JYT 映射同步迁移；
- 旧节点退出当前选择和筛选；
- 保留轻量“旧车型 A 已合并到车型 B”历史。

---

## 13. 旧车型保留

真实存在的旧年份车型长期保留。

只有：

- 录入错误；
- 重复并已合并；

才退出当前使用。

---

## 14. 人工上传与 JYT 入口分开

### JYT 批发车

> **先正常发布，后补本地车型字典映射。**

### 名邦 / 4S 人工上传

必须使用本地车型字典。

本地没有对应车型时：

> 由具备车型管理权限的人先补本地车型，再完成正式人工发布。

---

## 15. 人工上传车型固定资料

- 排量
- 变速箱

JYT 车辆不等待本地映射补这些资料。

# D4. R4_完整价格体系与查价权限

# R4｜完整价格体系 / 查价权限｜滚动合并当前版

## 1. 模块状态

- `BUSINESS_REVIEW = COMPLETE`
- 当前阶段：Phase 1｜业务重审
- 本文为 R4 当前有效业务规则。
- 已吸收 R11 对 R4 的客户展示价覆盖范围修正。
- 与本文冲突的旧价格规则均视为历史规则。
- 不自动启动工程施工。

---

## 2. 价格体系分层

### 2.1 批发车

保留上游原始价格事实，包括：

- `upstream_list_price`：上游标价；
- `upstream_wholesale_price`：上游批发价。

两者属于上游事实，不因客户展示逻辑互相覆盖。

批发车用于客户展示计算时使用 `base_wholesale_price`：

- 有上游批发价 → 基础批发价优先取上游批发价；
- 无上游批发价但有上游标价 → 基础批发价回退取上游标价；
- 两者都没有可用数字 → 无可用基础数字价格。

### 2.2 名邦 / 4S 人工车

人工车独立保存：

- 客户标价；
- 内部批发价（允许为空）。

名邦 / 4S 不参加 JYT 批发车统一阶梯加价。

---

## 3. 批发车客户展示价

批发车客户展示价按以下优先级：

### 第一优先级：单车客户展示价覆盖

有有效覆盖价：

> **直接显示覆盖价。**

### 第二优先级：统一加价规则

无覆盖价且加价开关开启：

> **`base_wholesale_price + 当前生效阶梯加价`**

### 第三优先级：加价关闭

无覆盖价且加价开关关闭：

> **显示上游标价。**

如果当前没有可用客户数字价格：

> **显示“价格咨询”。**

---

## 4. 客户展示价覆盖（R11 回补后的当前规则）

旧规则“覆盖价只适用于批发车”正式废弃。

当前：

> **批发、名邦、4S 三类车源均支持客户展示价覆盖。**

### 4.1 批发车

覆盖价优先于统一加价或其他批发车客户展示逻辑。

覆盖价：

- 只改变客户最终看到的价格；
- 不修改上游标价；
- 不修改上游批发价；
- 不修改基础批发价。

### 4.2 名邦 / 4S

- 有覆盖价 → 显示覆盖价；
- 无覆盖价 → 显示当前最新客户标价；
- 客户标价为空 → 显示“价格咨询”。

覆盖价只改变客户最终展示结果：

> **不改原客户标价，不改内部批发价。**

覆盖期间底层客户标价仍可继续修改。

取消覆盖后：

> **立即回到取消时最新客户标价；若最新客户标价为空则显示“价格咨询”。**

---

## 5. 覆盖价生命周期

客户展示价覆盖属于当前车辆当前在售周期业务规则。

批发车继续与 `listing_cycle` 绑定：

- 当前周期内有效；
- 真正下架并重新上架形成新 `listing_cycle` 后，不默认把旧周期覆盖价当成新周期当前价。

人工车后续具体周期继承行为如在 Phase 1.5 发现跨模块冲突，再统一收口；当前不得把旧批发车限定重新套回三类车的“是否支持覆盖”范围。

---

## 6. 覆盖价权限

客户展示价覆盖继续保留独立权限控制。

可按角色 / 具体员工账号授权。

无权限时：

- 前端不显示对应入口；
- 后端拒绝执行。

所有覆盖操作必须保留必要审计。

---

## 7. 批发车阶梯加价

阶梯加价规则采用：

> **草稿 → 校验 → 正式启用**

未完整校验、未正式启用的规则不能影响客户当前价格。

正式启用后，按当前有效规则计算新的客户展示价。

单车覆盖价始终高于统一阶梯加价。

---

## 8. 批发车查价额度

查价额度只针对：

> **客户侧批发车数字价格解锁。**

员工查看不消耗客户查价额度。

每日基础额度由后台配置，并按日恢复。

同一个：

> `customer + vehicle + listing_cycle`

成功解锁一次后：

- 当前周期重复查看不重复扣额度；
- 当前周期普通改价不重复扣额度；
- 当前周期覆盖价变化不重复扣额度。

车辆真正重新上架形成新 `listing_cycle` 后：

> **需要重新取得新周期查价资格。**

---

## 9. Recommendation 与分享的查价关系

正式 Recommendation：

> **免费授予客户该车辆当前 `listing_cycle` 的查价权，不消耗每日基础额度。**

该免费查价权持续到当前周期结束。

普通分享：

> **不授予免费查价权。**

收藏：

> **不能绕过查价额度。**

如果 Recommendation 建立时车辆为“价格咨询”，后续当前周期出现数字价格：

> **仍沿用该 Recommendation 授予的本周期免费查价权，不再额外扣额度。**

旧周期查价权不能泄露新周期当前价格。

---

## 10. “价格咨询”与额度

车辆当前没有可用客户数字价格而显示“价格咨询”时：

> **不消耗客户查价额度。**

后续出现数字价格后，如果客户没有 Recommendation 等免费查价权，则第一次正常数字解锁按当前额度规则处理。

---

## 11. 名邦 / 4S 人工车价格

人工车：

- 客户标价允许为空；
- 为空时客户显示“价格咨询”；
- 内部批发价允许为空；
- 内部批发价为空仍允许进入锁车业务。

人工车不参加批发车统一阶梯加价。

---

## 12. 批发车锁车价格前提

批发车缺少可用基础批发价格时，不能把未知内部成本当成正常数字内部价。

批发车锁车所需的最终内部价格完整性继续按 R8 / 当前锁车规则共同校验。

人工车“内部批发价为空仍可锁车”不反向套用到 JYT 批发车上游价格事实。

---

## 13. 一键转名邦时的价格继承

批发车执行一键转名邦时，价格按“转换当下快照”生成新名邦车：

### 客户标价

- 原批发车当前有效客户展示价为数字 → 新名邦车 `customer_list_price` 复制该数字；
- 原批发车当前为“价格咨询” → 新名邦车客户标价为空，继续显示“价格咨询”。

### 内部批发价

- 转换时当前 `base_wholesale_price` → 新名邦车 `internal_wholesale_price`；
- 无可用基础批发价 → 新名邦车内部批发价为空。

### 上游原始价格

原 `upstream_list_price` / `upstream_wholesale_price`：

> **继续永久保留在原批发车 Source Data，不直接迁移为新名邦车上游字段。**

转换完成后：

- 新名邦车独立维护；
- 不再执行 JYT 统一阶梯加价；
- 不再随原批发车后续上游价格变化自动联动。

---

## 14. 内部价查看（R11 回补）

名邦员工进入内部模式后：

> **可以查看内部价 / 批发价，不再设置独立“内部价查看权限”。**

4S 成员不能查看名邦内部价 / 批发价。

进入内部模式不等于拥有调价、覆盖价、电话等其他敏感操作权限。

---

## 15. 价格快照与审计

关键价格业务必须保留必要历史和审计。

锁车等关键业务快照可包含：

- 当时客户标价；
- 当时内部批发价；
- 当时客户展示价；
- 是否存在覆盖价；
- 当时规则计算价；
- 相关周期和时间。

价格变更 / 覆盖操作按当前业务要求保留：

- 操作人；
- 操作时间；
- 变更前；
- 变更后；
- 必要的规则来源和历史。

---

## 16. 服务费 / 预计到手价体系

V1 继续取消以下独立报价体系：

- 服务费；
- 物流费报价；
- 检测费报价；
- 过户费报价；
- 其他附加费用报价；
- 预计到手价 / 到手价测算；
- 后台费用规则。

这里取消的是“费用报价体系”，不影响锁车 / Transaction 对车辆价格事实本身保存价格快照。

---

## 17. 当前明确废弃的旧方向

以下旧规则不得恢复：

1. 将客户展示价覆盖范围限制为单一车源类型的旧方案；
2. 加价关闭后直接统一显示“价格咨询”；
3. 普通分享自动获得免费批发车查价权；
4. 收藏绕过查价额度；
5. 同一 `listing_cycle` 每次查看都重复扣额度；
6. 名邦 / 4S 必须存在内部批发价才能锁车；
7. 名邦 / 4S 参加 JYT 统一阶梯加价；
8. 名邦员工查看内部价 / 批发价必须额外独立查看权限；
9. 恢复服务费 / 预计到手价整套报价体系。

# D5. R5_客户注册归属分享转介绍离职交接

# R5｜客户注册 / 归属 / 分享注册 / 转介绍 / 离职交接｜当前版

## 1. 模块状态

- `BUSINESS_REVIEW = COMPLETE`
- 当前阶段：Phase 1｜业务重审
- 本文依据已在主线正式吸收的 R5 冻结结论重建为当前版。
- 当前运行环境未能重新物化原始 R5 分支最终文件，因此本文不伪称是原文件逐字副本。
- 后续 Phase 1.5 必须用历史遗漏扫描反查旧 R5 / CN11 / Decision Register，确认是否存在不冲突但未被本重建版带入的细节。

---

## 2. 首次进入与 customer_id

客户首次进入小程序：

> **只建立 `customer_id`，不因为首次进入就立即分配销售。**

普通浏览不是“必须归属销售”的触发条件。

---

## 3. 首次有效归属事件

客户第一次出现有效归属事件时，才确定当前 owner。

当前有效事件包括：

1. 有效销售分享；
2. 老客户转介绍；
3. 客户首次触发需要人工服务的动作，并进入正常接客分配池。

---

## 4. 当前 owner 唯一

同一客户同一时刻：

> **只能有一个当前 owner。**

不得存在两个并列正式 owner。

---

## 5. 分享不抢客

客户已经存在当前 owner 后：

> **后续再点击其他销售分享，不改变当前 owner。**

分享可以增加来源 / 触达事实，但不能变成“最后分享者抢客户”。

---

## 6. 原始来源与当前 owner 分离

必须长期区分：

- 客户原始来源；
- 直接推荐人 / 转介绍来源；
- 来源销售；
- 当前 owner。

owner 后续变化：

> **不得改写原始来源。**

---

## 7. 老客户转介绍

老客户 B 转介绍一个新客户时：

> **新客户归 B 在转介绍发生当时的当前正式 owner 承接。**

如果 B 的 owner 后续发生变化：

> 之后新发生的转介绍按之后的当前 owner 处理。

不能永久跟随历史 owner。

如果来源员工已离职或不再具备承接资格：

> 保留来源事实，当前 owner 从合格接客池产生 / 由当前管理规则处理。

---

## 8. 销售关闭接客

销售关闭“接客”：

> **只影响新客户进入，不自动转移其已有客户。**

已有客户仍归当前 owner，除非发生明确移交 / 公海 / 离职交接等业务事件。

---

## 9. 离职旧分享链接

销售离职后：

- 旧分享链接仍可以被打开；
- 来源事实仍保留；
- 新客户不能继续归属给 inactive / 离职销售。

需要 owner 时：

> 按当前有效归属 / 接客规则产生新的合格 owner。

---

## 10. 离职交接范围

员工离职 / 失去业务资格时，不只处理客户 owner。

必须同时检查并交接其仍在负责的未完成业务，包括但不限于：

- 客户 owner；
- active / paused demand 负责人；
- pending / processing consultation 负责人；
- 当前有效候补负责人；
- 当前 Lock 负责人；
- 进行中 Transaction 负责人。

意向金 / 退款事实继续保留原操作事实，不单独创造负责人。

交接不得改写原员工的历史贡献、操作和责任记录。

---

## 11. 离职交接批次

离职交接需要可追溯的交接批次。

至少应能够明确：

- 离职员工；
- 离职时间；
- 离职时正式归属客户清单；
- 后续转交 / 再次分配历史。

具体数据结构留 Phase 2。

---

## 12. owner 冲突

出现 owner 归属冲突且现有规则无法唯一自动消解时：

> **由具备管理权限的经理 / 店长指定当前 owner，并保留审计。**

不得静默覆盖历史。

---

## 13. 手机号与重复客户

相同手机号：

> **不能自动认定为同一客户并自动合并。**

重复客户只有确认属于同一自然人后，才允许人工合并。

合并必须：

- 保留历史；
- 保留来源与 owner 变化；
- 不把旧记录物理抹除。

---

## 14. 客户停用 / 注销

客户停用 / 注销：

> **不物理删除业务历史。**

重新确认是原客户后，可以恢复身份使用，但不能制造新的“历史被清空”客户。

---

## 15. 当前明确禁止

1. 首次进入小程序就强制分配销售；
2. 最后一次分享覆盖已有 owner；
3. 把原始来源和当前 owner 合成同一个字段；
4. 老客转介绍永久跟历史 owner；
5. 销售关闭接客就自动转走已有客户；
6. 离职销售继续承接新客户；
7. 同手机号自动合并客户；
8. 客户停用 / 注销后物理删除业务历史。

---

## 16. 当前结论

`BUSINESS_REVIEW = COMPLETE`

R5 当前业务主线为：

> **身份先建立，归属在有效业务事件发生时建立；来源永久可追溯，owner 可以合法变化但不能抢客；离职必须交接客户和活跃业务；重复客户与注销均不允许通过物理删除历史解决。**

# D6. R6_CRM公海与协作

# R6｜CRM / 公海 / 协作｜业务重审最终总结

## 1. 模块状态

- `BUSINESS_REVIEW = COMPLETE`
- 当前阶段：Phase 1｜业务重审
- 本文仅用于业务规则收口、主线合并与后续工程闭环输入
- **不自动启动 DB / API / Worker / Storage / 前端 / Tests 等工程施工**
- 后续工程实现统一进入 Phase 2｜全项目工程闭环

本文是 R6 当前最新业务规则。主窗口吸收本文后，即使不读取本分支完整聊天，也应能够独立理解 CRM、公海、协作销售、owner 变更、待公海处理、审计与历史保留等业务规则。

---

## 2. R6 适用范围

R6 只处理：

1. CRM 当前 owner；
2. 客户进入 / 退出公海；
3. 待公海处理；
4. 公海领取与管理分配；
5. 协作销售；
6. CRM 阶段、标签、跟进记录与待办；
7. owner 变更与协作关系的联动；
8. 离职、inactive、调店等场景下 CRM 处理；
9. 公海、移交、协作相关审计与历史保留。

R6 不重新打开已经冻结的客户身份、原始来源、转介绍、推荐、分享、找车 Matching、锁车 / 候补 / Transaction 等模块，只定义它们与 CRM / 公海 / 协作直接相交的边界。

---

## 3. CRM owner 基本原则

- 客户同一时刻只有一个正式 `owner`。
- 公海、协作销售不会制造第二个正式 owner。
- owner 变化不改写客户原始来源、历史 owner、历史操作记录。
- 客户成交后仍保留原客户身份和当前 owner。
- 客户以后再次购车、找车或咨询，在原客户身份下新建新一轮业务，不重新创建客户。

---

## 4. 什么情况下进入公海

客户**不会因为以下情况自动进入公海**：

- 长期没有登录；
- 长期没有访问小程序；
- 已经完成购车；
- 暂时无意向；
- 被标记“暂不联系”；
- 销售关闭自然接客；
- 销售短期休假；
- 跟进超期；
- 长期未联系。

正式进入公海必须由明确业务动作触发，例如：

- 当前销售主动释放；
- 具备权限的经理 / 店长处理；
- 销售离职 / inactive，且暂时没有明确接替人；
- 后台“待公海处理”名单经人工确认后进入。

原则：

> **系统可以提醒，但不能自动抢走客户。**

---

## 5. 待公海处理机制

后台允许根据可配置条件生成：

> **待公海处理**

例如：

- 长期无有效跟进；
- 业务结束后一段时间没有互动；
- 其他后台配置条件。

这些条件只产生提醒，不直接改变 owner。

具备对应管理权限的经理 / 店长可以选择：

1. 进入公海；
2. 继续保留当前销售；
3. 直接移交其他销售。

选择“继续当前销售”后：

- 当前 owner 不变；
- 记录本次处理结果；
- 支持配置重新检查周期；
- 周期内不重复进入待处理名单；
- 到期后如果仍满足条件，可以再次提醒。

---

## 6. 有未完成业务时不能直接进入公海

客户如果还有未完成的：

- 咨询；
- 找车；
- 锁车；
- 候补；
- 交易；
- CRM 待办；
- 回访计划；
- 未来跟进任务；
- 其他当前业务责任；

则：

> **不能直接进入公海。**

必须先：

- 完成；
- 取消；
- 或明确交接；

再正式进入公海。

---

## 7. 公海范围

公海不是默认全公司共享。

客户进入公海时，默认进入：

> **其当前所属门店 / 当前服务范围对应的公海。**

员工只能看到自己数据范围内可领取的公海客户。

- 普通销售：默认看本人数据范围内可领取公海；
- 经理 / 店长：按本人管理数据范围查看；
- 有跨店授权的人：可查看对应授权范围；
- 跨店转移 / 分配必须有对应权限。

---

## 8. 谁可以领取公海客户

可以领取公海客户：

- active 普通销售；
- active 经理；
- active 店长。

不能领取：

- 4S 成员。

销售关闭“自然接客”：

> **不影响主动领取公海客户。**

领取成功后：

- 立即成为正式 owner；
- 不增加“待确认领取”中间状态；
- 并发领取时以第一个成功领取者为准；
- 原 owner 没有优先领取权；
- 原 owner 只要仍符合条件，也可以和其他销售一样重新领取。

---

## 9. 公海领取数量 / 频率限制

后台支持配置：

- 公海领取数量上限；
- 公海领取频率限制。

达到限制后：

> 不能继续领取新的公海客户。

释放、处理掉部分客户后，再按配置规则恢复领取资格。

目的：

> 防止销售一次性大量囤积公海客户但不实际跟进。

---

## 10. 公海客户主动发起服务

客户已经在公海时，如果主动发起：

- 咨询；
- 找车；
- 其他需要人工服务的动作；

则：

> **不要求客户等待销售手工领取。**

系统立即按正常合格接客池进行分配。

分配成功后：

- 自动退出公海；
- 新分配销售成为正式 owner。

---

## 11. 公海客户产生转介绍

公海客户当前没有 owner。

如果其产生新的转介绍客户：

- 仍保留“谁介绍来的”直接来源关系；
- 不能恢复原 owner；
- 不能因为历史 owner 而自动归给某个销售；
- 新客户进入正常合格接客池分配。

---

## 12. 客户进入公海后的原 owner

客户正式进入公海后：

- 原 owner 立即失去正式负责人权限；
- 不能继续以 owner 身份操作；
- 历史 owner 记录永久保留。

如果原销售后续仍需协助：

> 必须重新以协作销售身份参与，或重新按公海规则领取成为 owner。

---

## 13. 公海客户被领取后的历史

公海领取只改变当前 owner。

以下历史全部保留：

- 原始来源；
- 转介绍来源；
- 历史 owner；
- 历史公海经历；
- 每次进入公海时间；
- 每次被谁领取；
- 是否再次进入公海；
- 历史跟进；
- 历史协作关系。

---

## 14. 经理 / 店长直接分配公海客户

具备对应管理权限的经理 / 店长可以：

- 将公海客户直接分配给某个 active 销售；
- 不要求销售本人先去领取。

分配成功后：

> 被指定销售立即成为正式 owner。

必须保留审计记录。

---

## 15. 批量公海处理

只有**具备对应管理权限**的经理 / 店长才允许批量处理。

可批量执行：

- 进入公海；
- 继续当前销售；
- 直接移交。

但是：

> **批量操作不能绕过未完成业务 / 待办 / 交接校验。**

每个客户仍需逐条满足业务条件。

---

## 16. 公海客户领取后再次释放

允许销售将领取后的客户再次释放回公海。

但必须继续遵守：

- 未完成业务先处理 / 交接；
- 未完成 CRM 待办先处理 / 交接；
- 不能直接把责任丢回公海。

经理 / 店长也可按权限执行。

---

## 17. 公海客户再次点击销售分享

已经进入公海的老客户：

> **不会因为再次点击某个销售分享链接就自动归该销售。**

如果因此主动发起人工服务：

- 按正常接客池分配；
- 或销售按公海规则主动领取。

不能用分享链接绕过公海规则。

---

## 18. 协作销售基本原则

协作销售只代表：

> **参与服务。**

协作不会改变正式 owner。

规则：

- 客户始终只有一个正式 owner；
- 可以存在一个或多个协作销售；
- 协作销售不能自动成为 owner；
- 真正换 owner 必须走正式移交流程。

---

## 19. 协作权限的基本模型

协作销售能操作的范围取决于：

> **协作范围 + 自身角色权限 + 数据权限**

三者同时满足。

协作销售不能因为“参与协作”就自动获得：

- 客户全部敏感信息；
- 内部敏感价格权限；
- owner 修改权限；
- 交易退款权限；
- 客户身份合并权限；
- 其他超出自身角色能力的权限。

---

## 20. 谁可以添加 / 移除协作销售

- 当前 owner 可以给自己负责的客户添加 / 移除协作销售；
- 具备对应权限的经理 / 店长可以在自己的数据范围内管理协作关系；
- 普通销售不能给其他人的客户随意添加自己为协作销售；
- 协作销售本人不能继续邀请新的协作销售。

协作关系新增、移除、范围变化必须留历史。

---

## 21. 协作范围分两种

协作分为：

### 21.1 具体业务级协作

例如：

- 某次找车；
- 某笔交易；
- 某次咨询；
- 某个具体任务。

默认优先采用具体业务级协作。

### 21.2 客户级协作

仅在确实需要长期共同服务客户时建立。

原则：

> **不能因为协助一次具体业务，就自动开放整个客户 CRM。**

---

## 22. 协作结束

### 22.1 具体业务级协作

对应业务正式结束时：

> **自动结束。**

### 22.2 客户级协作

持续到：

- owner / 有权限管理人员主动取消；
- owner 正式发生变更；
- 协作销售离职 / inactive。

---

## 23. 协作被移除后的权限

协作销售被移除后：

- 立即失去该客户 / 协作业务当前访问权限；
- 立即失去当前操作权限；
- 历史协作记录永久保留；
- 本人历史操作记录永久保留。

以后再次参与：

> 重新建立新的协作关系。

---

## 24. 协作销售离职 / inactive

协作销售离职或变为 inactive 后：

> **协作资格立即失效。**

不会影响客户正式 owner。

如果协作销售仍承担某些未完成任务：

- 由 owner；
- 或具备权限的经理 / 店长；

重新安排其他协作人员。

---

## 25. owner 变更后的协作关系

客户正式 owner 发生变化时：

> **原有协作关系默认结束。**

如果新 owner 仍需要某个协作销售：

> 重新明确建立协作关系。

避免客户已经换负责人，但旧协作人员长期保留访问权限。

---

## 26. 协作销售能看到多少历史

默认：

> **只看与其协作范围相关、且自身权限允许查看的内容。**

- 客户级协作：可查看更完整 CRM 历史；
- 具体业务级协作：只查看该业务必要历史。

---

## 27. 协作销售能做什么

协作销售可以：

- 新增跟进；
- 处理被授权的具体协作业务；
- 在自身权限范围内参与服务。

默认不能修改：

- 客户 owner；
- 原始来源；
- 客户身份合并；
- 其他 CRM 核心归属字段。

---

## 28. 客户 owner 与具体业务负责人分离

客户始终只有一个正式 owner。

但是：

> **某一项具体业务可以由其他销售协作负责。**

例如：

- 客户 owner = 张三；
- 某次找车由李四协助；
- 某笔交易由经理参与。

具体业务负责人变化：

> **不自动改变客户 owner。**

---

## 29. CRM 阶段

客户可以有 CRM 总体阶段，例如：

- 新客户；
- 跟进中；
- 有明确意向；
- 已成交；
- 暂无意向；
- 其他当前业务阶段。

CRM 阶段属于客户当前业务状态：

> **不属于某一个销售个人。**

因此：

- owner 变化不自动重置；
- 进入公海不自动重置；
- 被重新领取不自动重置；
- 成交后未来产生新需求时可进入新的当前阶段；
- 不因为历史“已成交”永久锁死状态。

---

## 30. 谁可以修改 CRM 阶段

- 当前 owner 可维护自己客户的 CRM 阶段；
- 具备对应权限的经理 / 店长可在管理范围内调整；
- 协作销售默认不能直接修改客户主阶段；
- 如确需修改，必须有明确授权。

---

## 31. CRM 总体阶段与具体业务状态分开

客户可以有一个总体 CRM 阶段。

同时：

- 咨询；
- 找车；
- 锁车；
- 候补；
- 交易；

等具体业务各自保留自己的状态。

不能把：

> 客户总体阶段

与：

> 某一个具体业务对象的状态

混为一套状态。

---

## 32. CRM 跟进记录

所有历史跟进记录长期保留。

owner 变化、进入公海、重新领取：

> **都不能删除或重置历史跟进。**

每条跟进至少保留：

- 操作人；
- 时间；
- 跟进内容。

---

## 33. 跟进记录不能物理删除 / 覆盖

已经提交的 CRM 跟进记录：

> **不能物理删除，也不能直接覆盖原内容。**

如果记录错误：

- 可以补充更正记录；
- 有管理权限的人可将错误记录标记为“作废 / 无效”；
- 原始内容、操作人、时间仍然保留。

---

## 34. owner 变化后的原销售访问权限

正式移交完成后：

> **原 owner 默认失去该客户当前完整 CRM 访问权限。**

例外：

- 被新 owner 添加为协作销售；
- 本人具有经理 / 店长等管理数据范围权限。

历史记录保留：

> 不代表原销售仍有权继续查看客户当前资料。

---

## 35. owner 变化后的 CRM 待办

未完成的：

- 跟进任务；
- 回访提醒；
- CRM 待办；

必须随客户：

- 一并交接给新 owner；
- 或由管理人员重新指定负责人。

已经完成的历史待办：

> 不改写。

---

## 36. 客户标签

客户标签属于客户本身：

> **不因 owner 变化自动清空。**

进入公海也不自动清空：

- CRM 阶段；
- 标签；
- 来源；
- 历史跟进。

如果某些标签属于销售个人内部备注：

- 可保留历史；
- 新 owner 可新增自己的标签 / 备注。

---

## 37. “暂不联系 / 暂无意向”

被标记为：

- 暂不联系；
- 暂无意向；

只代表 CRM 状态 / 标签。

> **不能自动进入公海。**

可以触发“待公海处理”提醒，但仍需人工决定。

---

## 38. 领取后的首次跟进提醒

后台可以配置：

> **领取公海客户后的首次跟进提醒时间。**

如果超时：

- 只提醒；
- 不自动收回客户；
- 不自动进公海。

如果需要重新判断是否进入公海：

> 仍进入“待公海处理”人工判断机制。

---

## 39. 4S 成员与 CRM

4S 成员：

- 不作为 CRM 正式 owner；
- 不领取公海客户；
- 不作为客户级协作销售。

如果某笔车辆 / 交易需要 4S 成员配合：

> 在对应车辆或具体业务模块处理。

不能因此开放整个客户 CRM。

---

## 40. 重复客户合并与公海冲突

如果重复客户合并时：

- 一个身份在公海；
- 一个身份已有 owner；

系统：

> **不能自动决定合并后的归属。**

由具备权限的经理 / 店长明确选择：

- 保留某个现有 owner；
- 进入公海；
- 指定新的 owner。

合并前双方的归属历史全部保留。

---

## 41. CRM 核心审计

以下变化必须留历史：

- owner；
- CRM 阶段；
- 公海状态；
- 进入 / 退出公海；
- 公海领取；
- 直接分配；
- “继续当前销售”确认；
- 协作关系新增 / 移除；
- 协作范围变化；
- 客户合并；
- 重要业务标签；
- 门店 / 数据范围归属。

至少记录：

- 修改前；
- 修改后；
- 操作人；
- 时间。

原因 / 备注：

> 默认可选填，不强制。

日常跟进内容直接按跟进记录保存，不要求对每一个普通字段做复杂审计。

---

## 43. 与 R5 的继承关系

R6 继续继承 R5：

- 客户保持稳定 `customer_id`；
- 同一时间只有一个正式 owner；
- owner 可以变化，原始来源不能被改写；
- 已有 owner 后点击其他销售分享不能抢客户；
- 离职需要交接客户及活跃业务；
- 客户停用 / 注销不物理删除历史；
- 重复客户合并不能仅凭手机号自动处理。

R6 在此基础上补充：

- 公海；
- 待公海处理；
- 公海领取；
- 公海直接分配；
- CRM 阶段；
- CRM 跟进与待办；
- 协作销售；
- 协作范围；
- 公海 / 协作 / owner 联动。

## 45. 对 CN11 的覆盖与继承原则

# 一、Recommendation 基本模型

## 3. 正式 Recommendation 与普通分享严格分离

正式 Recommendation 是系统内明确的业务对象。

只有当前 customer owner 对自己负责的、且已具备 Recommendation 资格的客户，才能创建正式 Recommendation。

普通分享只是车辆传播 / 进入路径：

- 不创建 Recommendation；
- 不授予批发车查价权；
- 不改变 customer owner；
- 不产生其他车辆权限；
- 不因为被转发而继承原客户权限。

---

## 4. Recommendation 客户资格

不是所有客户默认都能被正式推荐车辆。

规则：

- 普通客户默认不开通 Recommendation 资格；
- 只有明确开启该资格的客户，当前 owner 才能创建正式 Recommendation；
- 资格属于客户级状态，不属于某个销售个人；
- owner 变化后资格继续保留，除非有权限人员主动关闭；
- 资格不按固定天数自动到期。

### 4.1 谁能开启 / 关闭资格

Recommendation 资格只能由**拥有对应“推荐资格管理权限”且数据范围覆盖该客户**的人员开启 / 关闭。

- 普通销售不能直接开启 / 关闭；
- 经理只有后台明确授予该权限时才能操作；
- 店长同样只有后台明确授予该权限时才能操作；
- 职位本身不自动等于拥有该能力；
- System Admin 与员工业务权限体系分离，不因 System Admin 身份自动获得该业务能力。

### 4.2 关闭 / 重开

关闭资格后：

- 只禁止以后新建正式 Recommendation；
- 已存在 Recommendation 不删除；
- 已经授予的当前 `listing_cycle` 查价权不追回；
- 历史不删除。

重新开启后：

- 只恢复未来新建 Recommendation 的资格；
- 不自动恢复此前已经结束 / 作废 / 失效的 Recommendation。

### 4.3 资格审计

开启、关闭、重新开启必须记录：

- 修改前状态；
- 修改后状态；
- 操作人；
- 操作时间。

原因 / 备注可选，不强制。

---

## 5. 谁可以创建正式 Recommendation

正式 Recommendation 只能由：

> **该客户当前 customer owner**

创建。

因此：

- 经理 / 店长即使能看到或管理客户，也不能“代 owner”创建正式 Recommendation；
- 协作销售不能正式 Recommendation；
- 其他销售不能给不属于自己的客户正式推荐；
- 经理 / 店长如果本人正好是该客户 current owner，则可以以 owner 身份创建。

如其他人员只是想把车辆发给客户：

> 使用普通分享。

若确实要由其他销售承担正式 Recommendation：

> 先按既有规则正式变更 customer owner，再由新的 owner 创建。

---

## 6. Recommendation 的推荐人

Recommendation 创建时：

> `recommender` 永远记录创建当时的 customer owner。

后续：

- owner 变化；
- 原推荐人离职；
- 客户移交；

都不能改写历史推荐人。

---

## 7. Recommendation 适用车源

对具备 Recommendation 资格的客户：

- 名邦车源可以正式推荐；
- 4S 合作车源可以正式推荐；
- JYT 批发车可以正式推荐。

其中只有需要查价保护的批发车，Recommendation 才额外产生 R4 已冻结的：

> 客户 + 车辆 + 当前 `listing_cycle` 免费查价权。

名邦车 / 4S 合作车本身不因 Recommendation 额外产生批发车查价机制。

---

# 二、Recommendation 生命周期

## 8. 同车同周期重复推荐

同一：

> customer + vehicle + `listing_cycle`

已经存在有效 Recommendation 时：

- 再次推荐不重复创建第二条有效 Recommendation；
- 不重复授予查价权；
- 只新增一次新的推荐触达历史；
- 不改写原 Recommendation 的创建人、创建时间和原始推荐事实。

---

## 9. 多车推荐

同一客户可以同时拥有多辆有效 Recommendation。

一次勾选多辆车推荐时：

- UI 可以表现为一次操作；
- 业务记录仍按每辆车分别建立 Recommendation；
- 不合并成一条模糊的“推荐了一组车”记录。

---

## 10. Recommendation 再次打开

客户再次从同一 Recommendation 进入车辆时：

- 复用原 Recommendation；
- 不重复创建新 Recommendation；
- 不重复授予权限。

---

## 11. Recommendation 结束

Recommendation 可以人工结束。

可按权限执行结束操作的包括：

- 原推荐销售；
- 当前 owner；
- 管理范围内具有对应权限的经理 / 店长。

结束后：

- 历史永久保留；
- 不物理删除；
- 已经授予的当前 `listing_cycle` 查价权仍按 R4 规则持续到周期结束；
- 不自动关闭已经存在的咨询。

---

## 12. Recommendation 不按固定天数自动过期

Recommendation 不设计“创建后 N 天自动失效”。

当前有效作用结束的主要方式：

- 人工结束；
- 作废；
- 车辆真实下架；
- 对应 `listing_cycle` 结束。

历史始终保留。

---

## 13. Recommendation 创建错了

创建错误时：

- 不物理删除；
- 可以标记为“无效 / 作废 / 结束”；
- 已经产生的历史不删除；
- 已经授予的当前 `listing_cycle` 查价权不追回。

Recommendation 的核心对象创建后不可直接改写：

- `customer_id`
- 车辆
- `listing_cycle`
- 推荐人

建错时：

> 结束 / 作废原记录，再重新创建正确 Recommendation。

---

## 14. 同周期结束后再次正式推荐

原 Recommendation 已结束，但车辆仍处于同一个 `listing_cycle` 时：

- 可以创建一次新的 Recommendation，作为新的正式推荐行为；
- 客户如果已经拥有本周期查价权，不重复授予，也不重复扣查价额度。

---

## 15. 新 `listing_cycle` 必须重新 Recommendation

车辆真实下架后重新上架形成新的 `listing_cycle`：

- 旧 Recommendation 只保留历史；
- 不能自动成为新周期有效 Recommendation；
- 如仍要正式推荐，必须创建新周期 Recommendation；
- 旧周期查价权不能跨到新周期。

---

## 16. 推荐人离职 / inactive

推荐销售离职、inactive 或失去业务资格后：

- Recommendation 历史保留；
- 已经授予客户的当前 `listing_cycle` 免费查价权不追回；
- 后续如果产生咨询，按当前有效咨询负责人规则重新判断；
- 不能继续给离职销售产生新的业务责任。

---

# 三、普通分享

## 17. 普通分享的业务定义

普通分享只提供：

> **对应车辆的进入路径。**

它不授予：

- Recommendation 关系；
- 批发车查价权；
- customer owner；
- 咨询关系；
- 其他车辆权限；
- 原客户的任何业务权限。

---

## 18. 普通分享可以继续转发

普通分享链接允许被再次转发。

每次访问：

- 可以记录本次直接分享人 / 直接传播来源；
- 不建立多级权限继承；
- 不产生多级客户归属；
- 不改变客户原始来源；
- 不改变 customer owner；
- 不授予 Recommendation；
- 不授予查价权。

---

## 19. Recommendation 链接被其他客户打开

Recommendation 明确绑定具体 `customer_id`。

如果 A 的 Recommendation 链接被 B 打开：

- B 必须以自己的微信身份 / `customer_id` 正常进入；
- 对 B 来说，该链接只是一条进入该车辆的路径；
- B 不继承 A 的 Recommendation；
- 不继承 A 的免费查价权；
- 不继承 A 的 owner；
- 不继承 A 的咨询；
- 不继承 A 的其他客户权限。

B 的查价、咨询等业务全部按照 B 自己的身份和权限重新判断。

---

## 20. 普通分享链接不按固定天数失效

只要车辆当前仍可访问：

> 原普通分享链接可以继续打开。

车辆真实下架后：

- 链接仍保留历史来源；
- 打开时明确显示“车辆已下架 / 当前不可售”；
- 不允许继续产生新的该车咨询或 Recommendation。

---

## 21. 旧周期普通分享与重新上架

普通分享本质指向这辆车，而不是授予旧周期权限。

车辆进入新 `listing_cycle` 后：

- 旧普通分享仍可打开该车辆当前的新在售状态；
- 查价权限按新周期重新判断；
- Recommendation 按新周期重新判断；
- 咨询按新周期重新判断。

---

## 22. 离职销售旧普通分享

销售离职 / inactive 后，其以前发出的普通车辆分享：

- 车辆仍可售时，旧链接仍可打开；
- 原分享人历史继续保留；
- 不能再给离职销售形成新的 customer owner；
- 不能继续产生离职销售的新业务权限；
- 客户后续需要人工服务时，按当前 customer owner / 接客规则处理。

---

# 四、客户身份与登录

## 23. 客户端不存在匿名继续浏览状态

客户进入小程序后：

> 必须先完成微信身份识别 / 登录，才能继续正常浏览。

这个过程可以是：

- 无感识别；
- 无感登录；
- 或其他正常微信身份流程。

完成后立即建立稳定 `customer_id`。

因此后续：

- 分享；
- Recommendation；
- 查价；
- 咨询；

发生时，系统已经知道对应哪个 `customer_id`。

### 23.1 微信身份 ≠ 手机号绑定

微信登录不等于必须立刻绑定手机号。

手机号门槛继续按照 R5：

> 当客户进入需要人工服务等业务动作时，再按对应业务规则处理。

---

## 24. 换微信账号

同一设备切换成另一个微信账号后：

- 按另一个 `customer_id` 处理；
- 不能因为设备相同继承前一个客户的 Recommendation；
- 不继承查价权；
- 不继承咨询；
- 不继承 owner 关系。

---

## 25. 客户身份人工合并后的 R7 业务

R5 确认多个 `customer_id` 确属同一自然人并完成人工合并后：

当前仍有效的：

- Recommendation；
- 当前 `listing_cycle` 查价权；
- 未结束咨询；

迁移到保留的主 `customer_id`。

历史记录仍保留原客户身份来源，不抹掉合并前事实。

---

# 五、Consultation（咨询）

## 26. 咨询状态

统一采用：

- `pending`
- `processing`
- `resolved`
- `invalid`

正常流转：

1. 新咨询 → `pending`
2. 负责人开始实际处理 → `processing`
3. 正常结束 → `resolved`
4. 误触 / 重复 / 无效 → `invalid`

不设计“超时自动关闭”。

超时最多：

> 提醒。

---

## 27. 咨询重复创建

同一：

> customer + vehicle + 当前 `listing_cycle`

已经存在 `pending / processing` 咨询时：

- 不创建第二条咨询；
- 继续复用原咨询；
- 后续从新的 Recommendation、普通分享、搜索、收藏等入口再次进入，只记录新的触达历史。

原咨询的：

- 最初直接来源；
- 原负责人历史；

不能被后续入口改写。

---

## 28. 终态后再次咨询

原咨询已经：

- `resolved`
- `invalid`

之后客户又针对同一车辆再次发起咨询：

> 创建新的咨询记录。

旧咨询不覆盖、不复用。

---

## 29. 新 `listing_cycle` 的咨询

车辆进入新的 `listing_cycle` 后：

- 视为新的在售周期；
- 客户再次咨询时创建新的咨询记录；
- 旧周期咨询历史保留；
- 不直接复用旧周期咨询。

---

## 30. 车辆真实下架后的咨询

车辆真实下架后：

- 不允许新增该车咨询；
- 已存在的 `pending / processing` 咨询不自动删除；
- 由负责人继续处理到合适终态，例如 `resolved / invalid`。

---

## 31. 咨询直接来源

咨询创建时记录：

> 客户这一次实际进入咨询的直接来源。

例如：

- 某条 Recommendation；
- 普通分享；
- 搜索；
- 收藏；
- 其他入口。

规则：

- 不能简单取历史最近一次 Recommendation 作为咨询来源；
- 咨询创建后的最初来源不改写；
- 后续其他入口只新增触达记录。

---

## 32. Recommendation 与咨询来源

如果客户确实从某条 Recommendation 进入并发起咨询：

> 咨询关联该条 Recommendation。

Recommendation 后续即使：

- 结束；
- 作废；
- 失效；

也不反向修改这条咨询当时的来源事实。

---

## 33. 咨询负责人优先级

当咨询发生时，按以下顺序确定负责人：

1. 本次直接来源 Recommendation 的推荐销售，且该销售仍 active、仍具备当前业务处理资格；
2. 对应 demand 负责人；
3. 当前有效 customer owner；
4. 仍无人可承接时，进入正常合格接客池分配。

因为正式 Recommendation 只能由创建当时的 customer owner 创建，所以“推荐销售”本质上是创建推荐当时的 owner。

---

## 34. owner 变化不自动改咨询负责人

咨询已经进入 `processing` 后：

> customer owner 变化，不自动更换当前咨询负责人。

只有以下情况才调整咨询负责人：

- 正式移交；
- 当前负责人离职 / inactive；
- 当前负责人失去业务资格；
- 其他明确需要重新分配的业务事件。

---

## 35. 咨询负责人失去资格

当前咨询负责人：

- 离职；
- inactive；
- 失去业务处理资格；

则必须重新分配。

重新分配优先：

1. 当前有效 customer owner；
2. 正常合格接客池。

历史负责人记录保留。

---

## 36. 咨询可以正式移交

咨询可以转给另一名销售处理，但必须走正式移交。

必须记录：

- 原负责人；
- 新负责人；
- 操作人；
- 操作时间。

咨询负责人变化：

> 不自动改变 customer owner。

---

## 37. 咨询结束 / 作废权限

可以处理自己负责咨询的：

- 当前咨询负责人。

管理范围内具有对应权限的：

- 经理；
- 店长；

也可以处理。

其他销售不能随意：

- 结束；
- 作废；
- 修改别人负责的咨询。

---

## 38. 客户主动撤回咨询

客户明确表示“不咨询了”时：

- 不删除咨询；
- 正常结束该咨询；
- 记录为客户主动取消 / 结束。

`invalid` 主要用于：

- 误触；
- 重复；
- 明显无效咨询。

正常撤回不混入无效数据。

---

## 39. `invalid` 的边界

咨询标记 `invalid`：

- 只表示这条咨询本身无效；
- 不删除历史；
- 不改变 customer owner；
- 不改变 Recommendation；
- 不改变原始来源；
- 不修改其他业务对象。

---

## 40. Recommendation 结束不自动结束咨询

Recommendation 后续：

- 结束；
- 作废；
- 失效；

都不会自动关闭已经建立的 `pending / processing` 咨询。

咨询继续按照自己的生命周期完成。

---

## 41. 已有咨询时新增 Recommendation

同一客户 + 同一车辆当前周期已有未结束咨询时，又创建了新的有效 Recommendation：

- 不新建第二条咨询；
- 新 Recommendation 只作为新的推荐 / 触达事实；
- 不自动抢走当前咨询负责人；
- 不改写原咨询最初来源。

---

## 42. 咨询本身不授予批发价权限

发起咨询：

> **不会自动获得批发车数字价格查看权。**

咨询与查价是两套业务规则。

客户仍按 R4：

- 每日查价额度；
- 已有当前周期查价权；
- Recommendation 免费查价权；

判断是否可以看到受保护批发价。

---

## 43. 咨询负责人变更审计

每次咨询负责人调整必须保留：

- 原负责人；
- 新负责人；
- 操作人；
- 操作时间。

不得只保存“当前是谁负责”而覆盖历史。

---

## 44. 咨询内容可见范围

完整咨询内容可以按权限查看的包括：

- 当前咨询负责人；
- customer owner；
- 管理范围内具有对应权限的经理 / 店长；
- 明确参与该具体业务、且协作范围允许的协作销售。

其他销售：

> 不能因为能看到车辆，就查看客户完整咨询。

---

# 六、查价权限与 R7 的边界

## 45. 查价权绑定维度

批发车查价权继续按 R4：

> `customer_id + vehicle + listing_cycle`

绑定。

它不绑定：

- 设备；
- 某个微信入口；
- 某条分享链接。

客户换设备，只要还是同一个 `customer_id`：

> 当前周期已经取得的查价权继续有效。

---

## 46. Recommendation 免费查价

只有客户本身已经具备 Recommendation 资格，并由当前 owner 创建正式 Recommendation 后：

对于批发车：

> 免费授予该客户该车辆当前 `listing_cycle` 查价权。

该权限：

- 不消耗普通每日查价额度；
- 不解锁其他车辆；
- 不通过分享转给别人；
- 不因为 Recommendation 后续结束而追回；
- 不因为推荐销售离职而追回；
- 到当前 `listing_cycle` 结束时结束。

# 七、与 R5 / R6 的归属边界

## 47. Recommendation 不改变 customer owner

正式 Recommendation 是：

> 当前 owner 对自己客户的推荐行为。

因此 Recommendation 本身不产生：

- 抢客户；
- owner 变更；
- 第二个 owner。

---

## 48. 普通分享不改变 owner

已有 owner 的客户：

- 点击其他销售普通分享；
- 打开其他客户转发链接；

都不会改变当前 owner。

分享来源可以留痕，但只用于传播归因。

---

## 49. 咨询负责人 ≠ customer owner

必须区分：

- customer owner：长期正式客户负责人；
- consultation assignee：某一次咨询的当前处理人。

咨询负责人变化：

> 不自动改变 customer owner。

customer owner 变化：

> 也不自动重置已在处理中的咨询负责人。

## 3. 继续继承的既有核心规则

以下规则本轮整体复核后继续保留，不重新打开：

### 3.1 锁车唯一性

同一车辆同一时刻：

> **只能存在一个有效 Lock。**

同一客户可以锁不同车辆，但同一车辆不能同时被多个客户有效锁定。

---

### 3.2 候补

当车辆已经存在有效 Lock 时，其他客户可进入候补。

候补：

- 只形成排队 / 意向事实；
- **不会自动升级为锁车**；
- Lock 释放后，是否重新锁车仍需重新确认；
- 车辆单纯隐藏不结束候补；
- 车辆真实失效 / 已成交等才结束对应候补业务。

---

### 3.3 意向金

意向金属于：

> **真实收款事实。**

可以存在多笔记录。

意向金与 Lock、Transaction、退款分别作为独立业务对象保留关联，不把多个业务事实硬塞成一个状态。

已收意向金后：

> **不能仅因为普通锁车超时就自动释放车辆。**

---

### 3.4 Lock 与 Transaction

Transaction 必须基于当前有效 Lock 进入。

交易创建后：

- Lock 与 Transaction 建立明确关联；
- 历史锁车事实保留；
- 交易不能脱离原锁车事实凭空产生。

---

### 3.5 Transaction 取消

Transaction 正式取消后：

> **不自动恢复原来的旧 Lock。**

如果客户仍需要继续锁车：

> 重新创建新的 Lock。

旧 Lock 只作为历史保留。

---

### 3.6 供应异常

批发车 / 上游车已经进入锁车或交易后，如果上游车辆突然失效：

> **不能直接自动取消当前锁车 / 交易。**

系统应明确标记供应异常，由业务人员继续处理。

避免上游状态变化直接抹掉已经发生的客户业务事实。

---

### 3.7 退款主状态

继续采用已冻结规则：

> **退款主状态只保留 `pending / refunded`。**

部分退款不单独建立 `partial` 主状态。

实际部分退款通过：

> **多笔退款明细 / 实际退款记录**

表达。

不恢复复杂的 `partial / non_refundable` 等退款主状态体系。

---

### 3.8 锁车价格快照

正式锁车必须保存锁车发生时的客户有效展示价快照。

- 有数字价格 → 保存当时数字；
- 当时为“价格咨询” → 保存明确的“价格咨询”事实；
- 不允许用 0 或虚构价格代替。

后续价格变化不能改写历史锁车价格快照。

## 4. R8-01｜默认锁车时长

本轮正式冻结：

> **默认锁车时长 = 72 小时，后台可配置。**

规则：

1. 新 Lock 创建时，根据当时有效配置计算 `expires_at`；
2. Lock 创建完成后，该 Lock 的 `expires_at` 固化；
3. 后台以后修改默认锁车时长，不追改已经存在的 Lock；
4. 已收意向金的 Lock 不因为普通 72 小时超时自动释放。

本条正式覆盖旧资料中：

> 默认锁车 2 小时

的旧结论。

R8 当前统一以：

> **72 小时，可配置**

为准。

经过第二遍风险复核后，发现该方案会重新引入 V1 已经不需要的二级审批流程。

R8 当前最终采用：

> **权限控制 + 必填原因 + 完整审计**

而不是二级审批。

### 5.3 System Admin 边界

System Admin 属于独立系统身份。

因此：

> **System Admin 身份本身不具备成交纠错业务权限。**

如果某个真人同时具有：

- System Admin 身份；
- 员工身份；

其参与成交纠错时，必须使用：

> **具备对应业务权限的员工身份。**

不能因为拥有 System Admin 身份，就自动获得交易业务纠错权。

## 6. R8-03｜换车与旧意向金

V1 不单独设计复杂的“换车专用状态机”。

客户换车时：

1. 原车辆对应的旧 Lock / Transaction 按真实业务结果结束或取消；
2. 新车辆重新创建新的 Lock；
3. 新车辆需要 Transaction 时重新创建新的 Transaction。

如果旧车已经收取意向金：

> **旧意向金不能直接改挂 / 转移到新车。**

处理原则：

- 原交易按实际结果处理原意向金和退款；
- 新车需要意向金时，重新记录新的收款；
- 旧收款、旧退款、新收款分别保留真实资金历史。

本轮不建立：

> “意向金跨车转移”

机制。

这样确保：

> **钱的历史不因为换车被改写。**

---

## 7. 换车业务原则

换车不是修改原车辆 ID。

原则：

> **旧业务结束，新车辆重新建立新的锁车 / 交易关系。**

历史：

- 原车辆；
- 原 Lock；
- 原 Transaction；
- 原意向金；
- 原退款；

全部保留。

新车：

- 新 Lock；
- 新 Transaction；
- 新意向金记录；

重新建立。

不通过直接替换旧交易车辆的方式抹掉历史。

# 二、R10-01～R10-79 最终结论

## R10-01｜客户端车源页的两级结构

客户端一级车源切换固定为：

> **批发车源｜名邦车源｜4S店车源**

- 默认进入：**批发车源**。
- “名邦第一、4S第二、批发第三”不是一级频道顺序，而是 **批发车源页面内部展示顺序**。
- 批发页内部依次为：
  1. 名邦车源机会块 / 入口；
  2. 4S店车源机会块 / 入口；
  3. 正常批发车源列表。

**覆盖旧误判：**废弃“一级默认名邦、一级顺序名邦→4S→批发”的错误理解。

1. 上牌时间
2. 表显里程
3. 变速箱
4. 排量 / 能源
5. 车身 / 内饰颜色

## R10-04｜员工车辆详情内部模式

员工端车辆详情默认始终是 **客户安全视图**。

进入内部模式：
> **长按价格区域约 3 秒**

内部能力按来源、权限、数据范围和车辆状态裁剪，可包含：
- 内部价 / 批发价；
- 上游电话；
- 编辑车辆资料；
- 调价；
- 上 / 下架；
- 客户展示价覆盖；
- 一键转名邦；
- 隐藏 / 恢复显示。

权限原则：
- 进入内部模式本身不另设独立权限；
- 名邦员工进入内部模式后可查看内部价 / 批发价，不再另设“内部价查看权限”；
- 4S 成员不可查看名邦内部价 / 批发价；
- 电话、隐藏 / 恢复、调价、上下架、客户展示价覆盖等敏感动作仍按各自具体权限控制；
- 无相应具体权限时，对应敏感按钮 **完全不显示**，不是灰色禁用；
- 后端在提交敏感动作时仍必须重新校验当前权限、数据范围和车辆状态。

内部模式只在当前员工、当前车辆、当前访问过程内有效。返回、离开详情、重新打开、切换车辆、分享、推荐、长时间进入后台后再返回等，都恢复客户安全视图，不长期记住内部模式。

## R10-16｜客户端「帮我找车」完整业务结构

申请与正式需求分离：
> 手机号门槛 → 找车申请 pending → 员工处理 → 激活后生成正式 demand

客户端工作区允许同时管理：
- 活跃需求；
- 待处理申请；
- 已暂停需求；
- 推荐结果；
- 已结束需求；
- 新建需求。

状态文案必须真实：
- 待处理申请：等待服务确认；
- 已激活但条件仍在整理：顾问整理条件；
- 条件进入正式匹配：匹配中；
- 某些条件未知时，可继续使用已明确条件，不要求全部补完。

找车申请最低必填：
> **想找什么车**

预算可选；年款、里程、车况、颜色、地域、其他要求等均可作为可选条件。

pending 申请客户可以编辑同一申请，也可以主动撤回；撤回后关闭，不生成正式需求。

推荐车辆在客户端找车工作区只负责展示 / 查看详情，不直接在卡片放“我要这辆车”；进入统一详情后再走正常 CTA。

被推荐车辆后续售出 / 下架 / 不可公开时，推荐历史仍保留，可看历史详情，但不能发起新的在售动作。

客户可以暂停、恢复、结束自己的正式需求；暂停保留历史推荐；结束后未来如仍要找车，建立新需求。

员工 E05 找车详情包含：
- 客户原始找车要求；
- 销售匹配描述；
- 解析后的标准化条件；
- 备注；
- 跟进；
- 候选车辆及候选等级等。

需求上下文中候选车可“推荐给客户”，有权限且车辆可锁时可直接锁车；客户已明确，不重复选择。

## R10-33｜员工内部模式的上游电话

本节电话口径统一以：

作为当前唯一业务口径。任何非“上游发布人维度”的历史电话获取 / 缓存口径均废弃。


稳定身份键：
- 车辆保存 `upstream_publisher_id`；
- 本地电话缓存键：`source_platform + upstream_publisher_id`；
- 名邦调用采集端发送 `publisher_id = upstream_publisher_id`；
- 采集端内部再映射到 JYT `help_user_id`。

UI 只保留两个动作：

**1. 拨打电话**
- 先查本地缓存；
- 有缓存直接拨；
- 无缓存自动向采集端拉取一次；
- 成功后保存缓存再拨。

**2. 获取最新电话**
- 员工主动刷新；
- 绕过缓存；
- 强制获取最新；
- 成功后覆盖当前缓存；
- 历史号码可用于审计。

没有电话权限时整个电话区域不显示；客户端永远不展示上游电话。

## R10-34｜内部操作按车源类型裁剪

**批发车源：**
- 普通名邦销售可进入内部编辑 / 详情页面查看完整详细参数；
- JYT 上游原始车辆事实和上游原始价格只读，禁止普通人工改写；
- 名邦员工进入内部模式后可查看内部 / 批发价，不另设“内部价查看权限”；
- 上游电话、客户展示价覆盖、隐藏 / 恢复等继续按对应具体权限控制；
- 普通名邦销售默认可用“一键转名邦”，不另设独立权限门槛；
- 4S 成员不可用“一键转名邦”。

**名邦车源：**
- 在数据范围内可管理车辆，不以“是否本人上传”为权限边界；
- 调价、上下架、客户展示价覆盖、隐藏 / 恢复继续按对应具体权限控制。

**4S 车源：**
- 名邦员工在数据范围内可管理，不以“是否本人上传”为权限边界；
- 4S 成员仍按其自身可管理车辆范围操作；
- 调价、上下架、客户展示价覆盖、隐藏 / 恢复继续按对应具体权限控制。

**4S 成员公开浏览：**
- 可以正常浏览所有公开车源；
- 可以看到正常对外展示价格；
- 对外展示价不等于内部价 / 批发价；
- 4S 成员不能查看名邦内部价 / 批发价。

关键规则：**客户展示价覆盖适用于批发、名邦、4S 三种来源。**

内部菜单裁剪顺序：
> 先按身份 / 车源类型裁剪 → 再按具体权限 / 数据范围 / 当前状态裁剪。

## R10-36｜人工车源新增、草稿、编辑、发布

新增入口不使用旧右下角悬浮“+新增车源”。

入口：
> `E02 → 更多 → 新增车源`

草稿：
> `E02 → 更多 → 草稿车源`

新建表单：

- 不设“保存草稿”按钮；
- 不做预览步骤；
- 底部唯一主要动作：**正式发布**；
- 缺发布必要字段时不能执行并明确提示；
- 发布成功 → “发布成功” → 打开新车辆详情。

已发布车辆编辑：
- 编辑中可临时保存；
- 中间内容不能自动实时更新到客户端；
- 必须点击 **保存修改** 才正式生效；
- 离开后未提交修改可保留继续编辑；
- 价格、上下架、source_type 等敏感事项走专门业务动作。

草稿列表：
- 只显示有权管理的未发布草稿；
- 可继续编辑、删除（二次确认）、正式发布；
- 草稿不进入客户端、搜索、自动匹配、Recommendation、Lock。

source_type：
- 只允许一种人工来源 → 直接表单；
- 同时允许名邦+4S → 新建时必须明确选择，不默认；
- 首次正式发布前草稿可改 source_type；
- 正式发布后，有该车辆正常管理能力的员工可以通过专门业务动作修改 `source_type`；必须记录修改前、修改后、操作人、操作时间，不强制填写修改原因。

## R10-37｜地域规则

**当前最新规则彻底覆盖旧 700 公里逻辑。**

- 默认：**全国**；
- 定位城市只作为快捷选择项，用户主动点击后才筛选；
- 可手动选择其他城市；
- 当前一次只使用一个地域条件，不做多城市并选；
- 拒绝定位仍正常全国浏览；
- 地域条件在来源切换、搜索、返回列表等过程中保持。

明确废弃：

- 700公里自动范围。

## R10-38｜搜索、排序、车型选择和筛选

### 搜索框
搜索框与 **帮我找车匹配引擎** 使用同一套确定性解析 / 匹配字典规则，不是简单关键词搜索。

例：`26款 奥迪A6` 可直接解析品牌、车系、年款等结构化条件。

### 手动车型选择 UI
表现为：
> 品牌 → 车系 → 年款分组 → 具体车型 / 款式

但底层主数据仍遵守 R3：
> 品牌 → 车系 → 具体车型

年款是具体车型结构化字段 / UI 分组，不是额外主数据实体。

### 品牌选择器
- 品牌搜索；
- 热门品牌；
- A-Z 分组；
- 右侧 A-Z 快速索引。

### 年款分组多选
- `2026款（全部车型）` 可一键选中该年款全部具体车型；
- 可同一年款选多个具体车型；
- 可跨多个年款多选。

### 主筛选栏顺序
> **排序｜品牌/车系｜价格｜年份｜里程｜更多**

### 排序
1. 最新上架（默认）
2. 价格低→高
3. 价格高→低
4. 年份新→旧
5. 年份旧→新
6. 里程少→多
7. 里程多→少

**删除综合排序。**

### “年份”定义
主筛选“年份”= **首次上牌年份**，不是车型年款；采用区间，例如 2020–2025。

### 价格筛选
按当前真实客户展示价参与判断；即使客户尚未解锁数字价格也照常参与。明确数字价格区间下，“价格咨询”车辆不参与。不得按内部批发价 / 上游原始价筛选。

### 里程
按当前表显里程范围筛选，支持最小、最大、单侧；搜索解析到的里程条件落到同一结构化字段。

### 更多
- 能源类型：多选；
- 排量：数值范围，例如 1.8–2.0，2.0–2.0=精确 2.0；
- 颜色：多选；
- 变速箱：多选。

### 已选条件标签
筛选栏下方显示 chips，小标签可直接删除。

层级删除：
- 删除具体车型 → 保留品牌+车系；
- 删除车系 → 清依赖具体车型，品牌保留；
- 删除品牌 → 其下车系 / 具体车型依赖一起清除。

其他标签包括价格区间、上牌年份区间、里程、颜色、变速箱、能源、排量等；保留“重置”能力。

## R10-64｜新增车源与已有草稿

采用 **多草稿模式**。

原草稿统一在“更多 → 草稿车源”管理。

空白草稿控制：
- 刚进入新增页，什么有效内容都没填就退出 → 不生成草稿；
- 开始填写有效车辆资料 / 上传内容后 → 自动保存为草稿。

因此：
- 新增车源 = 新建；
- 草稿车源 = 找旧草稿继续。

## R10-65｜VIN 重复

人工车辆 VIN **不是必填字段**。

没填 VIN：不做 VIN 重复 Gate，不能用车型、年款、里程、相似描述猜同一台车并阻止发布。

填了 VIN：正式发布时做 **完全一致 VIN 精确查重**。

若当前已有名邦 / 4S 人工车辆使用相同 VIN：阻止普通正式发布，并明确提示：
> **检测到相同 VIN 的现有车辆，请确认是否重复录入。**

提供：
- 查看已有车辆；
- 返回修改。

查看已有车辆 → 打开疑似重复车辆的员工详情；返回修改 → 回当前草稿且已填数据完整保留。

普通员工不提供“忽略并继续发布”。特殊历史数据纠错以后由专门权限 / 工程机制处理。

- 新增成功后返回当前草稿；
- 自动选中刚新增的车型；

## R10-67｜找车表单手机号拒绝后的临时保留

重要边界：临时保留 ≠ 后台持久化找车草稿。

页面被销毁、关闭小程序、长时间离开等情况下，不承诺永久保存这份未提交内容；不因此新增“未授权找车草稿”状态机。

- 群聊；
- 朋友圈（按微信小程序当时官方实际能力接入）。

首页 / 车辆列表不单独增加“分享车源”按钮。

分享后打开当前车辆详情，分享态底部显示“查看更多车源”。

分享链路仍需要携带安全、轻量归因上下文，用于识别：
- 哪个员工分享；
- 或哪个客户分享；
- 哪台车辆；
- 必要来源链。

技术字段名本阶段不冻结。

归属原则：
- 已有客户打开别人的分享，不抢原 owner；
- 新客户通过有效销售分享进入，按 R5 当前规则建立对应归因 / 归属；
- 客户转介绍按 R5 规则处理。

普通分享：
- 不自动创建 Recommendation；
- 不赠送批发查价权限；
- 不携带员工内部模式；
- 不泄露内部价 / 上游电话等敏感信息。

## R10-69｜车辆分享卡片展示内容

分享卡片保持简单：
- 车辆主图；
- 完整车型名称；
- “点击查看车辆详情”等引导。

不把动态 / 受权限价格写死到分享卡片。

分享卡片不直接展示：
- 客户展示价；
- 内部批发价；
- VIN；
- 上游电话；
- 内部状态。

真正打开详情后，再按接收人的身份、权限、车辆当前状态实时计算展示。

旧分享消息无需追回，但再次打开时必须按车辆最新状态判断，不能因旧分享继续查看已不可公开内容。

---

## R10-70｜“在售车源 / 今日新增”统计口径

两个数字是 **全站公共统计**，不随当前频道、搜索、筛选变化。

在售车源：统计当前客户端真正可公开浏览的全部在售车辆，包含批发、名邦、4S。

不计入：
- 隐藏；
- 下架；
- 已售；
- 草稿；
- 未通过审核；
- 其他不可公开车辆。

Priority 保护车辆不是普通公共可见车辆，**不计入普通首页公共在售总数**。

今日新增：统计今天第一次进入系统并正式公开在售、且当前仍可公开浏览的新车辆。

---

## R10-71｜首页统计数字不可点击

“在售车源 / 今日新增”只做数据展示。

不：
- 点击跳转；
- 自动筛选；
- 切换来源；
- 建立跨三来源“全部车源列表”。

用户找车继续使用搜索、来源频道、筛选。

---

## R10-72｜上架日期、最新上架与今日新增

列表卡片“上架日期”使用 **当前 listing_cycle 的正式上架日期**，不是车辆第一次录入系统的历史日期。

例如 9月1日首次上架、9月10日下架、9月19日重新上架，当前卡片显示 09-19。

“最新上架”排序也使用当前 listing_cycle 上架时间。

“今日新增”与之区分：只统计今天 **首次进入系统并正式在售** 的新车辆；历史车辆重新上架不计入“今日新增”。

## R10-73｜“价格咨询”在价格排序中的位置

没有有效数字价格、显示“价格咨询”的车辆，在价格排序时统一排在所有有数字价格车辆之后。

- 价格低→高：数字价格低→高 → 价格咨询
- 价格高→低：数字价格高→低 → 价格咨询

多台“价格咨询”之间按 **最新上架优先**。

不能把“价格咨询”当 0 元、无限大或排序第一。

---

## R10-74｜批发车辆尚未解锁价格时怎么显示

有限查价次数客户，如果该批发车辆当前 listing_cycle 尚未解锁：
> **查看价格**

不显示 `****`、`¥?` 或假价格。

点击后如需要消耗 1 次额度，弹轻量确认，例如：
> 本次将使用 1 次今日查价机会，今日剩余 X 次。

确认后消耗额度并显示真实客户展示价。

不需要消耗的情况：
- 本车当前周期已经解锁；
- Recommendation 已赠送当前周期查价；
- 客户等级为无限查价；
- 本车实际为“价格咨询”。

“价格咨询”不消耗数值查价次数。

列表 / 详情任一处成功解锁后，另一处同步显示真实价格，不重复扣。

---

## R10-75｜未解锁批发价格仍参与真实价格排序

即使客户页面只看到“查看价格”，车辆仍按真实客户展示价参与价格低→高 / 高→低排序。

例如：A 实际10万未解锁、B 12万已解锁、C 15万未解锁，低→高仍为 A→B→C；页面仅分别显示“查看价格 / 12万 / 查看价格”。

排序准确性不受是否已解锁影响；“价格咨询”继续按 R10-73 放最后。

---

## R10-76｜车辆被锁定 / 进入交易后是否继续出现在客户列表

只要车辆底层仍属于 **在售**，即使已经：
- 普通 Lock；
- 已支付真实意向金进入持续占用；
- 已进入交易处理中，

仍可继续保留在客户正常车辆列表。

对其他普通客户统一只暴露：**已锁定**。

不公开：
- 谁锁的；
- 是否已交意向金；
- 意向金金额；
- 内部交易进度；
- 具体交易状态。

其他客户仍可登记候补。

车辆最终已售、正式下架或其他原因退出公开在售时，才从普通列表消失。

这种仍公开显示、允许候补的已锁车辆仍计入“在售车源”数量。

---

## R10-77｜客户列表区分“自己的锁车”和“别人锁车”

当前客户自己有有效 Lock：
> **我的锁车**

被其他客户锁定：
> **已锁定**

员工客户安全视图不使用“我的锁车”这种客户个人视角文案，员工按车辆真实经营状态显示。

---

## R10-78｜客户列表多业务状态显示优先级

同一车辆若命中多种当前客户本人业务关系，只显示最高优先一个，不堆多个标签。

优先级：
1. **我的交易**
2. **我的锁车**
3. **我的候补**
4. **已锁定**

该顺序与车辆详情 CTA 状态矩阵保持一致。

---

## R10-79｜员工车辆列表的占用状态

员工端 E02 不使用“我的锁车 / 我的候补”这类客户个人视角，而看车辆真实经营占用状态。

- 有有效普通 Lock → **已锁定**
- 已支付意向金、持续占用 → **已锁定**
- 已正式进入 Transaction → **交易中**
- 无占用 → 不显示占用标签

同时命中时：
> **交易中 > 已锁定**

列表不直接显示客户姓名、手机号、意向金金额、详细交易进度。

要查看谁锁的、负责人、Lock 时间、Transaction 信息，进入车辆详情 / 锁车业务 / 交易业务页面。

# 三、R10 期间同步确认的锁车补充规则

## 1. 普通 Lock 可以延期

必须审计：
- 原到期时间；
- 新到期时间；
- 操作人；
- 操作时间。

客户端“我的锁车”同步显示新到期时间，可显示“已延期”。

客户真实支付意向金 / 定金事实成立后，车辆进入持续 / 长期占用状态，不再因原 72 小时 Lock 到期自动释放。

必须有明确业务结果才结束，例如继续成交、取消、换车或其他正式结束动作。

客户端此时不显示普通倒计时。

# 2. R11 核心定位

R11 管理的是：

> 员工在车辆详情中的客户安全视图、内部模式、敏感信息展示、敏感操作入口、权限裁剪、异常退出与审计边界。

内部模式本身不是一套新的权限系统，而是：

> **敏感能力的承载入口。**

进入内部模式之后，系统仍然需要根据：

1. 车源类型；
2. 员工身份；
3. 数据范围；
4. 具体权限；
5. 当前车辆状态；

决定最终显示哪些敏感信息、哪些按钮可以操作。

---

# 3. 客户安全视图

员工进入车辆详情时，默认始终进入：

> **客户安全视图**

客户安全视图与客户端对外展示口径一致，不展示员工内部敏感信息。

至少不得展示：

- 内部价；
- 批发价；
- 上游发布人电话；
- 员工内部备注；
- 其他只允许内部查看的敏感信息。

## 3.1 后端隔离

客户安全视图不能只靠前端“隐藏按钮 / 隐藏文字”。

原则：

> **敏感字段应从数据返回层就按照当前模式和权限进行隔离。**

不能出现：

- 后端把全部敏感字段返回；
- 前端只是视觉隐藏；
- 切换模式、缓存、页面恢复或调试后又泄露敏感内容。

---

# 4. 内部模式进入方式

员工端车辆详情：

> **长按价格区域约 3 秒进入内部模式。**

内部模式不单独增加“能不能进入内部模式”的权限开关。

即：

> 员工可以进入内部模式，但进入之后看到什么、能做什么，仍按具体权限和数据范围逐项裁剪。

不能理解为：

> 进入内部模式 = 自动获得全部敏感权限。

---

# 5. 内部模式生命周期

内部模式只对：

> 当前员工 + 当前车辆 + 当前一次访问过程

有效。

以下情况恢复客户安全视图：

- 返回上一页；
- 离开车辆详情；
- 重新打开车辆详情；
- 切换到另一辆车；
- 分享车辆；
- 推荐车辆；
- 页面重新进入；
- 长时间进入后台再返回；
- 员工身份 / 权限发生变化后重新校验。

内部模式不能长期记忆为全局状态。

# 6. 内部价 / 批发价

最终冻结：

> **内部价 / 批发价必须进入内部模式后才能查看。**

默认客户安全视图绝不展示。

## 6.1 名邦员工

普通名邦销售进入内部模式后：

> **可以查看内部价 / 批发价。**

不再为“查看内部价 / 批发价”单独设置一层独立权限。

## 6.2 4S 成员

4S 成员：

> **不能查看名邦内部价 / 批发价。**

但 4S 成员仍然可以正常浏览所有公开车源，并查看所有车源当前正常对外展示的价格。

即：

- 批发车源：看客户对外展示价；
- 名邦车源：看当前对外展示价；
- 4S 车源：看当前对外展示价；
- 价格咨询车辆：显示“价格咨询”。

必须严格区分：

> **对外价格 ≠ 内部价 / 批发价**

`upstream_publisher_id`

> 能做哪些高风险操作。

# 11. P07｜Lock / 候补 / 意向金 / Transaction / 退款

- 退款；

## 11.1 Lock 时长

当前统一：

> **默认 72 小时，后台可配置。**

新 Lock 创建时按当时配置生成 `expires_at`。

之后修改默认锁车时长：

> **不追改已经创建的 Lock。**

已收意向金的 Lock 不因普通 72 小时超时自动释放。

## 11.2 候补

候补：

- 不占车辆；
- 不自动升级成 Lock；
- Lock 释放后仍需人工重新确认是否锁车。

后台不得提供“自动候补顶锁”开关。

## 11.3 成交纠错

旧后台规则中：

> “授权经理 / 店长 / System Admin 等按权限直接纠错”

正式废弃。

当前规则：

- 普通销售不能直接纠正已成交 Transaction；
- 具备对应交易纠错业务权限的经理 / 店长可以执行；
- 必须填写原因；
- 必须完整审计；
- 不做二级审批；
- **System Admin 身份本身不具备成交纠错业务权限。**

同一真人如果同时有 System Admin 和员工身份，必须使用员工身份执行交易纠错。

## 11.4 退款

退款主状态继续只保留：

- `pending`
- `refunded`

部分退款通过多笔实际退款事实表达，不新增 `partial` 主状态。

# 17. 配置统一原则

## 17.1 配置必须有明确业务归属

配置不建设一个脱离业务的“大杂烩配置中心”。

配置放回对应业务模块：

- Lock 时长 → P07；
- 公海 / CRM 提醒条件 → P06；
- 查价 / 阶梯加价 → P08；
- SLA / 夜间免打扰 / 飞书 → P09；
- Banner → P12；
- 上游集成 → P03；
- 权限 / 数据范围 → P04。

## 17.2 配置修改不能偷偷改写历史事实

已经创建并固化的业务对象：

- Lock `expires_at`；
- consultation 首次响应 deadline；

不得因为后来后台改默认配置而追溯重写。

## 17.3 配置变更可追溯

会改变业务行为、权限、安全或客户展示结果的重要配置必须记录：

- 修改前；
- 修改后；
- 操作人；
- 时间。

是否强制填写原因：

> 按对应业务规则执行；没有明确要求的，不额外强制。
